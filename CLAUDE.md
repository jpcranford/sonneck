# CLAUDE.md — House Rules & Conventions

Companion to `sonneck-design.md` (the design doc for **Sonneck**, named after Oscar Sonneck, the American musicologist and first head of the Library of Congress's Music Division — see the root README's "About the name" section for the full story). Re-read this file at the start of every session — its job is to keep cross-cutting decisions consistent across many separate sessions, which a design doc alone won't do.

`CONTRIBUTING.md` mirrors several of the rules below (migrations, the API contract, testing requirements) for human contributors, in its own words. When changing any of those here, check whether `CONTRIBUTING.md` needs the same update — it's a second copy by necessity (different audience), not a generated one, so it doesn't update itself.

## Database migrations
Tool: **goose**. Every schema change is a migration file, checked into the repo, never a hand-edited change to an existing migration. Several fields are already known to be coming later (`composerDeathYear`, `SheetType.definition`, custom fields — see design doc §13), each gets its own new migration when it lands, not a retrofit into v1's schema. (Reconsidered whether a lighter-weight approach than a dedicated migration tool would do for a small project — kept `goose` regardless, since this risk is driven by session count across a vibe-coded build, not team size, and the tool itself is small and low-overhead.)

**Deliberate exception:** `copyrightYear` (int) and `publicDomain` (bool) are pre-built into v1's `Piece` schema now, unused, even though the feature they belong to (the public-domain badge, design doc §13) is deferred — see design doc §3 for the reasoning. This is a one-off exception for these two specifically (cheap, simple columns), not a general license to pre-build ahead of features. `composerDeathYear` — part of the same deferred feature — does *not* get this treatment and arrives as a normal migration if/when that feature is built.

**Deliberate deviation from design doc §3:** `Piece.key` is many-to-many (`Piece.keys`), not the single `key` tag/FK column §3 specifies. Requested directly ("a piece can have multiple keys in it" — a piece that modulates, or a medley, can legitimately need more than one), not surfaced by a compliance review. Migration `00008_piece_keys_many_to_many.sql` adds a `piece_keys` join table (same shape as `piece_instruments`) and drops `pieces.key_id`; the down migration is lossy by necessity (collapses to `MIN(key_id)` per piece) and documented as such inline. Keys remain explicitly *not* book-inheritable, same as before this change — this is about single- vs. multi-valued, not about inheritance, so it doesn't conflict with §3's inheritance reasoning. Not reflected back into `sonneck-design.md`, same convention as the rest of this file.

**Follow-on, 2026-08-17:** the same reasoning extends to a piece modulating back to a key it already used (e.g. C Major → G Major → C Major) — `piece_keys` originally had `PRIMARY KEY (piece_id, key_id)`, which silently made that impossible (a repeat insert would hit the PK). Migration `00012_piece_keys_allow_repeats.sql` recreates the table with `PRIMARY KEY (piece_id, position)` instead (`position` already existed per-row since migration `00011`, so this reuses it rather than adding a surrogate key); the down migration is lossy the same way `00008`'s is (collapses repeats to the earliest `position` per `(piece_id, key_id)`). Frontend side: `TagComboBox` gained an `allowDuplicates` prop (Key(s) picker only — Instruments/Your Tags don't need it) and switched its selected-pill list from keying/removing by `tag.id` to keying/removing by array index, since two pills can now legitimately share an id.

## API response contract
Every endpoint returns one of two shapes — no per-handler improvisation:
```json
// success
{ "data": { ... } }

// error
{ "error": { "code": "VALIDATION_ERROR", "message": "human-readable description" } }
```
If a decision point isn't covered by this doc, default to this shape rather than inventing a variant.

## Testing
No comprehensive test suite is required for v1, but one area is **not optional** because failures there are silent and permanent:
- **PDF page-extraction logic** (the import wizard's split step) — a wrong page range is a data-correctness bug nobody notices until they open the piece later. Needs unit tests covering at least: single-page piece, multi-page piece, first piece includes page 1, last piece includes the final page, off-by-one boundaries between adjacent pieces.

(Public-domain calculation testing was flagged as similarly load-bearing in an earlier pass — that requirement is deferred along with the feature itself; see design doc §13. Revisit this section when that feature is built.)

Everything else: use judgment, but the PDF-extraction logic above is load-bearing.

## Live browser verification (dev tooling, not app code)
No MCP browser tool is configured in this environment — `ToolSearch` for "playwright"/"chromium"/"mcp" comes back empty, and every project's `mcpServers` in `~/.claude.json` is `{}`. A real Chromium is still available, though: `npx playwright` caches a full install — including the browser binaries themselves, under `~/Library/Caches/ms-playwright/` — to `~/.npm/_npx/<hash>/node_modules/playwright/`. Confirmed working 2026-08-17 (found via `find ~/.npm/_npx -maxdepth 3 -iname playwright`; run `npx playwright --version` once first if that comes up empty, to populate the cache). Drive it directly with a hand-written Node script through Bash, e.g.:
```js
import { chromium } from '/Users/<user>/.npm/_npx/<hash>/node_modules/playwright/index.mjs'
const browser = await chromium.launch()
const page = await browser.newPage({ viewport: { width: 1000, height: 1000 } })
await page.goto('http://localhost:5173/...')
// ...interact, assert, page.screenshot()...
await browser.close()
```
Needs both dev servers already running — backend on `:8080`, Vite on `:5173` (check with `lsof -iTCP -sTCP:LISTEN -P` rather than assuming either is up or down). Use this for anything a type-check or unit test can't actually catch — a real click-through sequence, animation/transition timing, DOM state after an interaction — rather than reporting "type-checks clean" as if that were equivalent to having verified the feature live.

**The dev library at `./data` (`DATA_DIR`) is read-only for Claude — direct instruction, 2026-08-18.** Earlier sessions mutated real piece records during live checks (editing a piece, toggling favorite) and restored them afterward via a follow-up API call; that's no longer good enough — don't write to it at all, through the app's own endpoints, direct SQL, or file operations. Live verification stays read-only (navigate, view, screenshot). If a check genuinely needs to mutate state to prove a feature, use a disposable piece/book created in a separate, throwaway location instead of touching the real dev library, or ask the user how they'd like it verified.

**Disposable-backend recipe for verifying a write flow, proven working end to end 2026-08-18** — don't re-derive this from scratch each time:
1. Start a second Go backend on a different port against a temp dir: `PORT=8099 DATA_DIR=<scratchpad>/throwaway-data go run ./cmd/sonneck` (migrations run automatically against the fresh temp DB).
2. Don't edit the committed `frontend/vite.config.ts` for a one-off check. Write a throwaway config instead (`proxy: { '/api': 'http://localhost:8099' }`, different port) — it must live **inside `frontend/`** (e.g. `frontend/vite.throwaway.config.ts`), not in the scratchpad directory, since Vite/Node resolves the config's own `node_modules` relative to its own location.
3. Run `npx vite --config vite.throwaway.config.ts` from inside `frontend/` — runs alongside the real dev server, not instead of it.
4. Drive Playwright at the throwaway Vite's port. Real writes land in the throwaway DB only.
5. Clean up afterward: kill both throwaway processes, `rm` the throwaway config and `DATA_DIR`, confirm via `lsof`/`git status` that only the real 8080/5173 pair is still listening and nothing leaked into the repo.

**The long-running dev backend doesn't hot-reload.** Adding a new backend route mid-session and testing it against the already-running `go run ./cmd/sonneck` process produces a "no such endpoint" error that looks like a code bug but is actually just a stale process — restart it (recover its env vars via `ps eww -p <pid>` if not already known; restarting doesn't touch `DATA_DIR`).

**Verify fine visual details with pixel data, not by eyeballing a screenshot.** Visual inspection is unreliable for shape-topology questions (is a glyph's counter actually open or closed) and gradient-fidelity questions (does an overlay render monotonically, how far does a color actually shift) — proven wrong repeatedly on this project before switching to programmatic checks: flood-fill connectivity analysis (render to canvas, classify ink/background, flood-fill from all four edges, count unreached background pixels) for open/closed questions; clean scanline pixel sampling (routed around any glyph/foreground content, not straight through it) for gradient monotonicity and color-delta questions. This is *in addition to* normal visual QA (layout, color, spacing are fine to eyeball) — specifically for fine-fidelity questions where the failure mode is a defect too subtle to reliably see by eye.

**Verify against data missing the relevant optional fields, not just happy-path fixtures.** A layout change involving a conditionally-rendered element (e.g. `justify-between` against a sibling that can render `null`, like `TagPills` with no tags) can look correct against test data that happens to have everything filled in, and break silently the moment that field is empty — which is often the common case, not an edge case. Check at least one render with the relevant fields absent before considering a layout change verified; prefer `margin-left: auto`/`ml-auto` over `justify-between` when the pinned element's sibling might not render.

**Inline images/screenshots don't render for the user in this chat client.** Save any screenshot or comparison image the user needs to actually see to `design-review/` (gitignored, already used for this) and tell them it's there — don't rely on an inline image actually being visible. Published Artifacts are unaffected (they render in their own viewer); this only applies to raw image files shown inline in conversation.

## Concurrency
v1 is single-user, single-session (see design doc §8). Do not build multi-writer conflict handling. Do enable SQLite WAL mode at startup regardless — cheap, no design cost, cost of skipping it isn't worth the reason to skip it.

**Naming/architecture note:** `Piece.userNotes`, `Piece.userTags`, `Piece.favorite`, and `Piece.practiceStatus` will all be genuinely account-scoped and different per-user once multi-user support lands (confirmed, not just speculative) — but there's no user model in v1 to scope them to yet (see above). **Resolved:** keep them simple in v1 (as currently structured — plain fields and a shared-catalog many-to-many for tags) and accept a real migration when multi-user lands, rather than pre-building relational structure now — same treatment as `composerDeathYear` above, for the same reason (not cheap/simple enough to justify pre-building unused). One detail worth remembering for that future migration: `userTags` is confirmed to become a **fully private per-user vocabulary** once multi-user lands (no shared tag catalog across users, unlike `Key`/`SheetType`) — a bigger restructuring than just adding a `userId` column, since it changes what a "tag" even is (user-owned, not globally shared), so budget the future migration accordingly rather than assuming it's a small add-a-column change.

## Book-level soft inheritance
Full mechanism in design doc §3/§14/§15/§16 — this section is about the implementation convention, not the feature itself.

**One shared "resolve effective piece values" helper, used everywhere a book-inheritable field is read** — display (Piece Details page, edit menu), validation, citation generation (design doc §6), and search indexing (below) all need the same piece's-own-value-falling-back-to-book's-value resolution. Implement it once, call it from all four places. Do not let validation or citation generation read `Piece` columns directly for `composer`/`publisher`/`publisherId`/`imslpNumber`/`yearWritten`/`workOpusNumber`/`instruments`/`sheetType` — that would silently diverge from what's displayed, which is exactly the kind of inconsistency this pattern exists to avoid.

**Saving a `Book` edit (design doc §16) writes to exactly one record — the `Book` itself.** Nothing about any `Piece` row changes. What changes is what gets *read*: every piece with that `sourceBookId` and no override for the changed field resolves its effective value live against current `Book` data (the shared helper above), so the result naturally reflects the edit without the app writing to any `Piece` row. This still needs: a search-index resync for every affected piece's `pieces_fts` row (not the underlying `Piece` row — see Search below, this is a property of how the search index denormalizes data, not of the data model itself), and ideally a UI-level "this affects N pieces" indication so it doesn't read as a surprising side effect.

**`sourceBookId` itself became editable from the Piece Properties Edit Menu (added 2026-08-19)** — new capability, not in the original design doc (§15 never described re-matching a piece to a different book after the fact; this is additive, not a deviation). `PieceWriteRequest.SourceBookID` (`*int64`) follows the same full-replace rule as every other field: a non-nil value must reference a real, existing `Book` — `applyPieceWriteRequest` (`internal/handlers/piece_write.go`) checks this explicitly via `repo.GetBookByID` and returns a `ValidationErrors` naming the field (`sourceBookId`) rather than letting a bad id surface as an opaque 500 later out of `repo.ResolveEffective`; `nil` clears the association entirely. The wizard's per-piece fill step (confirm-import) sets `SourceBookID` on the model *before* calling `applyPieceWriteRequest`, then re-asserts it *after* — the same guard already in place for `SourcePageStart`/`SourcePageEnd`, since the wizard's own request body never carries a `sourceBookId` key and would otherwise get it nulled back out by the general-case full-replace handling. Frontend: `SourceBookField` (`frontend/src/components/SourceBookField.tsx`) is a debounced search-as-you-type picker against `GET /api/books` (design doc §11's existing convention) — it does not offer a create-new affordance; a source book must already exist.

**Deliberate deviation from design doc §16's wording:** §16 states Books have no required fields at all ("a book can exist with only bookTitle set and nothing else"). In practice, `ValidateBook` (`internal/api/validate.go`) does require `bookTitle` to be non-empty. Confirmed intentional, not a bug — a Book with no title at all would be a confusing empty state anywhere it's displayed (the Piece Details page's own Book Details section, a future library-of-books view), and the wizard already defaults it from the upload filename in every real path anyway, so the practical cost of requiring it is zero. §16's own text is read as emphasizing the *contrast* with `Piece`'s two required fields (title/composer) rather than a strict "nothing is ever required" validation spec. Not reflected back into `sonneck-design.md` — that file stays as the original planning artifact; this file is where the deviation is tracked, per this file's own stated purpose.

## File handling
- All file hashing uses **SHA-256** (`crypto/sha256`, standard library — not BLAKE3, see design doc §2 for why), streamed incrementally during upload via the standard `hash.Hash` interface — never buffer a full 100+MB file into memory before hashing.
- **Duplicate upload behavior:** dedupe on SHA-256 hash match — reuse the existing `Book` record, never create a second copy of the same file. The single-piece upload path (design doc §5, no book involved) gets the same treatment: `POST /api/pieces` checks for an existing `Piece` with a matching hash first and, if found, returns it (`200 OK`) instead of creating a duplicate row; the frontend routes the user straight to that existing piece's page rather than showing the fill-in-details step meant for a genuinely new upload. **Deliberately scoped to this one endpoint only** — the book-import wizard's confirm step still creates sibling pieces via `repo.CreatePiece` directly with no hash check, and that's intentional: two different pieces split from the same book can legitimately end up byte-identical (e.g. duplicate blank pages), and that's not a duplicate upload to collapse. Don't add a DB-level `UNIQUE` constraint on `pieces.file_hash` (unlike `books.file_hash`, which does have one) — it would break that legitimate wizard case.
- **Deletion semantics (confirmed):** hard delete + orphan cleanup. Deleting a `Piece` removes its DB row and its extracted file. If that was the last `Piece` referencing a `Book`, the `Book` record and its original file are deleted too (no indefinite orphan retention). Both piece deletions and orphaned-book cleanups must be logged — see Logging below.
- **`Book` fields are not denormalized onto `Piece`** (design doc §3) — the Piece Details page resolves book-level display live via `sourceBookId → Book`, edited through the Book Properties Edit Menu (design doc §16), not stored copies on `Piece`. This is deliberate: don't add a "sync book fields to all pieces" step anywhere in application code, since there's nothing to sync — the join makes every piece reflect the current book data automatically. If a future feature ever needs book data to be point-in-time/historical rather than always-current, that's a real design conversation to have, not something to solve by quietly denormalizing it back.
- **`Book` is entirely optional** (design doc §3) — `Piece` is the app's actual primary unit, and a piece with no `Book` at all (via §5's single-piece upload) is a normal, first-class case, not an edge case to special-case around. Don't write code that assumes `sourceBookId` is usually present.
- **File replacement** (design doc §14): hard-replace on the same `Piece` record, not a new piece — same no-soft-delete philosophy as piece/book deletion above. `sourceBookId`/`sourcePageStart`/`sourcePageEnd` are kept as historical provenance after a replace, per an explicit decision — don't clear them, and don't assume they still describe the current file's exact page range.

## Logging
Use the standard library's **`log/slog`** (structured logging, built in since Go 1.21 — no third-party library needed, hence the version floor in the design doc's stack table).

Deletions (piece deletion, cascading orphaned-book cleanup) **and piece file replacement** (design doc §14) are logged at **INFO level**, not DEBUG or WARN/ERROR. This follows standard practice: INFO is the conventional level for production systems, and destructive-but-expected user actions belong there so they're visible in normal production logs rather than hidden behind DEBUG (typically disabled in production) or miscategorized as a warning/error when nothing actually went wrong. Reserve WARN/ERROR for things that are actually problems.

Use structured fields, not string interpolation — e.g.:
```go
logger.Info("piece deleted", "pieceId", piece.ID, "fileHash", piece.FileHash, "title", piece.Title)
logger.Info("orphaned book cleaned up", "bookId", book.ID, "fileHash", book.FileHash, "reason", "last referencing piece deleted")
logger.Info("piece file replaced", "pieceId", piece.ID, "oldFileHash", oldHash, "newFileHash", newHash)
```
This keeps logs greppable/filterable (e.g. `level:info AND pieceId:...`) rather than requiring regex over free text.

## Config
- All global settings are env vars (no settings table in v1) — see design doc §3. Includes `BACKUP_CRON` (backup schedule, standard cron expression, default `0 3 * * *`) as of this revision.
- Validate all env vars at startup and fail fast with a clear message rather than failing later mid-request (e.g. `BACKUP_RETENTION_DAYS` isn't a valid integer, `BACKUP_CRON` isn't parseable). A `COPYRIGHT_REGION` validation rule was specified in an earlier pass, tied to the now-deferred public-domain feature — revisit this when that feature is built (design doc §13).
- **How env vars get set is entirely a Docker Compose concern, not application code.** `environment:` block in `docker-compose.yml` (this project's own choice) vs. a sibling `.env` file are both natively supported by Compose — the app just reads env vars the same way either way. Don't build anything app-side to support one or the other.
- **Backup scheduling** uses `robfig/cron` (pure Go, no CGO, well-known/standard choice — same dependency posture as `modernc.org/sqlite`/BLAKE3-vs-SHA256 elsewhere in this doc) to parse `BACKUP_CRON` and drive the daily `VACUUM INTO` snapshot (design doc §4).
- **`CITATION_FORMAT` is loaded and validated but not actually consulted by citation generation** — `buildCitation` (`internal/handlers/citation.go`) hardcodes the format in Go rather than reading `Config.CitationFormat` and doing token substitution against it. Confirmed intentional, not unfinished work: blank-field omission (a citation must skip a blank field's surrounding punctuation entirely, not render it empty — design doc §6) doesn't fit a plain-substitution model, and a real conditional-template engine is explicitly deferred (design doc §6, §13). This means changing the `CITATION_FORMAT` env var currently has **no effect** — a direct deviation from design doc §6's "`CITATION_FORMAT` env var supports plain token substitution." Left as-is deliberately; not reflected back into `sonneck-design.md`, which stays as the original planning artifact.
- **Citation's `yearWritten` component renders the field's stored value verbatim, with no automatic "ca. " prefix** — a deliberate deviation from design doc §6's literal "ca. {yearWritten}" wording, caught during the Piece Details mockup review (2026-08-16). `yearWritten` is free text specifically so it can carry its own approximate-date qualifier when warranted (design doc §3: `"ca. 1708-1711"`); an unconditional prefix would misrepresent a precisely-known year (`"1848"`) as merely approximate. Any "ca." belongs in the value itself. `buildCitation` (`internal/handlers/citation.go`) updated accordingly; no existing test asserted the old prefix. Not reflected back into `sonneck-design.md`, same convention as the rest of this section.
- **Four more citation deviations, added 2026-08-17 (direct instruction):**
  1. **Arranger now appears in the citation**, fused onto the composer as `"{composer}, arr. {arranger}"` — a direct reversal of design doc §6's explicit exclusion of arranger from the citation format. Only renders when composer is non-blank (an arranger credit with no composer to attach to is dropped, same reasoning as the publisherId-with-no-publisher case above not inventing one either).
  2. **IMSLP number now renders as `"IMSLP #{number}"`** instead of the raw stored value verbatim. A new `stripImslpPrefix` helper (`internal/handlers/citation.go`) strips any leading `"IMSLP"` (with or without a following space/colon/hash/dash, case-insensitive) from the *effective* value before formatting, so old data already carrying it (e.g. a stored value of `"IMSLP04154"`) doesn't render doubled. `EditPieceModal.tsx` also strips the same prefix from the value itself before every save (its own `stripImslpPrefix`, independently implemented — not shared code across the Go/TS boundary), so newly-saved data stops carrying the prefix in storage at all; the backend-side stripping stays regardless, since it's the only thing that also normalizes pre-existing data and data written before this change.
  3. **The book-title citation component now also carries the book's own opus number** (`Book.WorkOpusNumber`, fetched directly — not the piece's *effective* one) as `"{bookTitle}, {bookWorkOpusNumber}"`, **unless** that book opus number (spaces ignored) is already contained in the piece's own effective `workOpusNumber` — which is true whenever the piece doesn't override it (pure inheritance) or overrides it with something that still incorporates the book's number (book `"Op. 68"`, piece `"Op. 68, No. 9"`). Without this, a piece in a book both carrying opus numbers would show the same number twice in one citation — once from the book-title segment, once from the piece's own `"({workOpusNumber})"` parenthetical next to the title. New helper `containsIgnoringSpaces` in the same file.
  4. **A double quote character inside the title itself renders as a single quote**, before the whole title gets wrapped in the citation's own double quotes — a title like `Merry-Go-Round of Life from "Howl's Moving Castle"` would otherwise collide with the citation's wrapping quotes (`""Howl's Moving Castle""`), ambiguous as to which quote closes what. Standard nested-quote convention (outer double, inner single) resolves it — `strings.ReplaceAll(title, "\"", "'")` applied only to the title, right before it's wrapped.

  None of these four are reflected back into `sonneck-design.md`, same convention as the rest of this section.

## Operational basics
- `/healthz` endpoint, used by the Docker healthcheck.
- Backup: daily `VACUUM INTO` snapshot of the SQLite DB (design doc §4). Restore: stop container → replace the DB file → restart. Document this in the README, not just implied.

## Search
SQLite FTS5, not a separate search engine like Bleve — see design doc §2 for the full reasoning (StashApp's approach was the starting inspiration; FTS5 achieves the same goal with less operational overhead for this project's scale).

- Virtual table: `pieces_fts`, one row per `Piece`, denormalized content per design doc §3 — **book-inheritable fields are indexed by their effective value** (the shared resolution helper above), not the raw `Piece` column, or search would miss pieces that only inherit a value from their book.
- **Sync mechanism:** application-level — an explicit `resyncSearchIndex(pieceId)` call after any `Piece` or tag-assignment mutation, run in the same transaction as the mutation itself. Not SQL triggers: trigger logic spread across `Piece` and several tag join tables is harder for a Go-focused contributor to discover and test than one function called from application code, which fits this project's existing maintainer-accommodation reasoning (design doc §2's TypeScript choice, for one). Real trade-off accepted: this relies on remembering to call it at every mutation site, so a shared repository/service-layer helper (not ad hoc calls scattered through handlers) is worth building for exactly that reason. **Editing a `Book` field (design doc §16) must resync every affected `Piece`, not just call this once** — loop over every piece with that `sourceBookId` lacking its own override for the changed field.
- The `pieces_fts` table is derived data, not a source of truth — if it's ever suspected out of sync, it can be safely dropped and rebuilt from `Piece` and the tag tables. Same principle as StashApp's own index philosophy, just without needing a scheduled staleness check to trigger it.
- **Manual full rebuild**: exposed as a CLI subcommand, not an HTTP endpoint — see the general pattern below.

**General pattern for admin/maintenance actions before real auth exists:** default to a CLI subcommand on the same binary, gated by shell/`docker exec` access to the container, rather than an HTTP endpoint with no auth to protect it. The search-index rebuild is the first concrete instance of this; treat it as the template for future maintenance actions (e.g. anything that comes up before OIDC/multi-user, §13, actually lands). Reuse the app's existing config/DB-connection bootstrap code in these subcommands rather than duplicating it — the CLI command and the server should read the same config the same way. Commands that write to the SQLite file while the server may still be running rely on WAL mode (already an established v1 convention, see Concurrency above) for safety — this is the one deliberate exception to "single writer" in an otherwise single-user/single-session v1.

- **Second instance of this pattern (2026-08-16): `regenerate-thumbnails`.** Wipes `data/cache/thumbnails` (derived data, same "safely dropped and rebuilt" reasoning as `pieces_fts`) and re-renders every page of every piece from scratch — the recovery path if a cached thumbnail is ever suspected corrupted (a real, confirmed bug: a torn/truncated PNG from a page-render race, now fixed — see `internal/handlers/helpers.go`'s `cachedThumbnail`/`regenerateThumbnail`), without needing to know which cache entries are actually bad. Also cleans up orphaned entries for since-deleted pieces, since the wipe isn't scoped to currently-known pieces. Safe against a live server for the same WAL-mode reason as `rebuild-search-index` — writes land via an atomic rename, so a concurrent live thumbnail request never observes a partial file.

- **Third instance of this pattern (2026-08-20): `export-csv`.** A full data export, one CSV file per real table, written to a new timestamped subdirectory of `data/export/`. Read-only against the database (no admin action so far has been read-only, but the pattern still applies — same auth-gap reasoning, same "reuse the app's own bootstrap" rule). Table/column lists come from `sqlite_master`/`rows.Columns` rather than a hardcoded list, so a future migration's new table is picked up automatically; `goose_db_version`, `sqlite_sequence`, and `pieces_fts` + its FTS5 shadow tables are explicitly excluded as internal/derived, not real library data (same "safely dropped and rebuilt" tables called out for `pieces_fts` above — exporting them would just be noise in a dump meant to hand someone their actual library back). See `internal/export/export.go`.

## Frontend
- **Shell scope:** build the sidebar nav/route shell to accommodate *all* planned features from early on, not just whatever's functionally wired up in the current commit — scaffold-and-hide a not-yet-built feature (route/component exists, reachable in code, visually present even if stubbed or disabled) rather than omitting it as if undecided. The failure mode to watch for is the opposite one: building only the current commit's narrow slice and losing track of the rest of the design doc.
- **Language:** TypeScript. Types should mirror the backend's `{data}`/`{error}` API contract (see above) — this is the main defense against frontend/backend drift across sessions.
- **Icons:** Tabler Icons via `@tabler/icons-react` — the scoped package, not the older unscoped `tabler-icons-react` (stale, last published years ago). Import icons by name; never `import *` (defeats tree-shaking).
- **No AI-generated visual assets.** Logo/brand/icon work stays hand-authored (SVG built from primitives/paths written by hand, not sourced from an image generator like Recraft) — most such tools' Terms of Service don't permit releasing the output under an open-source license, which conflicts with Sonneck being open-source. Check ToS compatibility with open-source redistribution before adopting any AI-generated asset; don't assume it's fine because the tool is popular or the output looks clean.
- **Data fetching:** TanStack Query for all API calls — one consistent caching/loading/error pattern, not ad-hoc `useEffect`+`useState` per component.
- **Forms:** react-hook-form, with **light** client-side validation only — required fields and obviously-plausible ranges. The backend (design doc §5's validation table) remains sole authority; don't maintain a full second copy of every backend rule as a mirrored zod schema, since keeping two validation definitions in sync in two languages is exactly the kind of drift risk not worth taking on for this project's size. Surface whatever error the backend returns for anything beyond the cheap checks. All line-text inputs share a 255-char max (design doc §5); box/multi-line inputs (`description`, `userNotes`) don't.
- **Computed fields — deliberate deviation from design doc §3 (2026-08-16):** `Piece.duration` is a plain, directly user-entered field (`mm:ss` in the UI, stored server-side as an integer of seconds), *not* recomputed from `bpm`/`measureCount`/`beatsPerMeasure` on every write, contrary to §3's "recalculate and store whenever those three change." The Edit Piece Menu (§15) has its own manual `mm:ss` duration input plus a one-shot "Calculate" convenience button that fills it in from the tempo fields using the same formula the backend used to apply automatically — but nothing re-applies that formula server-side once saved. `bpm`/`measureCount`/`beatsPerMeasure` remain stored and independently editable; they're now purely informational/calculator inputs, no longer mechanically driving `duration`. Chosen over two alternatives (keep server-side auto-compute authoritative with a conditionally-read-only field; add a separate manual-override column alongside the computed value) specifically for simplicity — this was a direct, explicit choice, not something decided silently. `PieceWriteRequest.Duration` is a normal `*int`; omitting it on a write clears it, same full-replace rule as every other field. Not reflected back into `sonneck-design.md`, same convention as the rest of this file.
- **Styling:** Tailwind CSS with the high-contrast palette defined once as theme tokens, not re-picked per component. Formal accessibility compliance (WCAG auditing, full ARIA coverage) is a **tertiary concern for v1** — see design doc §10. The actual driver is a clean, non-distracting, intuitive interface (calmer wizard flow, restrained notifications, one thing at a time rather than dense all-at-once forms).
- **Routing:** React Router. Wizard steps are real routes.
- **API calls:** relative paths (`/api/...`), same-origin — no base URL config, no CORS, a direct consequence of the single-image architecture.
- **Wizard draft persistence:** `localStorage`, keyed by `bookId`, storing split points + in-progress field values. Restore on return to an in-progress import; clear on confirm or explicit cancel. See design doc §5.
- **Mobile scope:** the import wizard must work well on phones/small tablets, not just the browse/view screens — this needs deliberate touch-friendly interaction design for the split-marking step, not just responsive CSS carried over from a desktop layout.
- **Component choices:** where an accessible pattern (e.g. a proper combobox for tag entry) is also just the better component generally, use it — this isn't extra compliance work, it's picking the better tool. Don't do additional accessibility-only work with no general-UX upside (full keyboard-nav audits, ARIA completeness as its own task) — that's the part actually being deprioritized.
- **Dropdown keyboard nav is a standing requirement, not the blanket accessibility work the previous bullet deprioritizes (added 2026-08-19):** every dropdown-style field — `TagComboBox`, `SingleSelect`, `SourceBookField`, and any future one — must support ArrowUp/ArrowDown (move a highlighted row through exactly what's rendered, wrapping at both ends) and Enter (pick the highlighted row). `TagComboBox`'s variant resets the highlight to row 0 on every keystroke (so Enter with no arrow presses acts on "the top result," or creates a new tag when nothing matches); `SingleSelect`'s variant seeds the highlight from the *currently selected* option when a closed menu opens via an arrow key, since there's always a real current value there. When auditing for compliance, grep for the shared dropdown-panel markup (`absolute z-10 mt-1 w-full overflow-hidden rounded-md border border-border bg-paper-raised py-1 shadow-lg`) across `frontend/src` rather than trusting memory of which components exist — a new dropdown-style field is not done until it has this.
- **Icon colors are always a solid pre-blend, never a translucent opacity utility (added 2026-08-19):** no `text-ink-soft/40`, `opacity-70`, `opacity-[0.85]`, etc. applied to or inherited by a Tabler icon. Many icons render as several overlapping `<path>` elements sharing one stroke color (`book-off`'s diagonal slash, `plus`'s crossing lines, `file-x`'s corner joins, `IconInfoCircle`'s circle+dot+line) — a translucent color re-blends at every overlap, leaving visibly darker patches exactly there, distinct from the flat color elsewhere on the same glyph. First found on the "No-File Cover" icons, re-confirmed via both computed styles and rasterized-pixel sampling; a 2026-08-19 audit found and fixed ~20 more instances across `EditPieceModal`, `PiecePage`, `TagComboBox`, `SingleSelect`, `SourceBookField`, `Sidebar`, `BookListCard`, `BookDetailsPage`, and their mockup counterparts. Fix: compute the solid hex the alpha would have produced against the icon's actual background (same per-channel blend math each time) and hardcode it via an arbitrary-value class (`text-[#9d9892]`). Applies uniformly regardless of whether a given icon's paths happen to self-intersect — simpler as a blanket rule than re-litigating per icon. Text (labels, placeholders, captions) is unaffected — this is specific to icon stroke colors.
- **Serif heading weight (added 2026-08-20):** every serifed heading (Libre Baskerville) and all sidebar text renders at `font-medium` (500) minimum, app-wide, including mockups. Never bump italic font-display text to 500 — no 500-weight italic Libre Baskerville file exists, so it would silently fall back to regular or trigger inconsistent browser-synthesized bold instead.
- **`tsc --noEmit -p .` is a silent no-op — critical, added 2026-08-20:** `frontend/tsconfig.json` is a solution-style config (`{ files: [], references: [...] }`). Running the type-checker against it type-checks nothing and reports no errors either way, which looks identical to a clean pass. Always run `tsc --noEmit -p tsconfig.app.json` instead — never `-p .`.
- **Dot separator is a bullet (`•`), not an interpunct (`·`) — added 2026-08-20**, in every `"{a} · {b}"`-style metadata label. Recurs easily in freshly-built `/mockup/*` screens, since their source design artifacts often carry the stale interpunct glyph — grep for `·` across `frontend/src` when finishing a new mockup or metadata line.
- **Page abbreviation is the academic `p.`/`pp.` convention app-wide (singular vs. a range) — added 2026-08-20**, never `pg.`. Applies everywhere a piece's source page range is shown (Piece Details, Book Details, citation).
- **React lint gotchas, worth knowing before they cost you time re-discovering them:** `react-hooks/refs` forbids assigning `ref.current = value` directly in a component's render body ("Cannot access refs during render") — do the sync inside a `useEffect` instead. `react-hooks/set-state-in-effect` flags a `setState` call inside an effect; where it's a genuine external-trigger sync rather than a same-render feedback loop, the resolved pattern on this project is a scoped `eslint-disable-next-line` with a comment justifying why (see `Modal.tsx`/`EditBookModal.tsx` for precedent) — not restructuring the code to dodge the rule. `react-refresh/only-export-components` flags a component file that also exports non-component constants (e.g. a shared data array) — breaks Fast Refresh for that file; move the constants into their own module instead (see `lib/navItems.ts`, split out of `Sidebar.tsx` for this exact reason).
- **Card-style navigation renders a real `<a>`, not a click-handled `<div>` — added 2026-08-22:** `ClickableCard` (used by `PieceGridCard`/`PieceListCard`/`BookGridCard`/`BookListCard`/Book Details' own piece cards) wraps React Router's `Link`, not a `div role="button"` with an `onClick` navigate. A synthetic click handler has no `href` for the browser to act on, so cmd/ctrl/middle-click and right-click → "Open in new tab" silently don't work with it — a real anchor gets all of that natively, for free. Any new card/list-row navigation component should route through `ClickableCard` rather than reinventing div+onClick. Nested interactive children (`PageCycleControl`, `TagPills`, `ContextMenu`) already call `stopPropagation()` on their own click/mousedown handlers, so they don't trigger the card's own navigation regardless of div-vs-anchor.
- **"Back" controls use real browser history, not a hardcoded destination — added 2026-08-22:** Piece Details' back button calls `navigate(-1)`, falling back to `navigate('/')` only when `location.key === 'default'` (no real history entry exists — a direct link or hard refresh), so it behaves like the browser's own back button rather than always returning to one fixed route. Its label is dynamic, sourced from `location.state.backLabel` — every entry point that navigates to a page with this pattern passes `state: { backLabel: 'Library' | 'Book' | ... }` (via `ClickableCard`'s `state` prop or `navigate`'s own `state` option) so the control reads "Back to Library"/"Back to Book"/etc. instead of a fixed generic label. A chain of same-type navigations (e.g. Piece Details' "Practice Another") should forward the current `location.state` along rather than resetting it, so the label stays accurate through the whole chain.
- One cheap habit worth keeping regardless: don't rely on color alone to distinguish tags/keys — pair with text or shape.
- **Device-aware conventions (design doc §12):** buttons over sliders (or both); progress bars over spinners wherever progress is measurable; no hover-dependent interactions — tap-triggered info buttons instead of hover tooltips. These apply across v1, not just the deferred Sheet Viewer.
- **Search-as-you-type** (design doc §11): debounced (~200-300ms) query against the backend, not a full client-side filter over the whole library.
- **Uploads:** show real upload progress (not just a spinner) for 100+MB files, plus client-side file-type/size checks before the request starts.
- **Linting/formatting:** ESLint + Prettier, standard config.
- **Testing:** not comprehensive for v1, but the wizard's page-range calculation/display logic (mapping thumbnails to piece boundaries) should have unit tests — same "silent, permanent correctness bug" risk as the backend's PDF-extraction logic in Testing above, just on the frontend side of the same operation.

## Docker / build
**Packaging gate lifted 2026-08-23, direct instruction** (was on hold since 2026-08-15 — see git history for that period's reasoning if it matters later). Docker packaging is built and live: the repo is public, the image is public on GHCR, and the first real release (`0.1`, "Giant Steps") produced a real multi-arch build — confirmed pullable with no auth (`docker manifest inspect ghcr.io/jpcranford/sonneck:latest` lists both `linux/amd64` and `linux/arm64`), not just assumed working from a green CI checkmark.

**Real prerequisite this surfaced, not previously built despite the design doc describing it:** nothing embedded the frontend or served it before this — `internal/handlers/server.go`'s catch-all route used to return a JSON 404 for literally every non-`/api` request. Fixed via a new `internal/webui` package: `//go:embed all:dist` (a committed placeholder `index.html` lives in `internal/webui/dist/` so the embed compiles even without a real frontend build present — local `go run`/`go build` never needs the real one, since local dev serves the frontend via Vite on `:5173` instead). `server.go`'s catch-all is now `spaHandler`: `/api/*` misses still return the `{error}` envelope, everything else serves a real static file from the embedded FS or falls back to `index.html` so a client-side route (e.g. `/favorites`) survives a hard refresh. `cmd/sonneck/main.go` wires `webui.FS()` into `handlers.New(...)`, which gained a fourth parameter (`frontend fs.FS`) for this — the test helper in `handlers_test.go` needed updating too.

- **`Dockerfile`**: 3 stages, no cross-compilation anywhere in the file itself — `node:22-bookworm-slim` builds the frontend, `golang:1.26-bookworm` copies that build's output over `internal/webui/dist`'s placeholder and runs `CGO_ENABLED=0 go build` (no CGO anywhere in this module — `modernc.org/sqlite`/`robfig/cron` are both pure Go — so this produces a fully static binary), `debian:bookworm-slim` is the runtime with `poppler-utils` (PDF thumbnailing) and `wget` (only so `HEALTHCHECK` can hit `/healthz` without a dedicated Go subcommand for it — debian-slim ships neither `wget` nor `curl` by default). `org.opencontainers.image.source` label points at the repo, which is what let GHCR auto-link the package without a manual step. Image is ~172MB.
  - **Runs as a fixed non-root uid/gid 1000 (added 2026-08-23, security assessment SNK-03)** — `/data` is created and `chown`'d to that user at build time, so a fresh Docker named volume inherits correct ownership automatically (Docker initializes an empty named volume from whatever's already at that path in the image). `docker exec` correctly defaults to the same user too (inherits the Dockerfile's `USER` directive), so admin CLI commands work with no extra flags. The one real wrinkle: a host bind-mount (what `docker-compose.yml` actually uses, `./data:/data`) keeps whatever ownership the host directory already has — on most single-user Linux installs the operator's own login is already uid 1000 (Ubuntu/Debian/Fedora's default first-user uid), so this is a non-issue in practice, but `docker-compose.yml` carries a comment on the fix (`sudo chown -R 1000:1000 ./data`) for the case where it isn't.
- **`docker-compose.yml`**: one service, host bind-mount at `/data` (see the uid/gid note above), commented `environment:` block, healthcheck using `/healthz`.
- **`.github/workflows/docker-publish.yml`** — three triggers, one of which (`release`) splits into two publish channels by `github.event.action`:
  - `push` to `main`: validation build only (`push: false`) — this is what makes the README's Build-status badge meaningful day to day, separate from actual releases.
  - `release: types: [released, prereleased]` — both actions run the same multi-arch build (native runners, not QEMU emulation — GitHub's free, GA native ARM64 hosted runners, `ubuntu-24.04-arm` — build `linux/amd64`/`linux/arm64` as separate matrix jobs, no cross-compile flags needed since each job already produces the right architecture). Each arch job pushes **by digest only** (`push-by-digest=true`); a separate `merge` job combines both digests into one multi-arch manifest via `docker buildx imagetools create`, tagged with the release's own tag name — Docker's own documented pattern for multi-arch builds split across separate native runners. Every `${{ github.event.release.tag_name }}` reference here goes through an `env:` var, never interpolated straight into a `run:` script body (security assessment SNK-04 — git ref names allow shell metacharacters, and direct `${{ }}` interpolation in a script body is GitHub's own well-documented script-injection class).
    - **Both actions unconditionally point the floating `:dev` tag at whatever was just published** (added 2026-08-23, direct instruction) — `:dev` tracks the tip of publishing activity, period, not just pre-releases: a real release can legitimately contain fixes made after the last pre-release was cut, so `:dev` needs to move forward on a real release too, or it'd go stale exactly when someone testing against it needs it least. No `releases/latest`-style check needed either way — GitHub has no "marked latest pre-release" concept to compare against, so this step carries no `if:` at all within the `merge` job.
    - **`action == 'released'` only** (a real release, or a prerelease converted to one) additionally: **`:latest` tracks GitHub's actual latest release, not just "most recently published"** — the `merge` job calls `GET /repos/{owner}/{repo}/releases/latest` (via `gh api`) and compares its `tag_name` to the release that triggered the run, only tagging `:latest` if they match, so a release published for an older branch (or with "Set as the latest release" unchecked) can't clobber it. The `attach-assets` job also only runs here, uploading `docker-compose.yml` to the release via `gh release upload <tag> docker-compose.yml --clobber` (a stable, versioned download URL, and a real number for the README's Downloads badge to count — GHCR exposes no public pull-count API, so a release asset is the closest thing to a live counter this setup can offer). Independent of `build`/`merge` (it's a repo file, not the image), needs its own job-level `permissions: contents: write` override since the workflow's top-level permissions only grant `contents: read`. **Doesn't retroactively apply to a release published before this job existed** — the first real release (`0.1`) predates it and would need the asset attached by hand if it's ever worth backfilling. Doesn't run at all for `action == 'prereleased'` — that's part of the polished, stable distribution story, not a dev/testing build.
  - `workflow_dispatch`: no build at all, just re-runs the same `releases/latest` check and re-points `:latest` (`docker buildx imagetools create` again — a cheap manifest copy, not a rebuild) — for "I changed which release is marked latest after the fact" without cutting a whole new release. Doesn't have an equivalent `:dev`-resync path — there's no "marked latest pre-release" override concept for it to correct for, so the scenario that motivates this for `:latest` doesn't really apply to `:dev`.
- **GitHub-website steps this needed** (not app code, but real one-time setup, worth remembering if a future repo/org needs the same thing): Settings → Actions → General → Workflow permissions → "Read and write permissions" (the workflow's own `permissions: packages: write` is capped by this repo-level setting regardless of what the YAML requests); after the first release-triggered publish, the GHCR package defaults to **private** regardless of the source repo's visibility and needs a manual Package settings → visibility → Public (confirmed via GitHub's own docs: package visibility is independent of repo visibility for Container Registry specifically — this is a real, deliberate GHCR feature, not a bug to route around. One caveat worth remembering: switching a package to public **cannot be undone** through the normal UI).
