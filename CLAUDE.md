# CLAUDE.md — House Rules & Conventions

Companion to `sonneck-design.md` (the design doc for **Sonneck**, named after Oscar Sonneck, the American musicologist and first head of the Library of Congress's Music Division — see the root README's "About the name" section for the full story). Re-read this file at the start of every session — its job is to keep cross-cutting decisions consistent across many separate sessions, which a design doc alone won't do.

`CONTRIBUTING.md` mirrors several of the rules below (migrations, the API contract, testing requirements) for human contributors, in its own words. When changing any of those here, check whether `CONTRIBUTING.md` needs the same update — it's a second copy by necessity (different audience), not a generated one, so it doesn't update itself.

## Database migrations
Tool: **goose**. Every schema change is a migration file, checked into the repo, never a hand-edited change to an existing migration. Several fields are already known to be coming later (`composerDeathYear`, `SheetType.definition`, custom fields — see design doc §13), each gets its own new migration when it lands, not a retrofit into v1's schema. (Reconsidered whether a lighter-weight approach than a dedicated migration tool would do for a small project — kept `goose` regardless, since this risk is driven by session count across a vibe-coded build, not team size, and the tool itself is small and low-overhead.)

**Deliberate exception:** `copyrightYear` (int) and `publicDomain` (bool) are pre-built into v1's `Piece` schema now, unused, even though the feature they belong to (the public-domain badge, design doc §13) is deferred — see design doc §3 for the reasoning. This is a one-off exception for these two specifically (cheap, simple columns), not a general license to pre-build ahead of features. `composerDeathYear` — part of the same deferred feature — does *not* get this treatment and arrives as a normal migration if/when that feature is built.

**Deliberate deviation from design doc §3:** `Piece.key` is many-to-many (`Piece.keys`), not the single `key` tag/FK column §3 specifies. Requested directly ("a piece can have multiple keys in it" — a piece that modulates, or a medley, can legitimately need more than one), not surfaced by a compliance review. Migration `00008_piece_keys_many_to_many.sql` adds a `piece_keys` join table (same shape as `piece_instruments`) and drops `pieces.key_id`; the down migration is lossy by necessity (collapses to `MIN(key_id)` per piece) and documented as such inline. Keys remain explicitly *not* book-inheritable, same as before this change — this is about single- vs. multi-valued, not about inheritance, so it doesn't conflict with §3's inheritance reasoning. Not reflected back into `sonneck-design.md`, same convention as the rest of this file.

**Follow-on, 2026-08-17:** the same reasoning extends to a piece modulating back to a key it already used (e.g. C Major → G Major → C Major) — `piece_keys` originally had `PRIMARY KEY (piece_id, key_id)`, which silently made that impossible (a repeat insert would hit the PK). Migration `00012_piece_keys_allow_repeats.sql` recreates the table with `PRIMARY KEY (piece_id, position)` instead (`position` already existed per-row since migration `00011`, so this reuses it rather than adding a surrogate key); the down migration is lossy the same way `00008`'s is (collapses repeats to the earliest `position` per `(piece_id, key_id)`). Frontend side: `TagComboBox` gained an `allowDuplicates` prop (Key(s) picker only — Instruments/Your Tags don't need it) and switched its selected-pill list from keying/removing by `tag.id` to keying/removing by array index, since two pills can now legitimately share an id.

**Migration `00020_people_and_credits.sql`, 2026-08-30 (composer/arranger overhaul, Phase 6 Stage A):** adds a `people` table plus four ordered join tables (`piece_composers`/`piece_arrangers`/`book_composers`/`book_arrangers`, each `(piece_id/book_id, person_id, position)` with `PRIMARY KEY (..., person_id)` — no `piece_keys`-style repeat-value PK trick needed, since a person is never credited twice in the same role on the same work). **Deliberately additive only — does NOT drop `pieces.composer`/`pieces.arranger`/`books.composer`/`books.arranger`.** Those columns stay in the schema, unused by application code from this migration forward, until a **separate future migration** drops them, and only after the one-shot `migrate-people` CLI backfill (`internal/peoplemigrate`, same admin-CLI pattern as `rebuild-search-index` etc. below) has actually been run against real data and spot-checked. This is load-bearing: goose runs every pending migration automatically on startup with no pause for a manual step in between, so a column-drop migration shipping in the same deploy as this one would destroy the backfill's own source data before it ever ran. Full Stage A implementation record in memory `project_people_composer_overhaul.md`.

## API response contract
Every endpoint returns one of two shapes — no per-handler improvisation:
```json
// success
{ "data": { ... } }

// error
{ "error": { "code": "VALIDATION_ERROR", "message": "human-readable description" } }
```
If a decision point isn't covered by this doc, default to this shape rather than inventing a variant.

## Testing
No comprehensive test suite is required for v1, but one area is **not optional** because failures there are silent and permanent:
- **PDF page-extraction logic** (the import wizard's split step) — a wrong page range is a data-correctness bug nobody notices until they open the piece later. Needs unit tests covering at least: single-page piece, multi-page piece, first piece includes page 1, last piece includes the final page, off-by-one boundaries between adjacent pieces.

(Public-domain calculation testing was flagged as similarly load-bearing in an earlier pass — that requirement is deferred along with the feature itself; see design doc §13. Revisit this section when that feature is built.)

Everything else: use judgment, but the PDF-extraction logic above is load-bearing.

## Live browser verification (dev tooling, not app code)
No MCP browser tool is configured in this environment — `ToolSearch` for "playwright"/"chromium"/"mcp" comes back empty, and every project's `mcpServers` in `~/.claude.json` is `{}`. A real Chromium is still available, though: `npx playwright` caches a full install — including the browser binaries themselves, under `~/Library/Caches/ms-playwright/` — to `~/.npm/_npx/<hash>/node_modules/playwright/`. Confirmed working 2026-08-17 (found via `find ~/.npm/_npx -maxdepth 3 -iname playwright`; run `npx playwright --version` once first if that comes up empty, to populate the cache). Drive it directly with a hand-written Node script through Bash, e.g.:
```js
import { chromium } from '/Users/<user>/.npm/_npx/<hash>/node_modules/playwright/index.mjs'
const browser = await chromium.launch()
const page = await browser.newPage({ viewport: { width: 1000, height: 1000 } })
await page.goto('http://localhost:5173/...')
// ...interact, assert, page.screenshot()...
await browser.close()
```
Needs both dev servers already running — backend on `:8080`, Vite on `:5173` (check with `lsof -iTCP -sTCP:LISTEN -P` rather than assuming either is up or down). Use this for anything a type-check or unit test can't actually catch — a real click-through sequence, animation/transition timing, DOM state after an interaction — rather than reporting "type-checks clean" as if that were equivalent to having verified the feature live.

**The dev library at `./data` (`DATA_DIR`) is read-only for Claude — direct instruction, 2026-08-18.** Earlier sessions mutated real piece records during live checks (editing a piece, toggling favorite) and restored them afterward via a follow-up API call; that's no longer good enough — don't write to it at all, through the app's own endpoints, direct SQL, or file operations. Live verification stays read-only (navigate, view, screenshot). If a check genuinely needs to mutate state to prove a feature, use a disposable piece/book created in a separate, throwaway location instead of touching the real dev library, or ask the user how they'd like it verified.

**Disposable-backend recipe for verifying a write flow, proven working end to end 2026-08-18** — don't re-derive this from scratch each time:
1. Start a second Go backend on a different port against a temp dir: `PORT=8099 DATA_DIR=<scratchpad>/throwaway-data go run ./cmd/sonneck` (migrations run automatically against the fresh temp DB).
2. Don't edit the committed `frontend/vite.config.ts` for a one-off check. Write a throwaway config instead (`proxy: { '/api': 'http://localhost:8099' }`, different port) — it must live **inside `frontend/`** (e.g. `frontend/vite.throwaway.config.ts`), not in the scratchpad directory, since Vite/Node resolves the config's own `node_modules` relative to its own location.
3. Run `npx vite --config vite.throwaway.config.ts` from inside `frontend/` — runs alongside the real dev server, not instead of it.
4. Drive Playwright at the throwaway Vite's port. Real writes land in the throwaway DB only.
5. Clean up afterward: kill both throwaway processes, `rm` the throwaway config and `DATA_DIR`, confirm via `lsof`/`git status` that only the real 8080/5173 pair is still listening and nothing leaked into the repo.

**The long-running dev backend doesn't hot-reload.** Adding a new backend route mid-session and testing it against the already-running `go run ./cmd/sonneck` process produces a "no such endpoint" error that looks like a code bug but is actually just a stale process — restart it (recover its env vars via `ps eww -p <pid>` if not already known; restarting doesn't touch `DATA_DIR`).

**Verify fine visual details with pixel data, not by eyeballing a screenshot.** Visual inspection is unreliable for shape-topology questions (is a glyph's counter actually open or closed) and gradient-fidelity questions (does an overlay render monotonically, how far does a color actually shift) — proven wrong repeatedly on this project before switching to programmatic checks: flood-fill connectivity analysis (render to canvas, classify ink/background, flood-fill from all four edges, count unreached background pixels) for open/closed questions; clean scanline pixel sampling (routed around any glyph/foreground content, not straight through it) for gradient monotonicity and color-delta questions. This is *in addition to* normal visual QA (layout, color, spacing are fine to eyeball) — specifically for fine-fidelity questions where the failure mode is a defect too subtle to reliably see by eye.

**Verify against data missing the relevant optional fields, not just happy-path fixtures.** A layout change involving a conditionally-rendered element (e.g. `justify-between` against a sibling that can render `null`, like `TagPills` with no tags) can look correct against test data that happens to have everything filled in, and break silently the moment that field is empty — which is often the common case, not an edge case. Check at least one render with the relevant fields absent before considering a layout change verified; prefer `margin-left: auto`/`ml-auto` over `justify-between` when the pinned element's sibling might not render.

**Inline images/screenshots don't render for the user in this chat client.** Save any screenshot or comparison image the user needs to actually see to `design-review/` (gitignored, already used for this) and tell them it's there — don't rely on an inline image actually being visible. Published Artifacts are unaffected (they render in their own viewer); this only applies to raw image files shown inline in conversation.

## Concurrency
v1 is single-user, single-session (see design doc §8). Do not build multi-writer conflict handling. Do enable SQLite WAL mode at startup regardless — cheap, no design cost, cost of skipping it isn't worth the reason to skip it.

**Naming/architecture note:** `Piece.userNotes`, `Piece.userTags`, `Piece.favorite`, and `Piece.practiceStatus` will all be genuinely account-scoped and different per-user once multi-user support lands (confirmed, not just speculative) — but there's no user model in v1 to scope them to yet (see above). **Resolved:** keep them simple in v1 (as currently structured — plain fields and a shared-catalog many-to-many for tags) and accept a real migration when multi-user lands, rather than pre-building relational structure now — same treatment as `composerDeathYear` above, for the same reason (not cheap/simple enough to justify pre-building unused). One detail worth remembering for that future migration: `userTags` is confirmed to become a **fully private per-user vocabulary** once multi-user lands (no shared tag catalog across users, unlike `Key`/`SheetType`) — a bigger restructuring than just adding a `userId` column, since it changes what a "tag" even is (user-owned, not globally shared), so budget the future migration accordingly rather than assuming it's a small add-a-column change.

## Book-level soft inheritance
Full mechanism in design doc §3/§14/§15/§16 — this section is about the implementation convention, not the feature itself.

**One shared "resolve effective piece values" helper, used everywhere a book-inheritable field is read** — display (Piece Details page, edit menu), validation, citation generation (design doc §6), and search indexing (below) all need the same piece's-own-value-falling-back-to-book's-value resolution. Implement it once, call it from all four places. Do not let validation or citation generation read `Piece` columns directly for `composer`/`publisher`/`publisherId`/`imslpNumber`/`yearWritten`/`workOpusNumber`/`instruments`/`sheetType` — that would silently diverge from what's displayed, which is exactly the kind of inconsistency this pattern exists to avoid.

**Saving a `Book` edit (design doc §16) writes to exactly one record — the `Book` itself.** Nothing about any `Piece` row changes. What changes is what gets *read*: every piece with that `sourceBookId` and no override for the changed field resolves its effective value live against current `Book` data (the shared helper above), so the result naturally reflects the edit without the app writing to any `Piece` row. This still needs: a search-index resync for every affected piece's `pieces_fts` row (not the underlying `Piece` row — see Search below, this is a property of how the search index denormalizes data, not of the data model itself), and ideally a UI-level "this affects N pieces" indication so it doesn't read as a surprising side effect.

**`sourceBookId` itself became editable from the Piece Properties Edit Menu (added 2026-08-19)** — new capability, not in the original design doc (§15 never described re-matching a piece to a different book after the fact; this is additive, not a deviation). `PieceWriteRequest.SourceBookID` (`*int64`) follows the same full-replace rule as every other field: a non-nil value must reference a real, existing `Book` — `applyPieceWriteRequest` (`internal/handlers/piece_write.go`) checks this explicitly via `repo.GetBookByID` and returns a `ValidationErrors` naming the field (`sourceBookId`) rather than letting a bad id surface as an opaque 500 later out of `repo.ResolveEffective`; `nil` clears the association entirely. The wizard's per-piece fill step (confirm-import) sets `SourceBookID` on the model *before* calling `applyPieceWriteRequest`, then re-asserts it *after* — the same guard already in place for `SourcePageStart`/`SourcePageEnd`, since the wizard's own request body never carries a `sourceBookId` key and would otherwise get it nulled back out by the general-case full-replace handling. Frontend: `SourceBookField` (`frontend/src/components/SourceBookField.tsx`) is a debounced search-as-you-type picker against `GET /api/books` (design doc §11's existing convention) — it does not offer a create-new affordance; a source book must already exist.

**Same book-matching capability extended to the single-piece upload path too (added 2026-08-24)** — `UploadPage.tsx`'s "About this piece" screen already had the book-link prompt (`SourceBookField`, see the Frontend polish note elsewhere in this file); it now also shows Start/End page number fields, but only once a book is actually matched (asking "page of what?" with no book selected doesn't make sense) — same one-row-below-the-book-field layout as the Edit Piece Menu's own Start/End page fields. Fully optional, same as `sourceBookId` itself. Real bug caught building this: clearing a matched book hid the fields but left their typed values in the form, so saving could silently persist `sourcePageStart`/`sourcePageEnd` on a piece with `sourceBookId: null` — the book-picker's `onChange` now explicitly clears both page fields whenever the new value is `null`. Worth remembering if any other "field B only makes sense when field A has a value" pattern gets built: clearing A must clear B's *stored* value, not just hide B's input.

**Deliberate deviation from design doc §16's wording:** §16 states Books have no required fields at all ("a book can exist with only bookTitle set and nothing else"). In practice, `ValidateBook` (`internal/api/validate.go`) does require `bookTitle` to be non-empty. Confirmed intentional, not a bug — a Book with no title at all would be a confusing empty state anywhere it's displayed (the Piece Details page's own Book Details section, a future library-of-books view), and the wizard already defaults it from the upload filename in every real path anyway, so the practical cost of requiring it is zero. §16's own text is read as emphasizing the *contrast* with `Piece`'s two required fields (title/composer) rather than a strict "nothing is ever required" validation spec. Not reflected back into `sonneck-design.md` — that file stays as the original planning artifact; this file is where the deviation is tracked, per this file's own stated purpose.

**Two more required-field deviations, same section of `internal/api/validate.go`:**
- **`ValidatePiece`: composer OR arranger, not composer alone** — design doc §5's field-validation table lists `composer` itself as required. A piece crediting only an arranger (no named composer) is a real, legitimate case — a traditional/folk tune, for instance — not missing data, so the check is against the *effective* composer and effective arranger together (either one, from the piece itself or its book, satisfies it).
- **`ValidateBook`: also requires one of composer/arranger/publisher** — beyond the `bookTitle` deviation above, `sonneck-design.md`'s "no required fields beyond title" wording doesn't hold in practice either. A Book with none of the three is missing the one piece of attribution every other bibliographic field on it is meant to attach to; publisher counts on its own because a book whose only known attribution is its publisher (no composer/arranger on record) is still a legitimate, identifiable Book.

## File handling
- All file hashing uses **SHA-256** (`crypto/sha256`, standard library — not BLAKE3, see design doc §2 for why), streamed incrementally during upload via the standard `hash.Hash` interface — never buffer a full 100+MB file into memory before hashing.
- **Duplicate upload behavior:** dedupe on SHA-256 hash match — reuse the existing `Book` record, never create a second copy of the same file. The single-piece upload path (design doc §5, no book involved) gets the same treatment: `POST /api/pieces` checks for an existing `Piece` with a matching hash first and, if found, returns it (`200 OK`) instead of creating a duplicate row; the frontend routes the user straight to that existing piece's page rather than showing the fill-in-details step meant for a genuinely new upload. **Deliberately scoped to this one endpoint only** — the book-import wizard's confirm step still creates sibling pieces via `repo.CreatePiece` directly with no hash check, and that's intentional: two different pieces split from the same book can legitimately end up byte-identical (e.g. duplicate blank pages), and that's not a duplicate upload to collapse. Don't add a DB-level `UNIQUE` constraint on `pieces.file_hash` (unlike `books.file_hash`, which does have one) — it would break that legitimate wizard case.
- **Deletion semantics (confirmed):** hard delete + orphan cleanup. Deleting a `Piece` removes its DB row and its extracted file. If that was the last `Piece` referencing a `Book`, the `Book` record and its original file are deleted too (no indefinite orphan retention). Both piece deletions and orphaned-book cleanups must be logged — see Logging below.
- **Cached page thumbnails must be purged on deletion too, not just the source file** — `data/cache/thumbnails` is derived data (same "safely dropped and rebuilt" status as `pieces_fts`, see Search below), but a deleted `Piece`/`Book`'s own cached entries (`piece-<id>-page-*.png` / `book-<id>-page-*.png`) don't get swept up by that general recovery path on their own. `handleDeletePiece` already did this (`piece.go`'s `stalePattern` glob-delete); **`handleDeleteBook` didn't (found and fixed 2026-08-24)** — it deleted the book's source PDF but silently left every cached page thumbnail behind, reachable indefinitely with no piece/book left to own them. New helper `purgeBookPageThumbnails` (`internal/handlers/helpers.go`), called from `handleDeleteBook` alongside the existing file removal. Relevant specifically because a book cancelled out of the upload wizard before any `Piece` exists yet still needs this — its About/Split/Titles screens all render book-page thumbnails straight from the original file, so real cache entries exist well before any `Piece` row would.
- **Cached book-page thumbnails also get purged right after a successful import completes, except page 1 (added 2026-08-28)** — the book's own file stays permanently (design doc §3: it's the "original unmodified file," kept regardless of import status), but its cached page thumbnails become dead weight the moment `handleConfirmImport` commits: every `Piece` created is a real, physically split-out PDF of its own (`pdf.ExtractPages` into `library/pieces/`, a separate file from the book's `library/books/` one), and `handlePieceThumbnail` always renders from the piece's own file, never the book's — so nothing requests a book's own page thumbnail again after import. New helper `purgeStaleBookThumbnailsAfterImport` (`internal/handlers/helpers.go`), a variant of `purgeBookPageThumbnails` that deliberately spares page 1: `handleGetBookCover` keeps serving `book-<id>-page-1` forever as the cover-image fallback for any book with no custom cover uploaded (Books library grid, Book Details header), so purging it here would just force an immediate, pointless re-render the moment either page is next viewed. Best-effort/non-fatal, same posture as the staged-file-move logging beside it in `handleConfirmImport` — a cache-cleanup failure doesn't fail an otherwise-successful import. Regression-tested (`TestConfirmImport_PurgesStaleBookThumbnailsExceptPageOne`) by actually requesting all of a real book's page thumbnails through the handler stack first, then confirming import, then asserting real filesystem state — not just checking a function's return value.
- **`Book` fields are not denormalized onto `Piece`** (design doc §3) — the Piece Details page resolves book-level display live via `sourceBookId → Book`, edited through the Book Properties Edit Menu (design doc §16), not stored copies on `Piece`. This is deliberate: don't add a "sync book fields to all pieces" step anywhere in application code, since there's nothing to sync — the join makes every piece reflect the current book data automatically. If a future feature ever needs book data to be point-in-time/historical rather than always-current, that's a real design conversation to have, not something to solve by quietly denormalizing it back.
- **`Book` is entirely optional** (design doc §3) — `Piece` is the app's actual primary unit, and a piece with no `Book` at all (via §5's single-piece upload) is a normal, first-class case, not an edge case to special-case around. Don't write code that assumes `sourceBookId` is usually present.
- **File replacement** (design doc §14): hard-replace on the same `Piece` record, not a new piece — same no-soft-delete philosophy as piece/book deletion above. `sourceBookId`/`sourcePageStart`/`sourcePageEnd` are kept as historical provenance after a replace, per an explicit decision — don't clear them, and don't assume they still describe the current file's exact page range.
- **Download/Open PDF filename hint (added 2026-08-26):** `Content-Disposition`'s suggested filename for both `GET /api/pieces/{id}/file` and `GET /api/books/{id}/file` is `"<composer/arranger/publisher> - <title> (<yearWritten>).pdf"` (`downloadFilename`, `internal/handlers/filename.go`), not the bare title it used to be — first non-empty of composer/arranger/publisher wins the name segment, and both the name and year segments are omitted cleanly (including their separator) when unset. For a piece, the name/year come from `repo.ResolveEffective`, not raw `Piece` columns — composer/publisher/yearWritten are book-inheritable, so a piece inheriting them from its book must still get them in its downloaded filename. A Book reads its own columns directly (nothing for it to inherit from).

## Logging
Use the standard library's **`log/slog`** (structured logging, built in since Go 1.21 — no third-party library needed, hence the version floor in the design doc's stack table).

Deletions (piece deletion, cascading orphaned-book cleanup) **and piece file replacement** (design doc §14) are logged at **INFO level**, not DEBUG or WARN/ERROR. This follows standard practice: INFO is the conventional level for production systems, and destructive-but-expected user actions belong there so they're visible in normal production logs rather than hidden behind DEBUG (typically disabled in production) or miscategorized as a warning/error when nothing actually went wrong. Reserve WARN/ERROR for things that are actually problems.

Use structured fields, not string interpolation — e.g.:
```go
logger.Info("piece deleted", "pieceId", piece.ID, "fileHash", piece.FileHash, "title", piece.Title)
logger.Info("orphaned book cleaned up", "bookId", book.ID, "fileHash", book.FileHash, "reason", "last referencing piece deleted")
logger.Info("piece file replaced", "pieceId", piece.ID, "oldFileHash", oldHash, "newFileHash", newHash)
```
This keeps logs greppable/filterable (e.g. `level:info AND pieceId:...`) rather than requiring regex over free text.

## Config
- All global settings are env vars (no settings table in v1) — see design doc §3. Includes `BACKUP_CRON` (backup schedule, standard cron expression, default `0 3 * * *`) as of this revision.
- Validate all env vars at startup and fail fast with a clear message rather than failing later mid-request (e.g. `BACKUP_RETENTION_DAYS` isn't a valid integer, `BACKUP_CRON` isn't parseable). A `COPYRIGHT_REGION` validation rule was specified in an earlier pass, tied to the now-deferred public-domain feature — revisit this when that feature is built (design doc §13).
- **How env vars get set is entirely a Docker Compose concern, not application code.** `environment:` block in `docker-compose.yml` (this project's own choice) vs. a sibling `.env` file are both natively supported by Compose — the app just reads env vars the same way either way. Don't build anything app-side to support one or the other.
- **Backup scheduling** uses `robfig/cron` (pure Go, no CGO, well-known/standard choice — same dependency posture as `modernc.org/sqlite`/BLAKE3-vs-SHA256 elsewhere in this doc) to parse `BACKUP_CRON` and drive the daily `VACUUM INTO` snapshot (design doc §4).
- **`CITATION_FORMAT` is loaded and validated but not actually consulted by citation generation** — `buildCitation` (`internal/handlers/citation.go`) hardcodes the format in Go rather than reading `Config.CitationFormat` and doing token substitution against it. Confirmed intentional, not unfinished work: blank-field omission (a citation must skip a blank field's surrounding punctuation entirely, not render it empty — design doc §6) doesn't fit a plain-substitution model, and a real conditional-template engine is explicitly deferred (design doc §6, §13). This means changing the `CITATION_FORMAT` env var currently has **no effect** — a direct deviation from design doc §6's "`CITATION_FORMAT` env var supports plain token substitution." Left as-is deliberately; not reflected back into `sonneck-design.md`, which stays as the original planning artifact.
- **Citation's `yearWritten` component renders the field's stored value verbatim, with no automatic "ca. " prefix** — a deliberate deviation from design doc §6's literal "ca. {yearWritten}" wording, caught during the Piece Details mockup review (2026-08-16). `yearWritten` is free text specifically so it can carry its own approximate-date qualifier when warranted (design doc §3: `"ca. 1708-1711"`); an unconditional prefix would misrepresent a precisely-known year (`"1848"`) as merely approximate. Any "ca." belongs in the value itself. `buildCitation` (`internal/handlers/citation.go`) updated accordingly; no existing test asserted the old prefix. Not reflected back into `sonneck-design.md`, same convention as the rest of this section.
- **Four more citation deviations, added 2026-08-17 (direct instruction):**
  1. **Arranger now appears in the citation**, fused onto the composer as `"{composer}, arr. {arranger}"` — a direct reversal of design doc §6's explicit exclusion of arranger from the citation format. Only renders when composer is non-blank (an arranger credit with no composer to attach to is dropped, same reasoning as the publisherId-with-no-publisher case above not inventing one either).
  2. **IMSLP number now renders as `"IMSLP #{number}"`** instead of the raw stored value verbatim. A new `stripImslpPrefix` helper (`internal/handlers/citation.go`) strips any leading `"IMSLP"` (with or without a following space/colon/hash/dash, case-insensitive) from the *effective* value before formatting, so old data already carrying it (e.g. a stored value of `"IMSLP04154"`) doesn't render doubled. `EditPieceModal.tsx` also strips the same prefix from the value itself before every save (its own `stripImslpPrefix`, independently implemented — not shared code across the Go/TS boundary), so newly-saved data stops carrying the prefix in storage at all; the backend-side stripping stays regardless, since it's the only thing that also normalizes pre-existing data and data written before this change.
  3. **The book-title citation component now also carries the book's own opus number** (`Book.WorkOpusNumber`, fetched directly — not the piece's *effective* one) as `"{bookTitle}, {bookWorkOpusNumber}"`, **unless** that book opus number (spaces ignored) is already contained in the piece's own effective `workOpusNumber` — which is true whenever the piece doesn't override it (pure inheritance) or overrides it with something that still incorporates the book's number (book `"Op. 68"`, piece `"Op. 68, No. 9"`). Without this, a piece in a book both carrying opus numbers would show the same number twice in one citation — once from the book-title segment, once from the piece's own `"({workOpusNumber})"` parenthetical next to the title. New helper `containsIgnoringSpaces` in the same file.
  4. **A double quote character inside the title itself renders as a single quote**, before the whole title gets wrapped in the citation's own double quotes — a title like `Merry-Go-Round of Life from "Howl's Moving Castle"` would otherwise collide with the citation's wrapping quotes (`""Howl's Moving Castle""`), ambiguous as to which quote closes what. Standard nested-quote convention (outer double, inner single) resolves it — `strings.ReplaceAll(title, "\"", "'")` applied only to the title, right before it's wrapped.
- **`publisherId`, when it's the one actually rendering (`imslpNumber` blank), fuses onto `publisher` as `"{publisher} #{publisherId}"`** — no comma, a `"#"` prefix — rather than its own comma-joined part like every other citation component. A bare publisher ID on its own (`"G. Schirmer, HL50252950"`) read ambiguously, like a second unrelated value, without something marking what it actually is; `imslpNumber` itself is unaffected by this, since a catalog number reads fine on its own.
- **Three more citation deviations:**
  1. **Arranger is book-inheritable** (`repo.EffectivePiece.Arranger`, not a raw `Piece` column) — a piece/book may legitimately have an arranger with no composer at all (`ValidatePiece`/`ValidateBook` require one of the two, not composer specifically — see Database migrations above). When composer is blank but arranger isn't, the composer segment renders as just `"arr. {arranger}"` instead of disappearing entirely.
  2. **ISBN** (a Book-only field, no Piece-level override or inheritance — `models.Book.ISBN`) renders as its own comma-joined part right after the publisher/publisherId segment, hyphenated via `hyphenateISBN`: `"{Publisher} #{PublisherID}, ISBN {hyphenated}"`. Only when `imslpNumber` is blank — same "IMSLP wins the fallback" rule as publisherId above, extended to ISBN for the same reason.
  3. **Publisher (and publisherId, fused onto it) is dropped from the citation entirely whenever `imslpNumber` is present** — previously only publisherId and ISBN deferred to `imslpNumber` this way; publisher itself used to still render alongside `"IMSLP #..."`. Same "IMSLP is the more useful identifier when both are known" reasoning as the ISBN/publisherId fallback, extended to cover publisher too.

  None of these four are reflected back into `sonneck-design.md`, same convention as the rest of this section.

## IMSLP live autofill
Design doc §13 listed this as deferred ("the API/parsing integration researched earlier") — built 2026-08-27, after first confirming the real access mechanism against live IMSLP data (not just reading their docs, which turned out to be incomplete/misleading — see below). Mocked first on both real screens' design references (`EditPieceModalMockup.tsx`, `UploadBookAboutMockup.tsx`) before the real build, same convention as everything else in this doc.

**How it actually works (`internal/imslp`, see that package's own doc comment for the full trail):** the "IMSLP#####" number isn't part of IMSLP's own wikitext/MediaWiki content model at all — it's injected into rendered HTML by a separate extension, and every file in a real work page's wikitext is keyed by a `PMLPxxxxx-filename.pdf` string instead. The human-facing page meant to resolve a bare number (`Special:ImagefromIndex/#####`) sits behind a JS-based redirect (`/friendlyredirect.html#/wiki/...`, target only in the URL fragment) that no server-side HTTP client can follow — confirmed directly via real `curl` requests, not assumed. `Special:ReverseLookup` (already used by this app's own "open on IMSLP" links, `frontend/src/routes/PiecePage.tsx` etc.) resolves the same number with a real, followable 302 instead — confirmed against real numbers (e.g. `101781` → Tosti's "Povera Maria!"). The resolved work page title is then fed to the standard MediaWiki Action API (`api.php?action=parse&prop=wikitext`) — no HTML scraping needed anywhere in the final implementation, despite that being one of the two paths seriously considered before this was found.

**Publisher/Publisher ID are extracted too** — added shortly after a first version shipped without them, on a real correction: the resolved redirect's `#IMSLP<number>` fragment doesn't just identify the work, it identifies the *exact file/edition* the user's own number refers to, so "a work can have many editions with different publishers" isn't actually ambiguity to resolve here — the number already picked one. That per-file publisher data only exists in *rendered* HTML, though (confirmed directly against three real files across two composers): IMSLP's file-listing extension wraps each file in `<div id="IMSLP<number>" ...>`, immediately followed by a `<table class="we_edition_info">` with a "Publisher Info." row — first `<a>` link's text is the publisher name, "Plate <digits>" in that same cell is this app's own "Publisher ID" concept (matches the field's own tooltip: "Publisher serial or engraving plate number"). `internal/imslp` fetches this via a second `api.php?action=parse&prop=text` call (rendered HTML, not wikitext — still not JS-redirect-gated, same as the wikitext call) and walks it with `golang.org/x/net/html`'s tokenizer, bounded to the one matching file's own block so a later edition's info is never mistaken for the requested one's. A file with no real publisher on record (e.g. an unpublished manuscript) has neither a link nor a plate number in that cell — both fields come back blank, not guessed at.

**Endpoint:** `GET /api/imslp/lookup?number=<digits>` → `{data: {composer, workOpusNumber, yearWritten, publisher, publisherId}}`, any field blank if that work/file doesn't have it on record (a normal result, not an error — IMSLP is community-maintained and often incomplete, and the edition-info fetch is best-effort/non-fatal on its own — a failure there just leaves publisher/publisherId blank rather than sinking a lookup that already has composer/opus/year). `404 NOT_FOUND` for a number IMSLP doesn't recognize, `400 VALIDATION_ERROR` for a non-numeric/empty number, `502 INTERNAL_ERROR` (logged at WARN) for a real IMSLP-side failure.

**Frontend:** shared `components/ImslpAutofillButton.tsx` (used identically by `EditPieceModal.tsx`, `BookUploadAboutStep.tsx`, and `EditBookModal.tsx` — not duplicated the way mockup-vs-real or the two mockups' own local copies are, since all three real callers are equally "real" with no reason to diverge). Sits inside the IMSLP field itself, right-aligned/vertically-centered like a password field's show/hide toggle. Two faint-but-distinct icon states, always visible (never hidden): a fetchable `cloud-download` (`#9d9892`) when the effective value — the field's own, or a book/inherited/filename-detected fallback, whichever applies — is number-only once any "IMSLP" label prefix is stripped; a fainter `cloud-off` (`#c9c2b6`) otherwise. Autofill only ever writes to fields **currently blank** — never overwrites something already entered, book-inherited or not. A brief `ring-2 ring-accent-on-dark` highlight (faded via `transition-shadow duration-700`, cleared after ~2.4s) marks exactly which fields a given autofill touched.

**Trigger differs by screen, on purpose:** `EditPieceModal.tsx` and `EditBookModal.tsx` (added 2026-08-27) are both manual-click only — a number already on record there was typed/confirmed at some point, same reasoning for both. `BookUploadAboutStep.tsx` also auto-runs once on mount, since a filename-detected number (`detectImslpNumber`, `internal/handlers/filename.go`) is already considered confirmed by the time that screen exists — but only after a **700ms delay**, deliberately: the user has to actually see the blank "About this book" screen first, then watch the fetch/highlight sequence play out on it, never have fields silently already-different the instant it mounts. `EditBookModal.tsx` fills the same five fields as `EditPieceModal.tsx` (composer, workOpusNumber, yearWritten, publisher, publisherId) — no arranger highlight either, same as the piece version, since IMSLP lookup never returns one. All three screens have this checked via `git status`-verified live tests against the real, production imslp.org before shipping — including the specific "still blank at +300ms, filled a few seconds later" timing check for the auto-trigger case.

**Gotcha re-confirmed adding the third caller (2026-08-27):** `EditBookModal.tsx` didn't previously use react-hook-form's `watch()`/`getValues()` — adding them (needed to read the live IMSLP field value and check other fields before overwriting) pushes the whole component onto the React Compiler's `react-hooks/incompatible-library` bail-out path, same as `EditPieceModal.tsx` already was. One concrete side effect: an existing `eslint-disable-next-line react-hooks/set-state-in-effect` on this file's own `reset()`-on-open effect became a reported "unused eslint-disable directive" the moment `watch` was added — the compiler bail-out stops that rule from analyzing the component at all, so the directive no longer suppresses anything. Removed the disable comment (kept the prose explaining *why* the effect sets state, since that reasoning is still true) rather than leaving a stale directive around. Worth checking again the next time `watch`/`getValues`/`setValue` gets added to a form component that didn't have them before — any existing hook-rule disable comments in that file are worth re-running lint on, not assumed still needed.

**Backend infra notes:** this is the backend's first-ever outbound HTTPS call. `Dockerfile`'s runtime stage now installs `ca-certificates` (previously omitted — nothing needed a system CA bundle before this) — see that file's own comment on the `RUN apt-get install` line. Also the first real dependency added since the design doc's original stack table — `golang.org/x/net` (for its `html` tokenizer, parsing the rendered-HTML edition-info table above) — same "well-known/standard choice, pure Go" bar as `modernc.org/sqlite`/`robfig/cron`; it's the official Go team's own extended-stdlib package for exactly this, not a third-party scraping library.

## Search
SQLite FTS5, not a separate search engine like Bleve — see design doc §2 for the full reasoning (StashApp's approach was the starting inspiration; FTS5 achieves the same goal with less operational overhead for this project's scale).

- Virtual table: `pieces_fts`, one row per `Piece`, denormalized content per design doc §3 — **book-inheritable fields are indexed by their effective value** (the shared resolution helper above), not the raw `Piece` column, or search would miss pieces that only inherit a value from their book.
- **Sync mechanism:** application-level — an explicit `resyncSearchIndex(pieceId)` call after any `Piece` or tag-assignment mutation, run in the same transaction as the mutation itself. Not SQL triggers: trigger logic spread across `Piece` and several tag join tables is harder for a Go-focused contributor to discover and test than one function called from application code, which fits this project's existing maintainer-accommodation reasoning (design doc §2's TypeScript choice, for one). Real trade-off accepted: this relies on remembering to call it at every mutation site, so a shared repository/service-layer helper (not ad hoc calls scattered through handlers) is worth building for exactly that reason. **Editing a `Book` field (design doc §16) must resync every affected `Piece`, not just call this once** — loop over every piece with that `sourceBookId` lacking its own override for the changed field.
- The `pieces_fts` table is derived data, not a source of truth — if it's ever suspected out of sync, it can be safely dropped and rebuilt from `Piece` and the tag tables. Same principle as StashApp's own index philosophy, just without needing a scheduled staleness check to trigger it.
- **Query matching: three tiers — prefix, then trigram substring, then real typo-tolerant fuzzy (all added 2026-08-28).** `sanitizeFTSQuery` (`internal/handlers/search.go`) appends a trailing `*` to each quoted token — FTS5's phrase-prefix syntax — so a still-being-typed word matches ("andan" finds "Andantino"/"Andante sostenuto") instead of requiring the complete word. Confirmed live against the real dev library before/after — the bug this fixes was reproducible on any real title.
  - **Mid-word/substring matching, not just prefix:** a second FTS5 virtual table, `pieces_fts_trigram` (migration `00019_pieces_fts_trigram.sql`, `tokenize='trigram'`), is queried as a **fallback only when the primary prefix query finds nothing** — not merged with it — so a query like "crack" finds "Nutcracker Suite" without changing ranking/behavior for the common (prefix-matching-already-works) case, and without the noise a short query would produce if trigram ran on every request. `sanitizeTrigramFTSQuery` reuses the same safe-quoting as `sanitizeFTSQuery` (factored into `quoteFTSToken`) but with no trailing `*` — trigram already matches anywhere in a word, so the prefix operator adds nothing. `handleSearchPieces`'s `runQuery` closure runs both attempts through the exact same filter/sort/pagination logic (built once, shared), so the fallback still respects every other active filter — confirmed by a dedicated regression test. A trigram query token under 3 characters (its own tokenizer minimum) just matches nothing rather than erroring — confirmed directly against this project's actual pinned driver, not assumed from SQLite's docs.
  - **Substring alone is not fuzzy/typo-tolerant matching** — locked in by `TestSearchPieces_QueryFallsBackToTrigramForMidWordMatch`'s own negative case (an unrelated query still finds nothing there). A real misspelled/transposed letter is the third tier, immediately below.
  - **Real typo tolerance: `fuzzydist()`, a genuine SQLite scalar function, not a fetch-then-rank-in-Go layer (`internal/fuzzy`, `internal/db/db.go`'s `init()`).** `modernc.org/sqlite` supports `RegisterDeterministicScalarFunction` — registering a pure-Go function callable directly from SQL, no CGO, no separate driver. `internal/fuzzy.MinWordDistance(text, query)` computes Damerau-Levenshtein edit distance (the "Optimal String Alignment" restricted variant — handles adjacent transpositions like "sosetnuto" as one edit, not two) between the query and either the whole field or any individual word within it — one function that catches both "typo somewhere in an otherwise-complete phrase" ("nutkracker suite" → "Nutcracker Suite") and "a single, correctly-spelled-if-not-for-the-typo word out of context" ("sostenato" → "Andante Sostenuto", where whole-string comparison alone would never score well against the much longer title). `internal/fuzzy.MaxDistance(query)` is the threshold — roughly one edit per four characters, **rounded up (ceiling division), not down** — floored at 1, capped at 3. Widened from floor to ceiling division same-day (direct report: "boelu" should match "Boëly" — 2 real edits at 5 characters, and `floor(5/4)=1` missed it) — this only raises the threshold for a query length that isn't an exact multiple of 4, so it's a narrow correction, not a general loosening; confirmed no new false positives against the existing fixture set before shipping it. This is a **third fallback tier**, engaged only when *both* prefix and trigram find nothing — same "never merged, never changes common-case behavior" reasoning as the trigram tier itself, one step further out; still sorts by the user's chosen sort field, not by fuzzy distance, for the same consistency reason the trigram tier doesn't rank by bm25. **Because `WHERE`/`ORDER BY`/`LIMIT`/`OFFSET` all work normally against a registered scalar function** (confirmed directly, not assumed), this tier needed no pagination-architecture change at all — it's one more `WHERE` predicate + closure (`runFuzzyQuery`) alongside the existing `runQuery`, reusing the exact same filter/sort/pagination logic. Measured performance (full-scan, no index can help a scalar-function predicate): 36ms at 20,000 rows — a non-issue at this app's real per-user library scale. `spellfix1` (SQLite's own standard tool for this) remains unavailable on this driver (`no such module: spellfix1`, confirmed) — moot now, since the scalar-function approach gets the same real edit-distance capability without it. Queries `pieces_fts`'s own already-denormalized `title`/`composer`/`arranger` columns directly (plain `WHERE`, no `MATCH`) rather than adding a third virtual table — confirmed a plain non-`MATCH` predicate against an FTS5 table's columns works correctly, including `JOIN`ed with the real `pieces` table's own filter columns. Full research trail (library survey, algorithm alternatives, the reasoning that ruled out CGO) is in memory (`project_fuzzy_search_research.md`) — that memory now doubles as the design rationale for what's actually shipped, not just unbuilt research.
  - `repo.ResyncSearchIndex`/`RebuildSearchIndex` write both tables from the same row values (`internal/repo/search.go`) — `pieces_fts_trigram` is exactly as derived/rebuildable as `pieces_fts` itself. **`internal/export/export.go`'s CSV export exclusion list is now dynamic, not hardcoded per table** — adding this second FTS5 table was a real, caught gap: the export's exclusion list used to hardcode `pieces_fts` + its 5 shadow tables by literal name, so this migration would have silently exported six new "tables" (`pieces_fts_trigram` + its own shadow tables) as if they were real library data until `listTables` was changed to discover any `CREATE VIRTUAL TABLE ... USING fts5` table from `sqlite_master` itself and exclude it (plus its shadow tables) automatically. Regression-tested (`TestRunCSV_ExcludesInternalAndDerivedTables`).
  - **A real dev/prod database that already has pieces indexed before this migration lands needs a one-time `rebuild-search-index` CLI run** (CLAUDE.md > Search's general admin-CLI pattern) to backfill `pieces_fts_trigram` for existing pieces — the migration only creates the empty table; `ResyncSearchIndex` only fires on new writes going forward. Until backfilled, the trigram fallback simply finds nothing for not-yet-touched pieces (confirmed: returns `200 {"data":[]}`, doesn't error) rather than breaking anything.
  - Books search (`handleListBooks`) already did substring-anywhere matching via plain `LIKE '%term%'` (no FTS5 there at all) before any of this — this whole effort specifically closes a Pieces-only gap, not a general one.
- **`pieces_fts`/`pieces_fts_trigram` gained a `book_title` column (migration `00021_pieces_fts_book_title.sql`, 2026-09-02, direct request: "Book title should be a searchable field").** A piece imported from a book previously couldn't be found by searching that book's own title (e.g. "Off the Record") — only the piece's own fields. `repo.ResyncSearchIndex` (`internal/repo/search.go`) now also looks up `p.SourceBookID`'s `Book.BookTitle` (same lookup `api/dto.go`'s own `SourceBookTitle` response field already does) and writes it into the new column; a book-less piece just gets an empty string, same "blank if not applicable" treatment every other optional field here already gets. **No query-building changes needed anywhere** — `handleSearchPieces`'s prefix/trigram `MATCH ?` and `facets.go`'s `pieceTextMatchClause` are both already unqualified (no `column:` filter), so a new non-`UNINDEXED` FTS5 column is automatically included in every existing free-text search path for free. Deliberately **not** added to the third (fuzzy) tier's own explicit `fuzzydist(...)` predicate — that tier already only checks `title`/`composer`/`arranger`, not every column (`publisher`/`description`/etc. aren't in it either), so leaving `book_title` out is consistent with the existing scope, not an oversight.
  - **Schema change required drop-and-recreate, not `ALTER TABLE ... ADD COLUMN`** — confirmed directly against this project's actual pinned driver (a real throwaway Go program against `modernc.org/sqlite` v1.56.0, not assumed from general SQLite docs, per this project's own "verify external API before committing" standing rule): `ALTER TABLE` on an FTS5 virtual table fails outright here ("virtual tables may not be altered"). Later SQLite versions do support `ALTER TABLE ADD/DROP COLUMN` on FTS5 tables, but this driver's bundled version doesn't — this is exactly why migration `00019` introduced a whole second (trigram) table rather than altering the first, not an arbitrary stylistic choice as it might have read before this was checked. Both tables are already documented as safely droppable/rebuildable derived data, so drop-and-recreate (same full column list plus `book_title`) is the sanctioned way to change their schema; the down migration recreates them at their pre-migration column set.
  - **Same one-time backfill requirement as migration `00019`'s own trigram-table introduction**: a real dev/prod database with pieces already indexed needs a `rebuild-search-index` CLI run to populate `book_title` for existing rows — confirmed directly via the disposable-backend recipe (blanked `book_title` on a real indexed piece to simulate stale pre-migration data, confirmed the search correctly found nothing for the book's title, ran `rebuild-search-index`, confirmed it found the piece again afterward).
  - New `TestSearchPieces_QueryMatchesSourceBookTitle` covers both directions: a piece imported from a book is found by that book's own title, and a book-less piece's own fields never accidentally match a query for an unrelated book's title.
  - **Severity correction, 2026-09-02 — the "one-time backfill requirement" above badly understated the real impact.** Direct report ("There is a book with 'Christmas' in its title, but when I search the Piece Library for 'christmas', none of its pieces display, even those with 'christmas' in their piece titles") led to reproducing the actual failure live, not just re-reading the migration: migration `00021`'s `DROP TABLE pieces_fts` / `DROP TABLE pieces_fts_trigram` don't just leave the new `book_title` column blank on old rows — they destroy **every existing row in both tables outright**, since they're an already-populated table being dropped, not a fresh one. Nothing in this app's own write paths repopulates a piece's row except a real mutation to that specific piece (`ResyncSearchIndex`) or the manual `rebuild-search-index` CLI — a migration boundary itself triggers neither. So a real library that upgrades past this migration without immediately running that CLI command doesn't just lose book-title matching: **search returns zero results for literally any query**, even one matching a piece's own title, for the entire pre-existing library, silently, with no error surfaced anywhere. Reproduced twice: once synthetically (disposable-backend recipe, `DELETE FROM pieces_fts` to simulate the drop), and once live against the real dev backend after the user restarted it to actually apply migration `00021` — `GET /api/pieces?query=Andante` genuinely returned zero results against a library that still had "Andante con moto"/"Andante sostenuto" pieces fully present.
  - **Fixed the same way `migrate-people`'s own manual-step gap was fixed (2026-09-01, see that entry under Search below) — made automatic, not just documented as a manual step.** New `repo.SearchIndexNeedsRebuild(ctx, q) (bool, error)` (`internal/repo/search.go`): a cheap `(SELECT COUNT(*) FROM pieces) != (SELECT COUNT(*) FROM pieces_fts)` check, same "one query, run on every boot" cost posture as `peoplemigrate.Pending`. `cmd/sonneck/main.go`'s normal server-start path calls it right after the people-migration check and runs `repo.RebuildSearchIndex` automatically when it reports true — best-effort/non-fatal (logged, doesn't block startup), same reasoning as the people migration: a failed rebuild leaves search broken but the app otherwise fully usable, not worth failing startup over. The manual `rebuild-search-index` CLI subcommand stays as a fallback. New `TestSearchIndexNeedsRebuild_DetectsAndFixesWipedIndex` (`internal/repo/search_test.go`) locks in the exact reported scenario: a piece titled "O Christmas Tree" synced normally (guard reports false), `pieces_fts` wiped to simulate the migration (guard reports true, search finds nothing), `RebuildSearchIndex` runs (guard reports false again, search finds it). Live-verified end to end via the disposable-backend recipe, not just `go test`: restarted a throwaway backend against the same wiped database and confirmed the log line `"automatic search index rebuild completed"` fires and search immediately works again — and, separately, that a *healthy* library's restart logs nothing extra (the count-mismatch check is a true no-op there, not a per-boot tax). The real dev backend (`./data`) was left untouched by me per the standing read-only rule — restarting it again (the user's own action) picks up this fix and self-heals without any direct write on my part.
- **"&" and "and" are interchangeable in search, both directions (added 2026-09-02, direct request: "'&' should match 'and' and vice versa").** A real, common case in this app's own domain — "Boosey & Hawkes" (publisher), "Rodgers & Hammerstein" (a duo credited as one `Person`) — where FTS5's tokenizer already drops a bare `&` as a plain word separator with no token of its own, so without normalization it silently fails to line up with the real word "and" on the other side (a query for "and" never finds data stored with "&", and a query typed with "&" produces a phrase-query token FTS5 can't usefully match against anything). `repo.NormalizeAmpersand(s string) string` (`internal/repo/search.go`) canonicalizes `"&"` → `" and "` (space-padded, not a bare replace — so a no-space case like "Dungeons&Dragons" still tokenizes into two words instead of merging into one run-together token; the padding's own extra whitespace is harmless since both the FTS5 tokenizer and query-side `strings.Fields` treat any whitespace run as one separator). Applied on **both** sides of every FTS5-based comparison: at index time (`repo.ResyncSearchIndex`, applied to every free-text field going into `pieces_fts`/`pieces_fts_trigram` — title, composer/arranger names, publisher, description, user_notes, instruments, user_tags, book_title; identifier/fixed-vocabulary fields — publisher_id, imslp_number, year_written, work_opus_number, key_name, sheet_type_name — are deliberately left alone, since an ampersand there was never standing in for "and") and at query time (`sanitizeFTSQuery`/`sanitizeTrigramFTSQuery`, `internal/handlers/search.go` — the single shared point both `handleSearchPieces`'s own two tiers and `facets.go`'s `pieceTextMatchClause` all route through, so one change covers every caller; the third, fuzzy tier doesn't route through either sanitize function at all — `fuzzydist()` is a plain `WHERE` predicate, not a `MATCH` query — so `runFuzzyQuery` normalizes its own copy of `query` independently before using it for both the `MaxDistance` threshold and the actual comparison).
  - **Books/People search needed a second, distinct helper — `repo.NormalizeAmpersandForLike(s string) string`** (bare `"&"` → `"and"`, no padding) — because neither uses FTS5 at all (CLAUDE.md's own note above: Books search has always been plain `LIKE '%term%'`; People search, `internal/handlers/people.go`, is the same). A literal `LIKE` substring comparison needs identical spacing on both sides, and a real name almost always already has a single space on each side of a standalone `&` ("Boosey & Hawkes") — a bare replace preserves that spacing exactly, landing on the same single-spaced "and" a normally-typed query already has; the FTS version's space-padding would instead double an already-single space and silently break the match. Applied via a SQL-level `REPLACE(col, '&', 'and')` wrapped around each compared column (`book_title`/`publisher`/the joined `people.name` in `handleListBooks` and `bookTextMatchClause`; `name` in `handleListPeople`) plus the identical `NormalizeAmpersandForLike` call on the query text itself.
  - **Existing indexed data needs the same one-time `rebuild-search-index` backfill as every prior content-shape change to `pieces_fts`** (the trigram-table and `book_title`-column entries above) — `ResyncSearchIndex` only applies the new normalization on a piece's *next* write, so a library that upgrades without rebuilding just won't get the improved "&"/"and" matching for not-yet-touched pieces (not a breakage — the existing content still matches exactly as it did before, same as the trigram backfill's own "simply finds nothing extra until backfilled" posture). Books/People search needed no backfill at all — `NormalizeAmpersandForLike`'s `REPLACE()` runs directly against live `books`/`people` columns at query time, not a derived index, so it applies to every row immediately.
  - Regression-tested: `TestSearchPieces_AmpersandMatchesAnd` (both directions — `&`-stored data found by an "and" query, "and"-stored data found by a `&` query, via a real publisher field and a real composer name), `TestListBooks_AmpersandMatchesAnd`, `TestListPeople_AmpersandMatchesAnd`.
- **Manual full rebuild**: exposed as a CLI subcommand, not an HTTP endpoint — see the general pattern below.

**General pattern for admin/maintenance actions before real auth exists:** default to a CLI subcommand on the same binary, gated by shell/`docker exec` access to the container, rather than an HTTP endpoint with no auth to protect it. The search-index rebuild is the first concrete instance of this; treat it as the template for future maintenance actions (e.g. anything that comes up before OIDC/multi-user, §13, actually lands). Reuse the app's existing config/DB-connection bootstrap code in these subcommands rather than duplicating it — the CLI command and the server should read the same config the same way. Commands that write to the SQLite file while the server may still be running rely on WAL mode (already an established v1 convention, see Concurrency above) for safety — this is the one deliberate exception to "single writer" in an otherwise single-user/single-session v1.

- **Second instance of this pattern (2026-08-16): `regenerate-thumbnails`.** Wipes `data/cache/thumbnails` (derived data, same "safely dropped and rebuilt" reasoning as `pieces_fts`) and re-renders every page of every piece from scratch — the recovery path if a cached thumbnail is ever suspected corrupted (a real, confirmed bug: a torn/truncated PNG from a page-render race, now fixed — see `internal/handlers/helpers.go`'s `cachedThumbnail`/`regenerateThumbnail`), without needing to know which cache entries are actually bad. Also cleans up orphaned entries for since-deleted pieces, since the wipe isn't scoped to currently-known pieces. Safe against a live server for the same WAL-mode reason as `rebuild-search-index` — writes land via an atomic rename, so a concurrent live thumbnail request never observes a partial file.

- **Third instance of this pattern (2026-08-20): `export-csv`.** A full data export, one CSV file per real table, written to a new timestamped subdirectory of `data/export/`. Read-only against the database (no admin action so far has been read-only, but the pattern still applies — same auth-gap reasoning, same "reuse the app's own bootstrap" rule). Table/column lists come from `sqlite_master`/`rows.Columns` rather than a hardcoded list, so a future migration's new table is picked up automatically; `goose_db_version`, `sqlite_sequence`, and `pieces_fts` + its FTS5 shadow tables are explicitly excluded as internal/derived, not real library data (same "safely dropped and rebuilt" tables called out for `pieces_fts` above — exporting them would just be noise in a dump meant to hand someone their actual library back). See `internal/export/export.go`.

- **Fourth instance of this pattern (2026-08-28): `cleanup-thumbnails`.** The routine-maintenance counterpart to `regenerate-thumbnails`' nuclear option — that one wipes and rebuilds *every* piece thumbnail unconditionally; this one only touches an entry that's actually wrong, leaving everything else alone. Two things it fixes that no other code path ever will, because `purgeBookPageThumbnails` (book deletion) and `purgeStaleBookThumbnailsAfterImport` (added the same day, see File handling below) are both scoped to *one* book at the moment something happens to it: (1) book thumbnails orphaned by a book deleted before `purgeBookPageThumbnails` existed (2026-08-24), permanently stranded until something like this runs; (2) stale book-page thumbnails for every book imported before `purgeStaleBookThumbnailsAfterImport` existed — that fix only fires at the moment of a *new* import, never retroactively for a library's existing history. Works by parsing each cache filename back into an owning book/piece id + page number (`bookThumbnailCacheKey`/`pieceThumbnailCacheKey` regexes, `internal/handlers/helpers.go`) rather than starting from the database and asking whether each row's thumbnail exists — the point is to find cache entries the database side has no record of needing at all, which a query starting from `Piece`/`Book` rows could never surface. A filename matching neither pattern (e.g. a stray temp file from an interrupted render) is left untouched rather than guessed at. Per-entry logic: a book/piece thumbnail whose owning row no longer exists is removed outright; a book with zero pieces yet (still plausibly mid-wizard) has every page left alone regardless of page number; an imported book's own pages are dead weight except page 1, and even page 1 is removed once the book has a **custom cover** (a real refinement beyond `purgeStaleBookThumbnailsAfterImport`'s own simpler "always spare page 1" rule, affordable here since this isn't running on every request); a piece thumbnail whose page exceeds the piece's current `PageCount` (e.g. after a file replacement, design doc §14) is removed; anything still legitimately owned gets opened and PNG-decoded (`isCorruptPNG`) and regenerated in place — not removed — if that fails, the same torn/truncated-PNG failure mode `regenerate-thumbnails` exists to recover from. Reports `{removed, regenerated}` counts. See `internal/handlers/cleanup_test.go` for the real-HTTP-driven regression coverage (each "must be preserved" case populates its cache entry via a real thumbnail request, not a fabricated file, the same way `TestDeleteBook_PurgesCachedPageThumbnails` already established).

- **Fifth instance of this pattern (2026-08-30): `migrate-people`.** The composer/arranger overhaul's (Phase 6 Stage A) one-shot backfill — splits every Piece/Book's still-present legacy `composer`/`arranger` TEXT string (migration `00020` deliberately didn't drop these columns) into real `Person` rows and populates the new ordered join tables, via `internal/peoplemigrate.Run`. Idempotent (skips any piece/book that already has *any* composer or arranger credit), so safe to re-run. `internal/peoplemigrate.SplitNames` implements the locked migration-plan wording ("split... by any combination of commas/'and'/ampersands, handling a trailing Oxford comma") — order of the three regex passes matters (Oxford-comma pattern must run before the bare "and" pattern) — see that package's own test file for the full case coverage.
  - **This one deliberately breaks from the pattern's own "gated by shell/docker exec access" framing, added 2026-09-01 (direct instruction: "users shouldn't have to run a migration CLI command").** Unlike every other admin subcommand here, requiring a manual step for this one meant a real end user upgrading past migration `00020` would see blank composer/arranger everywhere until they thought to `docker exec` in and run it — not an acceptable UX for something that isn't actually a destructive or judgment-requiring operation. `cmd/sonneck/main.go`'s normal server-start path (not the CLI-subcommand branch) now calls `peoplemigrate.Run` unconditionally on every boot, logged but **best-effort/non-fatal** (`logger.Error`, no `os.Exit`) — unlike a real goose migration failure, a failed backfill here leaves the old TEXT columns fully intact and the app still fully usable, so it doesn't get to block startup. The `migrate-people` CLI subcommand itself stays, as a manual fallback (retry without restarting, or run against a different `DATA_DIR`).
  - **New `peoplemigrate.Pending(ctx, db) (bool, error)` guards this from becoming a permanent per-boot tax.** Without it, `Run` would pay for a full `pieces`/`books` scan plus a `GetPieceByID`/`GetBookByID` round trip per row on *every* startup forever, even for a library that finished migrating years ago — acceptable once as an opt-in CLI command, not as something that now fires unconditionally on every restart. `Pending` is one query (`EXISTS` over pieces/books, each checking for a non-blank legacy composer/arranger string with no matching join-table row yet) mirroring `Run`'s own per-row skip condition exactly — a row `Pending` calls pending is exactly a row `Run` would actually touch. `Run` calls it first and returns a zero `Result` immediately when nothing's pending, rather than scanning just to report accurate skip counts nobody depends on. Verified live via the disposable-backend recipe across three boots against one throwaway DB: empty library → no log line; a row with a freshly-seeded legacy string inserted directly via SQL → migrates and logs; same DB rebooted again → no log line, confirming the short-circuit actually engages once nothing's left.

**Library sort/filter/facets (built 2026-08-28):** `GET /api/pieces` and `GET /api/books` gained `sort`/`dir` query params (whitelisted field→SQL-fragment map via `sortColumnFunc`, `internal/handlers/sort.go` — never string-concatenated). A sort field whose value can be blank (piece `composer`, book `yearWritten`) prepends its own **direction-invariant** `(expr IS NULL) ASC` (or `GLOB`-based non-numeric check for `yearWritten`) clause ahead of the value's own direction-following clause — SQLite's default is NULL-sorts-*first*-on-ASC, so a naive single "expr + direction" fragment puts blank values at the front of an ascending list instead of trailing them regardless of direction; this was a real bug caught by the test suite, not spotted by inspection. Composer sort mirrors `repo.ResolveEffective`'s book-inheritance fallback in SQL (conditional `LEFT JOIN books`, only when `sort=composer`, + `COALESCE(NULLIF(TRIM(...),''),...)`) rather than fetch-then-sort-in-Go, which would break LIMIT/OFFSET pagination. Sort/dir are parsed only outside `handleSearchPieces`'s `sourceBookId`-scoped branch — that branch (Book Details' piece list) keeps its unconditional hardcoded page-order sort. **Superseded 2026-08-30 (composer/arranger overhaul, Phase 6 Stage A):** `composer` is no longer a plain column at all — both `pieceSortColumns["composer"]` and `bookSortColumns["composer"]` now use scalar subqueries returning each piece/book's own first-listed (`position 0`) composer name from the new `piece_composers`/`book_composers` join tables, with the piece-side version's `COALESCE` mirroring the same all-or-nothing book fallback as before, just against subqueries instead of raw `TRIM`/`NULLIF` column comparisons. Found and fixed as a real regression via the pre-existing test suite, not proactively — worth remembering that **any** future code still reading `composer`/`arranger` as a raw SQL column anywhere in this codebase is now silently wrong (always NULL for data written after migration `00020`).

**Title sort ignores a leading "A"/"An"/"The" (added 2026-08-28)** — the usual library-catalog convention, applied to both piece and book title sort via a shared `titleSortColumn` (`internal/handlers/sort.go`), computed in SQL (a `CASE`+`SUBSTR` expression, no `LOWER()` needed since SQLite's `LIKE` is already case-insensitive for ASCII) rather than a stored sort-name column — deliberately, to avoid a new field that would need backfilling and keeping in sync at every write path, the same computed-vs-stored tradeoff already made for composer's book-inheritance fallback above. Each `LIKE` pattern requires a literal trailing space after the article, so a title merely starting with those letters ("Andantino", "Aria", "Theme and Variations") sorts on its own literal text rather than getting a few characters chopped off — confirmed both by unit test and against the real dev library ("The Opener" sorts under O, "A Simple Matter of Conviction" under S).

**Multi-select filters:** `keyId`/`sheetTypeId`/`instrumentId`/`userTagId` (pieces) and `sheetTypeId`/`instrumentId` (books) all take **comma-separated IDs**, OR-matched (`parseIDListFilter` + `sqlPlaceholders`/`idsToArgs` helpers, `internal/handlers/search.go`) — same convention the pre-existing `practiceStatus` filter already used. The two inheritance-aware piece filters (`sheetTypeId`/`instrumentId`) each bind their id list **twice** (once per side of the inheritance `OR`) — a real place a swapped/misaligned arg bind could silently return wrong rows if touched again; regression-tested (`TestSearchPieces_SheetTypeAndInstrumentFiltersMatchInheritedValues`'s multi-value block).

**Facet counts:** `GET /api/pieces/facets` / `GET /api/books/facets` (`internal/handlers/facets.go`) — one combined response per resource, not per-facet endpoints or an extension of the pre-existing `/api/keys` etc. lookup endpoints (which stay untouched, used only by edit-form comboboxes). **Inheritance-aware** for SheetType/Instrument piece counts (mirrors the filter's own WHERE clause) so a displayed count never undersells what checking the box actually returns. A facet value with zero matches is omitted entirely, not shown at count 0. New `bookless=true` piece filter (`p.source_book_id IS NULL`) is deliberately asymmetric with `favorite`: `bookless=false` is a no-op, not a hard exclude, since the drawer's single checkbox never sends `false`.

**Live/faceted counts, added 2026-08-31 (superseding the original "fully static" design above)** — each facet value's count now reflects what checking it would add on top of every OTHER currently active filter and the current search box text, the standard multi-select faceted-search rule: a value never self-narrows against its own current selection (checking "Piano" doesn't shrink Piano's own displayed count, but does narrow every other facet, including every *other* instrument). `internal/handlers/search.go` gained `buildPieceFilterClauses` (a `[]namedClause` — `{name, where, args}` — instead of the flat `where []string`/`args []any` `handleSearchPieces` built directly before this) so `handlePieceFacets` can compose "every active filter except this one dimension's own" per facet via `combineClauses(clauses, exclude)`; `handleSearchPieces` itself is unchanged in behavior (same SQL text, same tests green with zero edits) — it just flattens the same clauses instead of building them inline. `buildBookFilterClauses` is a *separate*, `b.`-qualified builder used only by `handleBookFacets` — deliberately not shared with `handleListBooks`'s own inline (unaliased) filter code, since rewiring a working, tested handler's query structure through a shared alias-qualified builder for no behavioral gain wasn't worth the regression risk.
- **Deliberate scope cut: the free-text portion of a facet count is prefix-tier only** (`pieceTextMatchClause`/`bookTextMatchClause` in `facets.go`) — never the full prefix→trigram→fuzzy fallback chain `handleSearchPieces` uses for the actual result list. A facets request recomputes up to 8 dimension queries; replicating the "did tier 1 come back empty, fall back" decision (and the trigram/fuzzy tiers themselves — the one genuinely expensive, unindexed part of piece search) 8 times over for a set of cosmetic sidebar counts wasn't worth it. The one place this can visibly diverge from the result list: a query that only the list's own trigram/fuzzy fallback resolves (a typo, or a mid-word fragment) — facet counts stay at their whole-library values in that specific case, while the list itself still finds the right pieces via its own fallback tiers. Books never had a fuzzy/trigram tier to begin with (plain `LIKE`, CLAUDE.md's own Search section above), so `bookTextMatchClause` has no equivalent scope cut to make.
- Frontend: `getPieceFacets`/`getBookFacets` (`api/pieces.ts`/`api/books.ts`) now take an optional params object mirroring `SearchPiecesParams`/`ListBooksParams` minus sort/pagination/personId/sourceBookId (`PieceFacetsParams`/`BookFacetsParams`). `PieceBrowseView.tsx`/`BooksPage.tsx`'s facets `useQuery` now keys/fetches off the exact same debounced query+filter state (`debouncedQuery`/`debouncedDrawerFilters`, plus a page's own fixed `filters` for `PieceBrowseView`) the list query itself already builds — no new debounce, this reuses what search-as-you-type already had. Still fetched unconditionally on mount (not gated on drawer-open), same as before, so the Filters button's own active-count badge and the drawer's first paint stay correct with no loading flash.
- Live-verified via the disposable-backend recipe end to end (not just `go test`): seeded 4 real pieces (2 keys × 2 instruments) and 2 real books via curl against a throwaway backend, then drove the real Filter Drawer through a throwaway Vite instance — checking "Piano" correctly narrowed the Key facet (both keys still present, 1 each) while leaving the Instrument facet's own two options at their unfiltered counts (a facet never narrows against its own selection); adding a search-box query on top correctly dropped every option down to just what matched both. Confirmed identically for Books via its own drawer.
- Mockups kept in sync per this app's standing convention: `PieceLibrarySample.tsx`'s `matchesFiltersExcept`/`BooksLibrarySample.tsx`'s `booksMatchExcept` are each fixture-local client-side ports of the real backend's `combineClauses` "exclude" rule — every facet count function in both files now takes the current `filters`/`query` and recomputes against the fixture on every render, replacing the original always-static module-level constants (`FAVORITE_COUNT` etc.).

**"Show only" gained a third toggle: `hasImslpNumber` (added 2026-08-28).** Same asymmetric-boolean shape as `bookless`, but — unlike `bookless`/`favorite`, both plain columns — it tests the piece's *effective* IMSLP number (own value if non-blank, else the book's, `NULLIF(TRIM(...), '') IS NOT NULL` — this file's own established non-blank idiom, matching `resolveStringField`'s `isBlank`), the same inheritance-aware "own OR book's" shape `sheetTypeId`/`instrumentId` already use. The facet count needed the same inheritance-aware treatment for the same reason SheetType/Instrument counts do (a direct-only count would undersell a piece that only inherits its number) — `Favorite`/`Bookless` don't need this since neither is book-inheritable.

## Frontend
- **Shell scope:** build the sidebar nav/route shell to accommodate *all* planned features from early on, not just whatever's functionally wired up in the current commit — scaffold-and-hide a not-yet-built feature (route/component exists, reachable in code, visually present even if stubbed or disabled) rather than omitting it as if undecided. The failure mode to watch for is the opposite one: building only the current commit's narrow slice and losing track of the rest of the design doc.
- **Mockup/real parity is a standing rule, not a per-request judgment call (reinforced 2026-08-31 as a general default, not just for the two instances that prompted it).** Every real page with a `/mockup/*` counterpart (grep `frontend/src/routes` for a `*Sample.tsx`/`*Mockup.tsx` file, or check `App.tsx`'s `mockup/*` routes) works both directions: a genuinely new visual/UX design goes to the mockup first for approval before touching the real component (see the mockup-first note under Docker/build's neighbor sections and memory `feedback_mockup_first_standing_rule.md`); once *any* change lands in the real page — new interaction, added affordance, copy/behavior fix, not just a visual redesign — the same change gets ported into the mockup counterpart in the same pass, by default, without being asked each time. "The mockup's fixture has no real backend to call" is not by itself a reason to skip porting a change — check whether the mockup already has (or can cheaply get) its own local way to fake the same interaction (a toggleable `useState`, a stub-message banner like `PersonDetailsSample.tsx`'s `lastAction`, a plain `ContextMenu` instead of one wired to real mutations) before concluding it can't be mirrored; several real regressions/pieces of drift have been found specifically because a mockup was believed "not applicable" to a change that later turned out easy to port. Where the two genuinely can't share code (mockups deliberately don't import real components — see the mockup-vs-real duplication convention below), port the *shape* of the change by hand into the mockup's own local copy, same as every existing instance of this pattern throughout this file.
- **Language:** TypeScript. Types should mirror the backend's `{data}`/`{error}` API contract (see above) — this is the main defense against frontend/backend drift across sessions.
- **Icons:** Tabler Icons via `@tabler/icons-react` — the scoped package, not the older unscoped `tabler-icons-react` (stale, last published years ago). Import icons by name; never `import *` (defeats tree-shaking).
- **Typography — both `--font-display` and `--font-sans` are self-hosted (SIL OFL 1.1, Google Fonts), never loaded from Google's CDN at runtime** — files live in `frontend/src/assets/fonts/`, credited in README's Acknowledgements section, `@font-face` blocks in `index.css`. `--font-display` is Libre Baskerville (headings, piece/card titles, sidebar nav). **`--font-sans` became self-hosted Rethink Sans on 2026-08-24** (was previously a bare system stack, `-apple-system, Segoe UI, Roboto, Helvetica Neue, Arial` — kept as the fallback tail now, not removed). Reason: system fonts don't reliably support `font-weight: 500`/`600` — Arial/Helvetica Neue have no Medium cut at all (silent fallback to 400), older Windows Segoe UI's 500 request often snaps to 400 too — and this app's sans text genuinely uses both weights (tag pills, small uppercase section labels, a couple of wizard field labels/badges; confirmed via a real grep audit, not assumed — 700 is never used in a sans context anywhere). Decided via a published font-comparison artifact comparing 6 real candidates. Rethink Sans ships as a single *variable* font per subset/style on Google Fonts (confirmed via its own `fvar` table) — self-hosting it is 4 files total (`latin`/`latin-ext` × `normal`/`italic`) covering its full weight range, not one file per weight the way Libre Baskerville's static cuts need.
- **`--font-sans` replaced again, Rethink Sans → Cabin, 2026-09-01 (direct request).** Decision process, not just the outcome: a real comparison Artifact rendered the actual Piece Details mockup twice (screenshot diff first, then upgraded to two live Shadow-DOM-isolated copies of the real extracted DOM/CSS/fonts once a letter-spacing slider was requested) — landed on **`+0.02em` tracking** on top of the Cabin swap, dialed in live against real content rather than guessed. Two real Artifact-building bugs surfaced and fixed along the way, both worth remembering for any future artifact embedding real extracted app markup: (1) Google Fonts loaded via `@import` inside a `<style>` tag is silently dropped by the Artifact CSP — `getComputedStyle` kept reporting the "correct" font-family string the whole time, which is what made it easy to miss; only `document.fonts` status and actual canvas `measureText` glyph-width comparisons (against a definitely-fake font name) caught it. Fix: a real `<link rel="stylesheet">` tag, per the CSP's own documented allowance. (2) A CSS override rule targeted `body`, matching nothing — the extracted page snapshot is a bare `<div id="root">`, not a real `<body>` element. Fixed by retargeting to `#root`.
  - **A second false alarm, this time about Cabin itself, worth remembering for any future static (non-variable) Google Fonts family evaluation:** confirmed via Google's own CSS2 API that Cabin has no variable-font axis (unlike Rethink Sans) — but a *combined* multi-weight request (`ital,wght@0,400;0,500;0,600;0,700`) returned the literal same file URL for every weight, which looked exactly like "this family has no real Medium/Semibold cut," the exact disqualifying failure mode that ruled out the bare system stack in the first place. That reading was wrong — an artifact of the combined-request code path, not a fact about the font. Requesting each weight in total isolation (`ital,wght@0,500` alone, etc.) returned genuinely distinct files every time, confirmed both by URL and by live canvas `measureText` showing real width differences between weights. Self-hosting used the isolated-request files. Re-check any future static-family font this way before concluding it lacks a weight it appears to lack — a combined multi-weight query is not a reliable way to probe per-weight file distinctness.
  - **Weight/style coverage widened beyond the original 400/500-only scope**, per a fresh grep audit (the *original* Rethink Sans audit only found 400/500 reachable in a sans context — genuinely stale by this point): `font-semibold` (600) turned out to be reachable too, most notably `MarkdownText.tsx`'s own `strong` renderer (Piece/Book descriptions and notes support Markdown `**bold**`), plus several filter-drawer section labels and grid-card count badges; `font-bold` (700) has one real if minor reachable case (People Library's tiny circular info-badge glyph). 400 italic covers Markdown `*emphasis*` (`MarkdownText`'s `em` has no override, so it was already falling through to the browser's default italic rendering — a real cut beats a synthesized slant). Five weight/style combos self-hosted in total (400/500/600/700 normal + 400 italic) × latin/latin-ext = 10 files, ~139KB — Rethink Sans's own 4 files are deleted outright, not kept as a fallback (grepped first to confirm nothing else in the frontend still named it).
  - **`--font-music` (`Bravura Text`'s own text fallback, used by `MarkdownText.tsx` for every piece/book description and piece note) updated too, not just `--font-sans`** — caught by direct instruction mid-implementation ("be sure the special cases for the description field and user notes... get updated too"), and a real thing this exact class of change could otherwise silently miss: `MarkdownText`'s wrapper div always carries `font-music`, never `font-sans`, so a piece's description/notes text (including any Markdown-rendered bold/italic within it) was never going to pick up a `--font-sans`-only swap. Fixed by updating both tokens in lockstep: `--font-music: 'Bravura Text', 'Cabin', -apple-system, ...`.
  - **The `+0.02em` tracking applies via one rule, not two** — `body { letter-spacing: var(--tracking-sans); }`, which reaches `font-music`-styled text for free through ordinary inheritance (letter-spacing crosses a `font-family` change on the same element fine; MarkdownText's wrapper is a descendant of body either way). The only exemption needed is `.font-display { letter-spacing: normal; }`, for the same reason `--font-sans` itself needs no display-side exemption: sidebar nav and every heading already render in Libre Baskerville via `.font-display`, not the sans stack, so without this exemption the new tracking would leak into text that was never using Cabin in the first place (letter-spacing is inherited; a font-family change on a descendant doesn't reset it).
  - **`--tracking-sans` is a plain `@theme` custom property**, not a Tailwind-generated utility — it exists purely to be referenced by the one `body` rule above, not to be applied per-element via a class.
  - Live-verified against the real dev server (not just the mockup that originated the decision): `document.fonts`/canvas `measureText` confirm Cabin is genuinely rendering (not a silent fallback) and that weight 600 is genuinely distinct from 400; spot-checked `/`, `/people`, `/books` in addition to `/mockup/piece-details` to confirm the token change applies identically everywhere, since there's no separate mockup-only stylesheet — a shared `@theme` token can't be previewed in isolation, only shipped for real. README's Acknowledgements line updated (Cabin is by Impallari Type and Rodrigo Fuenzalida, same underlying foundry as Libre Baskerville's own Pablo Impallari, coincidentally).
- **IMSLP and ISBN fields use `font-mono` (Tailwind's built-in system-monospace stack, no self-hosted webfont) app-wide, both as input fields and wherever the raw value is displayed — added 2026-09-02, direct request.** These are catalog identifiers, not prose — a monospace treatment reads as "code/ID," matching the file-hash display (`PiecePage.tsx`) and the Source Book card's own IMSLP/ISBN identifier slot, which already used `font-mono` before this and was the precedent this generalizes. Applied to all 10 real input call sites sharing the `register('isbn', ...)`/`register('imslpNumber', ...)` pattern (`EditPieceModal.tsx`, `EditBookModal.tsx`, `BookUploadAboutStep.tsx`, and their 3 mockup counterparts — 4 ISBN + 6 IMSLP; `font-mono` on the `<input>` covers its placeholder text too, since placeholders inherit font-family) and every dedicated value-display site (`PiecePage.tsx`'s own "IMSLP no." `DetailRow`, `BookDetailsPage.tsx`'s IMSLP/ISBN rows, and their `PieceDetailsSample.tsx`/`BookDetailsSample.tsx` mockup counterparts) — the *fused* Source Book identifier slot (`PiecePage.tsx`/`PieceDetailsSample.tsx`, "IMSLP #12345" or a hyphenated ISBN shown opposite composer/year) already had it and needed no change. `PieceDetailsSample.tsx`'s local `EffectiveValue` helper had to widen its `value` prop from `string | null` to `ReactNode` (matching the real `PiecePage.tsx` version, which already accepted `ReactNode`) to accept a `<span className="font-mono">` wrapper. Live-verified against real dev data (read-only — viewed existing pieces/books, opened Edit Piece/Edit Book to check input styling, closed both via Escape with nothing saved): confirmed via `getComputedStyle().fontFamily` on both display spans and both modals' `#f-isbn`/`#f-imslp` inputs that they resolve to the monospace stack, not just eyeballed from a screenshot. `tsc`/`eslint` clean across all 10 touched files (only pre-existing, unrelated warnings/errors — confirmed via `git stash` comparison — on files this change didn't functionally touch).

- **React lint gotchas, worth knowing before they cost you time re-discovering them:** `react-hooks/refs` forbids assigning `ref.current = value` directly in a component's render body ("Cannot access refs during render") — do the sync inside a `useEffect` instead. `react-hooks/set-state-in-effect` flags a `setState` call inside an effect; where it's a genuine external-trigger sync rather than a same-render feedback loop, the resolved pattern on this project is a scoped `eslint-disable-next-line` with a comment justifying why (see `Modal.tsx`/`EditBookModal.tsx` for precedent) — not restructuring the code to dodge the rule. `react-refresh/only-export-components` flags a component file that also exports non-component constants (e.g. a shared data array) — breaks Fast Refresh for that file; move the constants into their own module instead (see `lib/navItems.ts`, split out of `Sidebar.tsx` for this exact reason). **`react-hooks/purity`/`react-hooks/refs` also fire on a `Date.now()` call or a `ref.current =` write placed inside a function passed to react-hook-form's `handleSubmit()`** (e.g. `onSubmit={handleSubmit(onSubmit)}`) — even though that function only ever actually runs from a real submit event, the linter can't statically prove `handleSubmit(...)` (an opaque call happening during render) doesn't invoke its argument synchronously right there, so it conservatively flags anything impure/ref-touching reachable from it. - **A popup/tooltip that must reposition itself dynamically near a scrollable boundary needs `position: fixed` with JS-computed viewport coordinates, not `position: absolute` anchored to a relatively-positioned ancestor — found the hard way 2026-08-24 building the Book Upload Wizard's hover-to-preview popup.** An absolutely-positioned element, even only mounted while actively shown, even at `visibility: hidden`, still contributes its bounds to its nearest *scrolling* ancestor's scrollable-overflow region for as long as it's in the DOM. If a clamp/reposition effect shrinks that footprint (exactly what "nudge it back into the viewport" does) while the container happens to be scrolled to its old max extent, the browser re-clamps `scrollTop` to the new max — which can silently cancel the popup's own on-screen correction, or worse, shift page content under a stationary mouse cursor and trigger a mouseleave→unmount→scrollHeight-shrinks-back→mouseenter-again oscillation (confirmed directly: a popup mounting/unmounting multiple times a second). `position: fixed` sidesteps this entirely — a fixed-position descendant never contributes to any ancestor's scrollable content regardless of size/position, the same reason `PageLightbox.tsx`/`Modal.tsx`'s own backdrops never hit this. No portal needed unless some ancestor establishes its own containing block via `transform`/`filter`/`perspective` (the *different*, unrelated fixed-position trap described in the bullet just above). A CSS-only fix (measuring via `getBoundingClientRect` and applying a `transform` shift, matching `InfoTooltip.tsx`'s own horizontal-clamp technique) looks correct, tests correct in isolation, and can still fail exactly like this in a real scroll container — this class of bug won't show up unless the popup is actually taller than its trigger and the container is actually scrolled near an edge when it's tested.

- **`Dockerfile`**: 3 stages, no cross-compilation anywhere in the file itself — `node:22-bookworm-slim` builds the frontend, `golang:1.26-bookworm` copies that build's output over `internal/webui/dist`'s placeholder and runs `CGO_ENABLED=0 go build` (no CGO anywhere in this module — `modernc.org/sqlite`/`robfig/cron` are both pure Go — so this produces a fully static binary), `debian:bookworm-slim` is the runtime with `poppler-utils` (PDF thumbnailing) and `wget` (only so `HEALTHCHECK` can hit `/healthz` without a dedicated Go subcommand for it — debian-slim ships neither `wget` nor `curl` by default). `org.opencontainers.image.source` label points at the repo, which is what let GHCR auto-link the package without a manual step. Image is ~172MB.
  - **Runs as a fixed non-root uid/gid 1000 (added 2026-08-23, security assessment SNK-03)** — `/data` is created and `chown`'d to that user at build time, so a fresh Docker named volume inherits correct ownership automatically (Docker initializes an empty named volume from whatever's already at that path in the image). `docker exec` correctly defaults to the same user too (inherits the Dockerfile's `USER` directive), so admin CLI commands work with no extra flags. The one real wrinkle: a host bind-mount (what `docker-compose.yml` actually uses, `./data:/data`) keeps whatever ownership the host directory already has — on most single-user Linux installs the operator's own login is already uid 1000 (Ubuntu/Debian/Fedora's default first-user uid), so this is a non-issue in practice, but `docker-compose.yml` carries a comment on the fix (`sudo chown -R 1000:1000 ./data`) for the case where it isn't.
- **`docker-compose.yml`**: one service, host bind-mount at `/data` (see the uid/gid note above), commented `environment:` block, healthcheck using `/healthz`.
- **`.github/workflows/docker-publish.yml`** — three triggers, one of which (`release`) splits into two publish channels by `github.event.action`:
  - `push` to `main`: validation build only (`push: false`) — this is what makes the README's Build-status badge meaningful day to day, separate from actual releases.
  - `release: types: [released, prereleased]` — both actions run the same multi-arch build (native runners, not QEMU emulation — GitHub's free, GA native ARM64 hosted runners, `ubuntu-24.04-arm` — build `linux/amd64`/`linux/arm64` as separate matrix jobs, no cross-compile flags needed since each job already produces the right architecture). Each arch job pushes **by digest only** (`push-by-digest=true`); a separate `merge` job combines both digests into one multi-arch manifest via `docker buildx imagetools create`, tagged with the release's own tag name — Docker's own documented pattern for multi-arch builds split across separate native runners. Every `${{ github.event.release.tag_name }}` reference here goes through an `env:` var, never interpolated straight into a `run:` script body (security assessment SNK-04 — git ref names allow shell metacharacters, and direct `${{ }}` interpolation in a script body is GitHub's own well-documented script-injection class).
    - **Both actions unconditionally point the floating `:dev` tag at whatever was just published** (added 2026-08-23, direct instruction) — `:dev` tracks the tip of publishing activity, period, not just pre-releases: a real release can legitimately contain fixes made after the last pre-release was cut, so `:dev` needs to move forward on a real release too, or it'd go stale exactly when someone testing against it needs it least. No `releases/latest`-style check needed either way — GitHub has no "marked latest pre-release" concept to compare against, so this step carries no `if:` at all within the `merge` job.
    - **`action == 'released'` only** (a real release, or a prerelease converted to one) additionally: **`:latest` tracks GitHub's actual latest release, not just "most recently published"** — the `merge` job calls `GET /repos/{owner}/{repo}/releases/latest` (via `gh api`) and compares its `tag_name` to the release that triggered the run, only tagging `:latest` if they match, so a release published for an older branch (or with "Set as the latest release" unchecked) can't clobber it. The `attach-assets` job also only runs here, uploading `docker-compose.yml` to the release via `gh release upload <tag> docker-compose.yml --clobber` (a stable, versioned download URL, and a real number for the README's Downloads badge to count — GHCR exposes no public pull-count API, so a release asset is the closest thing to a live counter this setup can offer). Independent of `build`/`merge` (it's a repo file, not the image), needs its own job-level `permissions: contents: write` override since the workflow's top-level permissions only grant `contents: read`. **Doesn't retroactively apply to a release published before this job existed** — the first real release (`0.1`) predates it and would need the asset attached by hand if it's ever worth backfilling. Doesn't run at all for `action == 'prereleased'` — that's part of the polished, stable distribution story, not a dev/testing build.
  - `workflow_dispatch`: no build at all, just re-runs the same `releases/latest` check and re-points `:latest` (`docker buildx imagetools create` again — a cheap manifest copy, not a rebuild) — for "I changed which release is marked latest after the fact" without cutting a whole new release. Doesn't have an equivalent `:dev`-resync path — there's no "marked latest pre-release" override concept for it to correct for, so the scenario that motivates this for `:latest` doesn't really apply to `:dev`.
- **GitHub-website steps this needed** (not app code, but real one-time setup, worth remembering if a future repo/org needs the same thing): Settings → Actions → General → Workflow permissions → "Read and write permissions" (the workflow's own `permissions: packages: write` is capped by this repo-level setting regardless of what the YAML requests); after the first release-triggered publish, the GHCR package defaults to **private** regardless of the source repo's visibility and needs a manual Package settings → visibility → Public (confirmed via GitHub's own docs: package visibility is independent of repo visibility for Container Registry specifically — this is a real, deliberate GHCR feature, not a bug to route around. One caveat worth remembering: switching a package to public **cannot be undone** through the normal UI).

- **A real, previously-latent bug in the shared `Modal.tsx` component surfaced immediately once two Modals could genuinely be open at once (Edit Person + the Upload Portrait it now nests) — the first real case of stacked modals anywhere in this app.** Every `Modal` instance independently registers its own `document`-level `keydown` listener for Escape, with no coordination between instances. With two open at once, **both** listeners fire for the same Escape press — normally harmless (pressing Escape while nothing else is open just closes the one modal, the only case that existed before this), but with two stacked: the *background* modal's listener, having mounted first, is also registered first and therefore always fires first, closing the modal *behind* the one the user is actually looking at — backwards from what Escape should do. Worse, that background modal's `onClose` firing triggers a cascading re-render that tears down the *foreground* modal's own listener before the same synchronous event-dispatch pass ever reaches it, so the topmost modal doesn't just fail to close first — it silently doesn't close *at all* on that press. Confirmed precisely via temporary render/listener-lifecycle logging (not guessed) before writing the fix: computed-style/bounding-box inspection alone couldn't distinguish "correct" from "wrong" here, since Edit Person's own dialog happened to be viewport-centered too, making both hypotheses' math coincide — only direct instrumentation of *which* listener actually fired settled it.
  - **Fix: a module-level stack of currently-open modals** (`openModalStack`, in `Modal.tsx`), keyed by a stable per-instance id (lazy `useRef` init, assigned once) rather than by `onClose` reference — an inline arrow-function `onClose` prop at the call site (common throughout this app) would otherwise cause spurious stack reordering on every unrelated parent re-render, so the id-holding effect that pushes/pops the stack entry deliberately depends only on `[open]`, reading the *current* `onClose` through a ref (`onCloseRef`, kept fresh by a separate small effect) rather than closing over a specific `onClose` value. The Escape-listener effect checks whether it's the stack's topmost entry before acting; a background modal's Escape press is now a silent no-op, deferring to whichever modal is actually on top.
  - Live-verified precisely, not just "it looks fixed": with Edit Person open and Upload Portrait nested on top, one Escape press now closes only Upload Portrait (dialog count 2→1, Edit Person's own fields still present); a second Escape then closes Edit Person too (1→0) — the correct topmost-first sequence. Re-verified the plain single-modal case (no nesting) is unaffected: Escape and backdrop-click both still close a lone open modal normally. This fix lives in the shared component, so it benefits any future stacked-modal case in this app for free, not just this one.
