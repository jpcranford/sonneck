# CLAUDE.md — House Rules & Conventions

Companion to `sonneck-design.md` (the design doc for **Sonneck**, named after Oscar Sonneck, the American musicologist and first head of the Library of Congress's Music Division — see the root README's "About the name" section for the full story). This file is the *living* counterpart to that doc: cross-cutting conventions, and every deliberate deviation from the design doc as the project actually got built, with the reasoning for each. Re-read it at the start of every session; if the two disagree, this file wins.

Keep this file itself lean — it holds **current-state conventions and deviations, not a changelog**. Two other places already carry related content, so don't duplicate their job here:
- **`CONTRIBUTING.md`** mirrors several of the load-bearing rules below for human contributors, in its own words. When changing either, check whether the other needs the same update.
- **Session memory and `git log`** hold the narrative behind these decisions — bug hunts, iteration rounds, dated "found via direct report" detail, the exact sequence a feature got built in. When something here is genuinely resolved and shipped, state the resulting rule/behavior plainly; don't narrate how it got there or when. A memory pointer is given where the fuller story is worth keeping.

## Working with Claude on this repo
Standing process rules, independent of any one feature — a new contributor pointing their own Claude at this repo should pick these up immediately.

- **No git mutations, ever — not even when asked.** No `commit`, `push`, `add`+commit, branch/tag creation, `reset`, `checkout`, `merge`, `rebase`, or `stash`. Read-only git (`status`, `log`, `diff`, `branch -vv`, `blame`) is always fine for orienting or diagnosing. This project's contributors handle every actual git operation themselves — implement, verify, and hand off, but stop short of committing even when a task's own natural completion would normally include one.
- **Never cite which AI tool(s) did the work, anywhere in this repo — no `Co-Authored-By: <AI>` trailer, no "🤖 Generated with ..." badge, no AI name added to a Contributors/Acknowledgements listing.** A coding tool isn't a contributor any more than a table saw is a co-builder of whatever furniture it cut the boards for — the person at the keyboard directed the work, reviewed it, and stands behind it; they're the one who gets credited, not the tool. This holds regardless of any default attribution behavior a given AI tool/session might otherwise apply on its own — for this repo specifically, don't add one. If drafting a commit message or PR description for someone to use, leave any such trailer/badge out of it.
- **Docs move with the code, in the same pass, not after it.** The moment a change makes something in `CLAUDE.md`/`CONTRIBUTING.md`/`README.md` stale — a new env var, a new endpoint, a new deviation from a stated design rule — update it right then, phrased as current-state fact. Don't defer doc updates to a cleanup pass at the end of a multi-step feature; a feature that's genuinely still in progress gets documented as of its current real behavior/limitation, not skipped until "done."
- **A spec with more than one plausible reading gets verified before it's built, not assumed from the first paraphrase that sounds right.** For an ambiguous interaction/state description, restate it as a concrete before/after worked example (specific inputs, specific resulting state) and let that get corrected before writing the algorithm. For a visual/design decision with more than one reasonable outcome (color, opacity, icon, spacing, badge shape) and no single answer already implied by the existing design system, build a real side-by-side comparison Artifact — using the app's actual markup/tokens and real data, not placeholders — rather than picking the most-defensible-sounding option and shipping it directly. Skip this for anything genuinely unambiguous, like a pure bug fix.
- **A third-party API or scraping approach gets a live verification pass before an implementation is designed around it.** Official docs can be incomplete or actively misleading about the real access mechanism (see IMSLP live autofill's own section below for a concrete case) — spend a research pass making real requests against real data first. This includes re-checking whether a specific already-resolved context actually removes an ambiguity a docs-only reading would assume still applies.

## Database migrations
Tool: **goose**. Every schema change is a migration file, checked into the repo, never a hand-edited change to an existing migration.

Deliberate deviations from the design doc's original schema:
- **`Piece.key` is many-to-many** (`Piece.keys`, migration `00008`), not the single `key` tag/FK column §3 specifies — a piece that modulates, or a medley, can legitimately need more than one. `piece_keys` uses `PRIMARY KEY (piece_id, position)` (migration `00012`), not `(piece_id, key_id)`, so the same key can legitimately repeat (e.g. a modulation back to an earlier key). Keys remain explicitly *not* book-inheritable — this is about single- vs. multi-valued, not inheritance.
- **`copyrightYear`/`publicDomain` were pre-built into `Piece`'s v1 schema ahead of their own feature** (§3's stated reasoning) — a one-off exception for cheap, simple columns, not a general license to pre-build ahead of features. (The Public Domain Badge has since shipped — see below — and `publicDomain` was superseded by a real `copyright_status` enum at that point; a plain bool couldn't represent the actual four-way choice.)
- **Composer/Arranger are an ordered reference to a `Person` entity, not a plain string** — see "People / Composer & Arranger" below.

Migration `00020_people_and_credits.sql` is deliberately additive-only — the old `pieces.composer`/`pieces.arranger`/`books.composer`/`books.arranger` TEXT columns are still in the schema, unused by application code, pending a **separate future migration** to drop them. This is load-bearing, not laziness: goose runs every pending migration automatically on startup with no pause for a manual step in between, so a column-drop migration shipping in the same deploy as an additive one would destroy the backfill's own source data before it ever ran.

Full build history for the People/Composer migration (and every polish fix since) is in memory `project_people_composer_overhaul.md`.

**A table-rebuild migration (`CREATE ..._new` / copy / `DROP TABLE <old>` / `RENAME` — needed whenever SQLite can't `ALTER` a `UNIQUE` constraint or `DROP COLUMN` a column carrying its own `CHECK` constraint in place) must bracket the `DROP TABLE` in `PRAGMA foreign_keys = OFF;` / `PRAGMA foreign_keys = ON;` (with a `-- +goose NO TRANSACTION` directive, since SQLite refuses to toggle that pragma inside a transaction) whenever any other table references the one being dropped via `ON DELETE CASCADE`.** `internal/db/db.go` sets `_pragma=foreign_keys(1)` on every connection permanently, and with that on, SQLite's `DROP TABLE` performs an implicit `DELETE FROM` first — which genuinely fires `ON DELETE CASCADE` on every referencing table, even though `DROP TABLE` is schema DDL, not an application `DELETE`. Migration `00025`'s own rebuild of `pieces`/`user_tags` did this un-bracketed and silently cascade-wiped `piece_composers`/`piece_arrangers`/`piece_keys`/`piece_instruments`/`piece_user_tags`/`piece_favorites`/`piece_practice_status`/`piece_user_notes` against the real dev library — see that migration's own header comment for the fixed, bracketed version to copy, and `internal/db/migration_safety_test.go`'s `TestMigrationPreservesRelationalData` (seeds real rows in every FK-child table at v24, asserts the count survives migrating to latest) for the regression guard this incident produced. Also in memory `feedback_migration_fk_cascade_wipe.md`.

## API response contract
Every endpoint returns one of two shapes — no per-handler improvisation:
```json
// success
{ "data": { ... } }

// error
{ "error": { "code": "VALIDATION_ERROR", "message": "human-readable description" } }
```
If a decision point isn't covered by this doc, default to this shape rather than inventing a variant.

## Testing
No comprehensive test suite is required for v1, but one area is **not optional** because failures there are silent and permanent:
- **PDF page-extraction logic** (the import wizard's split step, `internal/wizard/`/`internal/pdf/`, mirrored client-side in `frontend/src/lib/pieceSplitLogic.ts`) — a wrong page range is a data-correctness bug nobody notices until they open the piece later. Needs unit tests covering at least: single-page piece, multi-page piece, first piece includes page 1, last piece includes the final page, off-by-one boundaries between adjacent pieces.

Everything else: use judgment, but the PDF-extraction logic above is load-bearing.

## Live browser verification (dev tooling, not app code)
No MCP browser tool is configured in this environment. A real Chromium is still available: `npx playwright` caches a full install to `~/.npm/_npx/<hash>/node_modules/playwright/` (`find ~/.npm/_npx -maxdepth 3 -iname playwright`; run `npx playwright --version` once first if that comes up empty, to populate the cache). Drive it directly with a hand-written Node script through Bash:
```js
import { chromium } from '/Users/<user>/.npm/_npx/<hash>/node_modules/playwright/index.mjs'
const browser = await chromium.launch()
const page = await browser.newPage({ viewport: { width: 1000, height: 1000 } })
await page.goto('http://localhost:5173/...')
// ...interact, assert, page.screenshot()...
await browser.close()
```
Needs both dev servers already running — backend on `:8080`, Vite on `:5173` (check with `lsof -iTCP -sTCP:LISTEN -P` rather than assuming). **`PORT`'s own default is OS-dependent, not always `8080`**: `internal/config.defaultPort()` returns `"8080"` only on Linux — on darwin/windows (this maintainer's own dev machine) the real default is `"26163"` (middle C's frequency, 261.63 Hz), picked for the native desktop build's own end-user port-collision concerns, but it applies to the plain `cmd/sonneck` dev binary too since `config.Load()` has no way to know which `cmd/` package called it. Vite's own `/api` proxy is hardcoded to `:8080` regardless, so a bare `go run ./cmd/sonneck` on macOS/Windows binds a port Vite never proxies to — always start the dev backend with `PORT=8080` explicit on those platforms (`DATA_DIR=./data PORT=8080 go run ./cmd/sonneck`), not just `DATA_DIR=./data`. Use this section for anything a type-check or unit test can't actually catch — a real click-through sequence, animation/transition timing, DOM state after an interaction.

**The dev library at `./data` (`DATA_DIR`) is read-only.** Don't write to it — not through the app's own endpoints, not direct SQL, not file operations. To verify a write flow: start a second Go backend on a different port against a throwaway `DATA_DIR` (`PORT=8099 DATA_DIR=<scratchpad>/throwaway-data go run ./cmd/sonneck`), plus a throwaway Vite config (`frontend/vite.throwaway.config.ts` — must live inside `frontend/`, never committed — proxying `/api` to that port), and drive Playwright at the throwaway Vite's port. Clean up both processes and the throwaway files afterward.

**Stop a disposable backend by its exact PID, never by a `pkill -f` pattern.** `go run` compiles to a temp binary under a `go-build*` path containing the module name — since the real, long-running dev backend on `:8080` is typically also started via `go run ./cmd/sonneck`, any `pkill -f "go-build.*sonneck"`/`pkill -f "cmd/sonneck"` pattern matches both processes with no way to tell them apart once compiled. This has killed the real dev backend more than once, silently. Get the exact PID instead — `lsof -tiTCP:<port> -sTCP:LISTEN | xargs -r kill` — for both the disposable Go backend and its throwaway Vite server, and after any kill, verify the real dev backend (`curl -s http://localhost:8080/healthz`) and Vite (`lsof -iTCP:5173`) are still up before considering cleanup done.

**The long-running dev backend doesn't hot-reload.** A "no such endpoint" error against a newly-added route usually means the backend process is stale, not that the code is wrong — restart it (`ps eww -p <pid>` recovers its env vars if not already known; restarting doesn't touch `DATA_DIR`).

**Verify fine visual details with pixel data, not by eyeballing a screenshot.** Visual inspection is unreliable for shape-topology questions (is a glyph's counter open or closed) and gradient-fidelity questions (does an overlay render monotonically) — flood-fill connectivity analysis for the former, clean scanline pixel sampling for the latter. Normal visual QA (layout, color, spacing) is fine to eyeball; this is specifically for defects too subtle to reliably see by eye. A sub-pixel/font-rendering question (e.g. is an icon+label row *exactly* centered) is a *third* category this doesn't cover either — rendering genuinely differs by browser engine, so build a throwaway interactive calibration page and judge it live in the real target browser instead of trusting an automated cross-engine measurement.

**Verify against data missing the relevant optional fields, not just happy-path fixtures.** A layout relying on `justify-between` against a sibling that can render `null` (e.g. `TagPills` with no tags) looks correct against a fully-populated fixture and breaks silently the moment that field is empty — often the common case, not the edge case. Prefer `ml-auto` over `justify-between` when the pinned element's sibling might not render.

**Inline images/screenshots don't render for the user in this chat client.** Save any screenshot the user needs to see to `design-review/` (gitignored) and tell them it's there. Published Artifacts are unaffected — they render in their own viewer.

## Concurrency
No multi-writer conflict handling (design doc §8) — a deliberate, still-current decision even now that real multi-user backend support exists (see Multi-user support below): the realistic case is a household/small group, not concurrent strangers, and nothing in that build asked for optimistic locking/edit-conflict UX. SQLite WAL mode is enabled at startup regardless (cheap, no reason to skip it; it's also what lets the admin-CLI subcommand pattern below safely run reads/writes against a live server).

`Piece.userNotes`/`userTags`/`favorite`/`practiceStatus` are genuinely account-scoped as of migration `00025` — see Multi-user support below for the real shape this took. `userTags` is a **fully private per-user vocabulary** (`user_tags.owner_user_id`) — two different users typing the identical tag name each get their own row, never share one; this is a real behavior difference from `Key`/`SheetType`/`Instrument`, which stay shared/global catalogs.

## Multi-user support
Design doc §13's "Auth & multi-user" feature. Real backend support (permissions, sessions, per-user data scoping) shipped in Phase 10 of the build (memory `project_multiuser_build.md`). The sidebar's own account surface is real as of Phase 11: `AuthGate`/`LoginScreen` (`App.tsx`, `frontend/src/routes/LoginScreen.tsx`) is a genuine boot-time login wall for `singlepass` mode, and `UserMenuButton` (`frontend/src/components/UserMenuButton.tsx`, shared by `Sidebar.tsx`/`MobileNav.tsx`) shows the real signed-in identity/permissions and performs a real log out. **User Settings is real as of Phase 12** (`/settings`, `frontend/src/routes/UserSettingsPage.tsx`) — self-rename, self-service password change (singlepass), theme/library preferences (`GET`/`PATCH /api/user-settings`), and real create/rename/delete-merge for Tags/Practice Status; `UserMenuButton`'s own theme switcher shares the identical persisted setting, not a separate local value. **Admin Settings is real as of Phase 13** (`/admin`, `frontend/src/routes/AdminPage.tsx`) — Users (permission grid, delete), Security "Change…", Library stat counts, and Sheet Types/Instruments create/rename/delete-merge were already real from Phase 10; Phase 13 added the two remaining gaps, Library Settings and Version/Check-for-updates (see their own bullets below). **OIDC is real as of Phase 14** (own bullet below) — the only mode that ever produces more than one real account, so a real deployment using it can now genuinely have more than the one seeded `id=1` account the `none`/`singlepass` modes are always implicitly limited to.

- `AUTH_METHOD` env var — one of `none` (default), `singlepass`, `oidc`. Resolution order, one shared implementation (`repo.ResolveAuthMethod`, used by both `GET /api/config` and `authMiddleware`): the env var if set, else `server_settings.auth_method` (set via the first-launch flow, or later via `POST /api/admin/security`), else `none`.
- **First-time launch flow** (`frontend/src/routes/FirstLaunchFlow.tsx`, gated into `App.tsx` behind `GET /api/config`'s `firstLaunchCompleted`) — Welcome → Library Folder → Security. Library Folder has two real variants keyed off `buildTarget`: Docker's read-only mount-point display, and (native macOS/Windows builds, `cmd/sonneck-desktop` — memory `project_wails_native_app_investigation.md`) a native variant with a real OS folder dialog whose "Browse…" immediately persists the choice and restarts the app, since a native build's data directory is resolved once at process start and can't change without one. Security picks `none`/`singlepass` (`oidc` is env-var-only, never selectable here — it needs secrets a pre-auth web form can't safely collect); `POST /api/setup/complete` (`internal/handlers/setup.go`) is the one real write this flow performs — hashes a `singlepass` password with bcrypt onto the seeded `users` row (`id=1`), and refuses to run again once `first_launch_completed_at` is set.
- **`authMiddleware`** (`internal/handlers/middleware.go`) wraps every route except a small public allowlist (`GET /api/config`, `POST /api/setup/complete`, `POST /api/auth/login`, `GET /api/auth/oidc/login`+`/callback` (Phase 14), `GET /api/auth-change/candidates`+`POST /api/auth-change/complete` (Phase 16) — every one of these reachable pre-session by definition — plus the embedded frontend itself, always served unauthenticated so the SPA shell can load and ask these same endpoints what to show). In `none` mode every request resolves to the implicit `id=1` user with zero session overhead, identical to the pre-multi-user app; `singlepass`/`oidc` require a valid `sonneck_session` cookie (`internal/auth`, 30-day TTL, always `HttpOnly`/`SameSite=Lax`). **`Secure` is conditional, not hardcoded either way** (`isSecureRequest`, `internal/handlers/auth.go`, shared by the session cookie and OIDC's own short-lived state cookie) — true when the request itself arrived over real TLS (`r.TLS != nil`, effectively never in practice, this app always binds plain HTTP) or, only when the operator has explicitly opted in via the `TRUST_PROXY_HTTPS` env var (default `false`), a reverse proxy's `X-Forwarded-Proto: https` header. Found via a CodeQL scan flagging all four `http.SetCookie` calls for a hardcoded non-`Secure` cookie — hardcoding `Secure: true` instead would have silently broken login for this app's primary documented deployment (plain HTTP on a LAN with nothing in front of it, the README's own CAUTION callout), since a browser refuses to send a `Secure` cookie back over a non-HTTPS connection; only set `TRUST_PROXY_HTTPS=true` when a reverse proxy genuinely terminates HTTPS in front of this app and controls that header itself. `requirePermission` (`(*Server).requirePermission`, `internal/handlers/middleware.go`) is the one shared per-handler gate on top of that (CLAUDE.md's own "one shared helper" convention, same shape as `ResolveEffective`) — called as the first line of any handler that needs a specific permission, not a blanket route-metadata middleware, since requirements vary per-handler. `POST /api/auth/login` (singlepass password check), `POST /api/auth/logout`, `GET /api/auth/me` (current user + permissions + auth method — the frontend's one source of truth as of Phase 11, via `frontend/src/lib/AuthContext.tsx`'s `useAuth()`, set once by `App.tsx`'s `AuthGate` and read by `UserMenuButton` and the `/admin` route guard). **Phase 12** added `PATCH /api/auth/me` (self-rename, `read`-permission only — any authenticated user can rename themselves, no admin gate needed) and `POST /api/auth/change-password` (self-service, singlepass-only, verifies the caller's own current password first — distinct from `POST /api/admin/security`'s admin-only set-or-clear below, which never asks for one).
- **Home-screen web app downloads** (`manifest.webmanifest`'s `display: standalone`, detected by `lib/homeScreenApp.ts`): in that chrome-less window every plain link form — `<a download>`, `target="_blank"`, even a `Content-Disposition: attachment` response — just shows the PDF inside the app with no way back out (confirmed on a real iPhone). So `components/DownloadLink.tsx` (Piece Details' Download PDF button and dropdown item) fetches the file itself on tap (same-origin, so the app's own session cookie applies in every auth mode — no token or cookieless URL needed) and saves it through a blob URL + `download` attribute, which iOS opens in its own PDF viewer (close/back to the app, plus share and open-in-browser); other platforms save it normally. **Never via a scheme that forces a specific browser** (e.g. `x-safari-https://`) — the user's default-browser choice is respected. The Web Share API isn't an option for the common deployment: it only exists in a secure context, and plain HTTP on a LAN isn't one. Book Details' "Open PDF" isn't a download and stays a plain link. Outside home-screen mode every download link is the unchanged plain `<a href download>`.
- **Icons behind an authenticating reverse proxy** (Cloudflare Access etc.): `index.html`'s manifest link carries `crossorigin="use-credentials"`, since a manifest is otherwise fetched without cookies and gets the proxy's login redirect. iOS's home-screen icon fetch can't be fixed from the app, so the README's Security section tells operators to let the icon/manifest paths bypass the proxy's login.
- **Per-user data** (migration `00025`): `piece_favorites`/`piece_user_notes`/`piece_practice_status` replaced the old flat `pieces.favorite`/`.user_notes`/`.practice_status` columns entirely (`repo.GetUserPieceData`/`SetUserPieceData`) — fetched/written only by handlers with a request-scoped user (`api.BuildPieceResponse`/`applyPieceWriteRequest` both take a `userID`), never by `repo.GetPieceByID`'s many other callers (search indexing, thumbnail maintenance, CSV export, CLI subcommands), which have no such user to scope by. Practice Status itself became a real per-user `practice_statuses` lookup table (rename/create/delete/merge, same shape as `user_tags`) instead of a fixed enum — `models.Piece.PracticeStatus`'s old five-value CHECK constraint is gone from Go entirely; a piece write's `practiceStatus` name is validated against the calling user's own rows (`repo.FindPracticeStatusByName`) in the handler, not inside the (DB-user-unaware) `api.ValidatePiece`.
- **Practice Status is rename-proof** (migration `00026`): `practice_statuses` carries two durable columns beyond `name`, both set once when a status is seeded and never touched by a rename — `sidebar_slot` (`want_to_learn`/`practicing`/`learned`, not unique per slot — Learning and Stalled both carry `practicing`, since "Currently Practicing" is that pair OR'd together) and `icon_key` (`want_to_learn`/`learning`/`learned`/`stalled`/`dropped`, a *different* enum from `sidebar_slot` since Stalled/Learning share a slot but need different icons, and Dropped has an icon but no slot). The sidebar's three fixed views (`WantToLearnPage.tsx`/`PracticingPage.tsx`/`LearnedPage.tsx`) filter by a `practiceStatusSlot` query param (`practiceStatusSlotClause`, `internal/handlers/search.go`) matching `sidebar_slot`, not the old name-based `practiceStatus` param — renaming a status no longer breaks these views or the Piece Details/Grid-card icon that used to be keyed by live name. `repo.PracticeStatus.IconKey` carries this to `GET /api/practice-statuses`; User Settings' own icon lookup reads it directly (`item.iconKey`), no client-side caching. Both columns stay `NULL` for a user-created status — matches the still-deferred "no icon-assignment UX for custom statuses" decision (`canAdd={false}` on Practice Status creation in `UserSettingsPage.tsx`/its mockup) without touching it.
- `api/types.ts`'s **`PracticeStatus` type is a plain `string` alias, not a closed union** — it used to list the five original names, a leftover from before migration `00025` made Practice Status a real per-user table; the stale union caused a real crash (`components/PracticeStatusIcon.tsx` indexed a `Record<PracticeStatus, Icon>` unconditionally, so any piece carrying a renamed status threw "Element type is invalid" wherever it rendered — Piece Details, Grid cards). `PracticeStatusIcon` now returns `null` instead of crashing when a name isn't one of the five originals — a status renamed away from a default simply shows no icon outside User Settings (`GET /api/pieces` doesn't carry a status's `iconKey`, only its live name), an accepted display gap, not a functionality break.
- **Practice status from the piece menu** (design C′, `/mockup/add-to-setlist`): `PieceContextMenu` — every piece's right-click/long-press menu (Library grid and list, Book Details, Person Details) — opens with `components/PracticeStatusStrip.tsx`, one button per status in the viewer's own list (`GET /api/practice-statuses`, icons by the durable `iconKey` via `PracticeStatusKeyIcon`, so a renamed status keeps its icon; a status with no `iconKey` shows its initial), above the menu's actions. One click sets a status and closes the menu; clicking the current one clears it; the label line names the hovered/focused button, else the current status. It renders through `ContextMenu`'s `header` slot (custom content above the items, given `close`). **Hidden outright without the `practice` permission**, and the write goes through its own endpoint, `PATCH /api/pieces/{id}/practice-status` (`{practiceStatus: name | null}`, `read` then `practice`, `repo.SetUserPracticeStatus`), not the `edit`-gated full `PATCH /api/pieces/{id}` — a practice status is the caller's own data, not library metadata. The menu's Add to Favorites item still writes through the full `PATCH` and so still needs `edit`.
- **Practice statuses are always listed in practice order** — Want to Learn, Learning, Learned, Stalled, Dropped — never `GET /api/practice-statuses`' alphabetical order: by the durable `iconKey`, so a rename doesn't move a status, with any status lacking one after, by name. Frontend lists go through `lib/practiceStatusOrder.ts`'s `sortPracticeStatuses` (the piece menu's strip, the Edit Piece dropdown, User Settings' list and its merge picker); the Filter Drawer's Practice Status facet is ordered the same way in its SQL (`facets.go`, `TestPieceFacets_PracticeStatusesInPracticeOrder`). Mockups hard-code the same order.
- **Search index privacy**: `pieces_fts`'s `user_notes`/`user_tags` columns are deliberately always written empty as of this migration — both source fields became per-user, and the FTS index is one shared row per piece, so indexing either would leak one user's private text/tag names into every other user's search matches. Left as always-empty columns (not dropped from the FTS5 schema, which would need a drop-recreate migration for no benefit) rather than genuinely per-user indexed.
- **Admin endpoints** (all `admin`-permission-gated, `internal/handlers/admin.go`/`lookup.go`): `GET`/`PATCH /api/admin/users{,/{id}}`, `DELETE /api/admin/users/{id}` (guarded — can never remove the last remaining admin, whether via permission edit or delete), `POST /api/admin/security` (`none`↔`singlepass` only — `oidc` and any env-set `AUTH_METHOD` stay permanently unreachable from here, matching the mockup's own scope), `GET /api/admin/library-counts`, and full create/rename/delete-with-merge for Sheet Types/Instruments. The equivalent user-scoped set (`POST`/`PATCH`/`DELETE /api/tags{,/{id}}`, `POST`/`PATCH`/`DELETE /api/practice-statuses{,/{id}}`) is `read`-permission only, not admin-gated — the calling user's own data; the `PATCH` (rename) half of this pair was added in Phase 12, via a new owner-scoped `repo.renameNamedRow` helper (`internal/repo/lookup.go`) — the counterpart to `createNamedRow` below, same `ErrDuplicateName`/`ErrNotFound` guarantees. Every lookup/tag create endpoint rejects a duplicate name with a clean 400 (`repo.ErrDuplicateName`, mapped centrally in `writeError`), not the table's own raw `UNIQUE`-constraint error. **Phase 12** also added `GET`/`PATCH /api/user-settings` (`read`-permission only) — the HTTP surface for `user_settings.show_books_in_sidebar`/`.theme_preference`/`.content_view_mode` (plus `.dark_mode_scores`, migration `00030`), which had existed as repo-layer-only since Phase 10 with nothing calling it.
- **Library Settings** (Phase 13, `GET`/`PATCH /api/admin/library-settings`, `internal/handlers/librarysettings.go`) — Backup schedule/retention, Log level, Copyright region are now genuinely admin-editable at runtime, not just env-var-or-hardcoded-default. Persisted to **`DATA_DIR/config.yml`** (`internal/libraryconfig`), a second deliberate exception to "no settings table in v1" alongside `server_settings` — confirmed directly, not SQLite, so an operator can hand-inspect/back up these four values as a plain file at the library's own root, sibling to `db/`/`backups/`/`cache/`/`library/`. Resolution mirrors every other env-shadowed field: an env var, when set, always wins and gets written back into the file (so the file stays the honest record of what's actually running); each field's own `*SetByEnv` flag locks it in the Admin Settings UI. Every field applies **live, no restart**: `CopyrightRegion`/`BackupRetentionDays`/`BackupCron` are `sync.RWMutex`-guarded getter/setter pairs on `*config.Config` (not plain fields anymore — every read call site across the handlers package calls `s.Cfg.CopyrightRegion()`, not `s.Cfg.CopyrightRegion`), `LogLevel` is a `*slog.LevelVar` the process's one logger already reads from directly, and a changed backup schedule calls `(*backup.Scheduler).Reschedule` (`internal/backup/backup.go`) to actually replace the running cron job's entry, not just update a stored string nothing re-reads.
- **Version / Check for Updates** (Phase 13, `GET /api/admin/version` + `POST /api/admin/version/check`, `internal/handlers/version.go`) — the running build's identity is its own commit SHA + date, injected at build time via `-ldflags "-X main.buildSHA=... -X main.buildDate=..."` (`Dockerfile`'s `go build` step, `ARG BUILD_SHA`/`ARG BUILD_DATE` fed by `.github/workflows/docker-publish.yml`'s own resolved-commit logic; `native-build.yml` passes the same two flags to `wails build`). **A release build also bakes in its own tag as `main.buildVersion`** (`ARG BUILD_VERSION` / `native-build.yml`'s `RELEASE_TAG`, both via an `env:` var, empty for push/nightly/manual builds) — when set it is the running version, authoritative and known at startup (`Server.BuildVersion`, `versionResponse`): no GitHub lookup at all, so it shows on the very first Admin Settings view, offline, and regardless of GitHub's unauthenticated 60/hour rate limit (which a runtime-only lookup silently loses to). Only a build without one falls back to the runtime match below. A plain `go run`/`go build` straight from the repo — this project's entire dev loop included — keeps the `"dev"` sentinel default, which `Server.isDevBuild()` treats as "running from source": no GitHub check ever runs against it, and the frontend shows plain "Running from source" copy instead of a nonsensical templated line. `internal/githubrelease` is the real GitHub REST client (hardcoded to `jpcranford/sonneck`, never user-configurable) — bounded to one releases-list call plus at most two compare calls (the latest release overall, and the latest non-prerelease release, never one compare per historical tag) to determine both "does this exact commit match a tag" and "am I genuinely behind the latest official release," the exact ahead/behind/upToDate refinement the mockup's own forward note called for (a pre-release/dev build already ahead of the latest official release correctly shows "ahead," never a false "update available"). **The running build's own release identity and "Check for updates" are cached completely differently, deliberately.** `MatchedRelease` for a build without an injected `buildVersion` (does this exact commit match a tagged release — `githubrelease.Check` matches the commit against the repo's full tag list, restricted to non-draft releases, so an older build like a 0.7-beta binary still recognizes itself after 0.7-beta.2 ships; comparing only against the newest release/newest stable release couldn't) is resolved at most once per process lifetime — lazily, on the first real `GET /api/admin/version` call rather than on every server boot (so a test constructing a `Server` never triggers a live network call) — and then never re-checked again until the process restarts, since a running binary's own commit can't change while it's up. "Check for updates" (`CheckStatus`/`AvailableVersion`/`CheckedAt`) is the opposite: never cached at all, anywhere — `POST /api/admin/version/check` always performs a fresh `githubrelease.Check` and returns its result directly in that one response, and `GET /api/admin/version` never surfaces those three fields regardless of how recently a check ran. A page reload therefore always shows "Check for updates" as a plain, pressable button, never a stale result from before — and pressing it twice in a row always does two real GitHub round-trips, no TTL-based skip. Real API shapes (`tag_name`/`prerelease`/`draft`, compare's `status`) verified directly against `api.github.com/repos/jpcranford/sonneck` — GitHub's REST API is a stable, versioned, documented contract, a meaningfully different risk profile than the IMSLP scraping elsewhere in this codebase, but still worth a real spot-check if this ever starts silently returning blanks. **Release tags are bare numbers, never `v`-prefixed** (`0.5`, `0.5.1` — confirmed against this repo's own real releases, whose title separately carries a nickname, e.g. "0.5: Nickname"; a prerelease may extend this with a `-alpha`/`-beta`/`-rc[.N]` suffix, e.g. `0.7-beta` or `0.7-beta.4` — see the Native app section's own handling of this in `native-build.yml`, the one place tag format is more than cosmetic) — `internal/githubrelease.Release` only ever fetches `tag_name`, never that title/nickname, and the frontend displays the bare tag verbatim with a literal `"version "` prefix for clarity (`Running version 0.5`, `version 0.5 available`) rather than showing the nickname or inventing a `v` prefix.

## Book-level soft inheritance
Full mechanism in design doc §3/§14/§15/§16 — this section is the implementation convention.

**One shared "resolve effective values" helper** (`repo.ResolveEffective`, `internal/repo/effective.go`), used everywhere a book-inheritable field is read: display (Piece Details, edit menus), validation, citation generation, and search indexing. Never read a book-inheritable `Piece` column directly from any of those four call sites — that's exactly the kind of silent divergence this pattern exists to prevent.

Saving a `Book` edit writes to exactly one record — the `Book` itself. Nothing about any `Piece` row changes; every piece with that `sourceBookId` and no override for the changed field resolves its effective value live against current `Book` data. This still needs a search-index resync for every affected piece (see Search).

**`Piece.yearWritten` has a three-level fallback, not the plain piece-then-book every other field uses**: piece's own `yearWritten`, else the piece's own `copyrightYear` (`resolveYearWritten`, `internal/repo/effective.go`) — checking the piece's own raw column specifically, never the book's copyright year or the piece's *effective* copyright year — else the book's `yearPublished`. Both fallback steps are marked `Inherited: true` on the wire, a deliberate simplification (a genuinely distinct third UI state was considered and declined) — the frontend's Edit Piece Modal derives which of the two actually applies itself (`yearWrittenSource`, comparing the already-exposed `copyrightYear` field) to label `InheritedNote` as "Inherited from copyright year" instead of the default "book" wording when that's the real source, since claiming "from book" would be a factual error there, not just imprecise. `PieceBrowseView`'s SQL-level `sort=yearWritten` (`internal/handlers/search.go`) mirrors this exact chain — it doesn't go through `ResolveEffective` at all, being a raw `ORDER BY`, so it needed its own matching fix.

`sourceBookId` is itself editable from the Piece Edit Menu (`PieceWriteRequest.SourceBookID`, `*int64`, same full-replace rule as every other field — `nil` clears the association) — an addition beyond the original design doc, not a deviation from it (§15 never described re-matching a piece to a different book after the fact).

Three deliberate required-field deviations from design doc §16's "no required fields beyond title," all in `internal/api/validate.go`:
- `ValidateBook` requires `bookTitle` non-empty — an untitled book is a confusing empty state everywhere it's displayed, and the wizard already defaults it from the upload filename in every real path anyway.
- `ValidatePiece` requires composer **or** arranger, not composer alone — a piece crediting only an arranger (a traditional/folk tune) is a legitimate case, not missing data.
- `ValidateBook` also requires one of composer/arranger/publisher — a book with none of the three is missing the one piece of attribution every other bibliographic field is meant to attach to.

## File handling
- All file hashing uses **SHA-256** (`crypto/sha256`, not BLAKE3 — see design doc §2), streamed incrementally via the standard `hash.Hash` interface — never buffer a full upload into memory before hashing.
- **Dedup on SHA-256 hash match**, scoped to `POST /api/pieces` (single-piece upload — returns the existing `Piece` instead of creating a duplicate) and `Book` creation. **Deliberately not** the book-import wizard's confirm step: two sibling pieces split from the same book can legitimately end up byte-identical (e.g. duplicate blank pages), which isn't a duplicate upload to collapse. No DB-level `UNIQUE` on `pieces.file_hash` for this reason (unlike `books.file_hash`, which has one).
- **Hard delete + orphan cleanup**: deleting a `Piece` removes its DB row, its extracted file, and its cached page thumbnails. If it was the last `Piece` referencing a `Book`, the `Book` (record, original file, and its own cached thumbnails) is deleted too. Both logged at INFO (see Logging).
- **`Book` fields are never denormalized onto `Piece`** — Piece Details resolves book-level display live via `sourceBookId → Book`. Don't add a "sync book fields to pieces" step anywhere in application code; the join makes every piece reflect current book data automatically.
- **`Book` is entirely optional** (design doc §3) — a piece with no `Book` at all (single-piece upload, §5) is a normal, first-class case. Don't write code that assumes `sourceBookId` is usually present.
- **File replacement** (§14) hard-replaces the same `Piece` record, not a new piece. `sourceBookId`/`sourcePageStart`/`sourcePageEnd` are kept as historical provenance after a replace — don't clear them, and don't assume they still describe the current file's exact page range.
- **Custom cover / portrait images accept PNG, JPEG, GIF and WebP** (`detectImageContentType`, `internal/handlers/book.go` — sniffed at upload, stored and served exactly as uploaded with that content type, never re-encoded). WebP comes from `golang.org/x/image/webp` (pure Go, decode-only, already a dependency for the Setlist PDF's fonts).
- **Download filename**: `Content-Disposition`'s suggested name is `"<composer/arranger/publisher> - <title> (<yearWritten>).pdf"` (`downloadFilename`, `internal/handlers/filename.go`) — first non-empty of arranger/composer/publisher wins the name segment (arranger first: an arrangement is the arranger's edition), both segments omitted cleanly (including separator) when unset. For a piece, name/year come from `repo.ResolveEffective`, not raw columns, since they're book-inheritable.

## Logging
Use the standard library's **`log/slog`**. Deletions (piece deletion, cascading orphaned-book cleanup) and piece file replacement are logged at **INFO** level, not DEBUG or WARN/ERROR — destructive-but-expected user actions belong in normal production logs, not hidden behind DEBUG or miscategorized as a problem when nothing actually went wrong.

Use structured fields, not string interpolation:
```go
logger.Info("piece deleted", "pieceId", piece.ID, "fileHash", piece.FileHash, "title", piece.Title)
```

## Config
- All global settings are env vars (no settings table in v1, design doc §3), validated at startup — fail fast with a clear message rather than failing later mid-request. **Two deliberate exceptions**: `server_settings` (migration `00024_server_settings.sql`, singleton `id=1` row) — multi-user support's first-time launch flow needs somewhere to persist a choice made through the UI itself (which a plain env var can't hold), not just deploy-time config (see "Multi-user support" below); and, deliberately **not** an extension of `server_settings`/SQLite, **`DATA_DIR/config.yml`** (`internal/libraryconfig`) for Admin Settings' Library Settings card (Backup schedule/retention, Log level, Copyright region) — a plain YAML file at the library's own root, hand-inspectable/backup-able independent of the SQLite DB, merged with env vars at startup (`internal/config.Load`, env always wins and gets written back into the file) and live-mutated at runtime with no restart (see "Multi-user support" below for the live-apply mechanism per field).
- **How env vars get set is entirely a Docker Compose concern, not application code** — a Compose `environment:` block vs. a sibling `.env` file are both natively supported by Compose, and the app reads them the same way either way.
- Backup scheduling uses `robfig/cron` (pure Go, no CGO) to parse `BACKUP_CRON` and drive the daily `VACUUM INTO` snapshot.
- **`CITATION_FORMAT` is loaded and validated but never actually consulted by citation generation** — `buildCitation` (`internal/handlers/citation.go`) hardcodes the format in Go rather than doing token substitution against `Config.CitationFormat`, since blank-field omission (a citation must skip a blank field's surrounding punctuation entirely) doesn't fit a plain-substitution model, and a real conditional-template engine is out of scope. A direct, permanent deviation from design doc §6 — changing this env var currently has no effect.

**Citation format — the full current set of deviations from design doc §6** (`internal/handlers/citation.go`):
- **An arranger renders inline right after the title** (§6 excludes arranger entirely): `{composer}, "{title}", arr. {arranger}, {publisher/ID}, {year}` — the `"arr. {arranger}"` part sits after the quoted title (and its opus parenthetical) and before every identifier part, in both the flat format and Path B's sentence 1 (before "Published..."); nothing else in the line moves (IMSLP, publisher/ID, ISBN, book/opus keep their usual places). There is no separate "Arrangement by…" sentence. Composer and Arranger are both book-inheritable. With an arranger present, the citation's year is `effectiveArrangementYearWritten` (`resolveArrangementYearWritten`, applied via `citationYear`) instead of plain `yearWritten`: the piece-inheritable `YearWritten` field's own fallback chain (piece's own → piece's own `CopyrightYear` → book's `YearPublished`, see Book-level soft inheritance below) with tiers 2 and 3 swapped — book's `YearPublished` takes precedence over the piece's own `CopyrightYear`, since it's a better proxy for when an arrangement was made. Citation-only — doesn't change `YearWritten`'s own resolution or anything exposed on `PieceResponse`.
- IMSLP number renders as `"IMSLP #{number}"` (`stripImslpPrefix` strips any leading "IMSLP" already baked into stored data so it never doubles up), and wins the fallback entirely over publisher/publisherId/ISBN when present — those three are dropped from the citation, not shown alongside it.
- publisherId fuses onto publisher as `"{publisher} #{publisherId}"` (its own `"#"`-prefixed suffix, not a separate comma-joined part); ISBN (Book-only, no piece-level override) gets its own comma-joined `"ISBN {hyphenated}"` part right after publisher/publisherId.
- A double quote inside the title itself renders as a single quote, before the whole title is wrapped in the citation's own double quotes (standard nested-quote convention).
- `yearWritten`, when present, is unconditionally the citation's last component and gets a trailing period.
- **A book's own opus number always renders next to the book's name once set** — `"{bookTitle}, {bookWorkOpusNumber}"`. When the piece's own effective opus number incorporates the book's (per `containsIgnoringSpaces` — true for pure inheritance, or an override like book `"Op. 68"` / piece `"Op. 68, No. 9"`), only the piece's own distinguishing remainder renders, as a bare space-joined prefix directly on the quoted title (`No. 5 "Prélude"`, never in parens, never comma-separated) — a piece with nothing to add beyond the book's own opus gets a fully bare title. Otherwise (no book opus, or a piece opus that doesn't reference the book's at all), the piece's full own opus renders as the title's own `"(...)"` suffix, independently of the book segment.
- A piece with a book and an In Copyright or Copyleft status gets a different two-sentence "written / published" structure (`buildTwoSentenceCitation`) instead of the single flat line — see Public Domain Badge below. Two further rules apply within that structure, independently of each other:
  - **An opus match** (the book's opus contained in the piece's effective one, `resolvedOpus.matched` — "the piece is part of a greater work") folds the book's title/opus into the *first* sentence, the same way the flat citation already does, instead of a separate "Published in {book}..." sentence.
  - **Whichever entity owns the effective IMSLP number** (piece's own non-inherited value, vs. inherited from the book) decides the rest: a piece-owned number renders in the first sentence (right where the flat citation puts it) and the publish sentence is dropped entirely — a piece already pinned to its own IMSLP record doesn't need a second sentence restating facts that record already carries. A book-owned number instead becomes its own segment *inside* the publish sentence, alongside publisher/publisherId rather than replacing them (a deliberate divergence from the flat citation's own dominant-IMSLP-wins rule above, since this sentence is specifically about the book's own publication facts). The publish sentence's wording is `"Published by {publisher/publisherId}[, IMSLP #{n}], {yearPublished}."` when the opus matched (book title already said), or `"Published in {bookTitle}[, {bookWorkOpusNumber}], {publisher/publisherId}[, IMSLP #{n}], {yearPublished}."` otherwise.
- A Public Domain/Likely Public Domain citation ends bare by default — **no trailing note**, one exception: an explicit `publicDomain` pick that actually contradicts what the live calculation would otherwise show (the calculation alone would call the piece In Copyright) keeps a clarifying trailing note (the piece's own `copyrightSlug` if set, else the literal `"Public domain."`). `likelyPublicDomain` never hits this exception, since it's derived from the calculation and can't contradict it.
- **The copyright clause's holder falls back, when Copyright Holder is unset, to the arranger(s) — else the composer(s) — if the effective publisher is "self-published"** (`isSelfPublished`: letters/digits only, case-folded, must equal `selfpublished` — "Self-Published", "self published", "SELF PUBLISHED." all match), otherwise to the effective publisher. An explicitly entered holder always wins. The publisher text itself still renders unchanged in its usual slot.
- The copyright clause's `"Copyright © {year|holder}"` uses a non-breaking space right after `©` (a plain space everywhere else in the clause) — keeps the symbol from ever wrapping onto its own line, separated from whatever it's attributing. None of the above is reflected back into `sonneck-design.md`, which stays as the original planning artifact.

## IMSLP live autofill
Design doc §13 listed this as deferred; built since. `GET /api/imslp/lookup?number=<digits>` → `{composer, workOpusNumber, yearWritten, publisher, publisherId}`, any field blank if that work/file doesn't have it on record (a normal result, not an error — IMSLP is community-maintained and often incomplete). `404` for an unrecognized number, `400` for non-numeric/empty input, `502` (logged at WARN) for a real IMSLP-side failure. Shared `components/ImslpAutofillButton.tsx` (`EditPieceModal.tsx`/`EditBookModal.tsx`/`BookUploadAboutStep.tsx`) — autofill only ever writes to fields **currently blank**, never overwrites something already entered.

Trigger differs by screen, on purpose: `EditPieceModal.tsx`/`EditBookModal.tsx` are manual-click only (a number on record there was already typed/confirmed at some point). `BookUploadAboutStep.tsx` also auto-runs once on mount, since a filename-detected number is already considered confirmed by the time that screen exists — but only after a 700ms delay, so the user sees the blank screen first rather than fields silently already-different the instant it mounts.

The real access mechanism — why a bare IMSLP number needs `Special:ReverseLookup` rather than the human-facing resolver page (which is JS-redirect-gated and can't be followed server-side), and why per-file publisher/publisherId data needs a second, rendered-HTML fetch rather than wikitext — is documented in `internal/imslp`'s own package doc comment and in full in memory `project_imslp_live_autofill.md`. Neither `Special:ReverseLookup`'s redirect shape nor the `we_edition_info` table's HTML structure is a stable, versioned public contract — if autofill starts silently returning blanks, re-verify both with a real fetch against a known-good number before assuming the Go code regressed.

## Public domain badge
Design doc §13's deferred public-domain feature, now built. Four states — `publicDomain`/`copyleft` (explicit, user-picked) and `likelyPublicDomain`/`inCopyright` (computed) — resolved by `repo.ResolveCopyrightStatus` against `internal/copyright` (region-rule term calculation; `COPYRIGHT_REGION` env var, validated at startup against the region table embedded from `internal/copyright/regions.json`).

**Resolution is asymmetric and read-time only, never written back to the DB:** `publicDomain`/`likelyPublicDomain` are sticky — the live calculation never overrides them, since a term can't un-expire. `copyleft`/`inCopyright` are not sticky — the calculation can push either forward to `likelyPublicDomain` (never backward) on every read. `PieceResponse.copyrightStatus` (`CopyrightStatusResponse`) carries both the raw explicit pick (`value`/`inherited`, same shape every other book-inheritable field uses) and the calculation-corrected `effective` value the badge/citation actually display — a distinct type from the plain `EffectiveField` every other field uses, since no other field needs both a stored pick and a separately-computed display value.

`Book.yearWritten` was renamed to `Book.yearPublished` as part of this feature — a full rename (DB column, Go field, API JSON key, frontend field/label). `Piece.yearWritten` itself is untouched and still inherits from the renamed `Book.yearPublished`. The pre-built `pieces.public_domain` bool column (see Database migrations above) was dropped from `models.Piece` entirely, superseded by the real four-state enum. (The Books Library's own sort control — `BooksPage.tsx`/`api/books.ts` — was missed in that rename sweep and silently 400'd on `sort=yearWritten` until caught and fixed separately; grep for a bare `yearWritten` string literal if this class of gap is ever suspected again.)

**US renewal follow-up** (migration 00023) extends the fixed-term calculation for `en-US` specifically: a work published 1923-1963 needed a renewal registration filed during its 28th year to keep protection past that initial 28-year term (95 total once renewed); without one it's public domain today regardless of the region's normal 95-year rule. `Piece.copyrightRenewed`/`Book.copyrightRenewed` (book-inheritable, `*bool` — nil means "not explicitly set," not "confirmed not renewed," same as every other nullable copyright field) feed `internal/copyright.ComputeLikelyPublicDomain`'s `renewed` parameter, consulted only when the effective copyright year falls in `regions.json`'s `renewalWindowStart`/`renewalWindowEnd` (1923/1963) for a `fixed-term` region. A fifth status, **`possiblyPublicDomain`** (own icon `IconShieldQuestion`, neutral color same as `likelyPublicDomain`) — computed-only, never an explicit pick, not in the CHECK constraint or the frontend's status picker — is what `ResolveCopyrightStatus` returns instead of `likelyPublicDomain` specifically when the PD conclusion rests on this *unconfirmed* non-renewal default (`ComputeLikelyPublicDomain`'s `LowConfidence` flag) rather than a genuinely confirmed fact; a *confirmed* renewal whose term has since elapsed still resolves to the ordinary higher-confidence `likelyPublicDomain`. Deliberately a plain boolean, not tri-state — "explicitly marked not renewed" and "never answered" are indistinguishable by design, both treated as the conservative default. `buildCitation`'s `copyrightClause` appends a bare `"(renewed)"` marker (no specific year — the exact filing year never affects the term math) right after the copyright year when set. The Edit Piece/Book modals' renewal toggle only ever shows for `en-US` (exposed to the frontend via `GET /api/config`, `lib/usRenewalWindow.ts`'s shared 1923/1963 constants) with a Copyright Year in that window.

Full design history (region-rule research, badge visual options, every locked decision) is in memory `project_public_domain_badge.md`.

- **`setlists`/`setlist_entries`** (owner-scoped like `user_tags`/`practice_statuses`, `owner_user_id` CASCADE on the owning user). No uniqueness on `piece_id` at all: the same piece can repeat within one setlist (a reprised piece/encore) and belong to any number of different setlists at once, both deliberate.

- **The Table of Contents is drawn in real points, identically in the mockup and the PDF** (`SetlistProgramPageMockup.tsx`'s TOC section; `internal/setlistpdf/toc.go`, whose `toc*` constants are the mockup's values), for a one-page program and one that runs onto a continuation page: 72pt margins on every side; the › joined the way the app joins every key sequence — regular weight, 0.3em each side, lighter than the keys, here the solid fainter ink `#b3a99e` rather than the app's 55% opacity) • duration (m:ss, h:mm:ss from an hour) for a piece, role • duration for a custom entry; Piece titles use a real Libre Baskerville Medium (500) TTF (`assets/fonts/LibreBaskerville-Medium.ttf`, `varLib.instancer` 500 instance of Google's 400–700 variable font, same 2.005 release), registered as its own family (`fontDisplayMedium`). A piece entry's role now reaches the PDF (`Entry.PieceRole`, set by the handler). - **The cover is drawn in real PDF points, identically in the mockup and the PDF.** `SetlistProgramPageMockup.tsx`'s Cover (`pt()`, scaled from the page's own point width via container-query units) and `drawCover` (`internal/setlistpdf/pages.go`, its `cover*` constants) use the same numbers: frames inset 36pt/44pt (the outer one clears a printer's ¼" no-print margin), sizes on Bringhurst's classical scale, Cabin sizes ×1.08 (`cabinOptical`/`CABIN_OPTICAL`, its x-height .490 vs. Libre Baskerville's .530), and three solid print colors on pure white — ink `#1c1815`, faint `#5c5349`, fainter `#b3a99e` (`colorFainter`: frames, rule, ornaments) — never opacity, never theme tokens. `drawCover` lays the cover out as one **optically centered** stack, like the mockup's flex column: centered in the inner frame, then lifted by 4% of the page height (`coverOpticalLift`/`COVER_OPTICAL_LIFT` — the mockup gets it from bottom padding of twice that), since a block centered exactly reads as sitting low; the optical-center rule fits a single compact cluster in a symmetric frame, unlike a book page's unequal-margin canon or a title page anchored on a proportional line, both compared and rejected: each block's height is measured first (`richTextHeight` for the description; `wrapRichParagraph` is the line-breaking both it and `drawRichText` share), baselines placed with each font's real hhea ascent/descent (`baselineIn`), and an absent date drops out with its gap, and an absent description takes the rule above it along. **Text is kerned and tracked like the browser's** (`internal/setlistpdf/kerning.go`): fpdf neither kerns nor letter-spaces, so kerning pairs are read from each embedded font's GPOS table via `golang.org/x/image/font/sfnt` (all four fonts keep their kerning there, none in a legacy `kern` table — which is why fpdf-family alternatives like gopdf, whose kerning only reads `kern`, wouldn't help) and text is placed one character at a time: fpdf's own glyph width + the pair's kerning + tracking between characters. `kernedWidth`/`kernedLines` (measuring, wrapping) and `drawKerned` share that one walk, so wraps always agree with what's drawn — with both kerning and the 0.02em tracking in, the cover description breaks on the same words as the mockup. The rich-text renderer (`drawRichText`, cover description and Program Page notes) uses it too, and positions by baseline rather than fpdf cells, so it no longer carries fpdf's default ~2.8pt cell margin. Known cost: per-character placement means text copied out of the PDF can pick up stray spaces where tracking is wide (the tracked cover date copies as "OC TO BE R"); ligatures aren't formed (browsers skip them on letter-spaced text anyway). It also falls back per character, the way the browser walks a font stack: a character the requested font lacks (♭/♯/♮ in a literal title or key name — neither text font has them) is drawn in Bravura Text instead (`fontFor`), so a setlist named "Sonatas in B♭" doesn't print a missing-glyph box. Every generated page (cover, TOC, Generated Program Page, colophon) is drawn entirely through it — none uses fpdf's own text cells. The ornament is the **Garamond fleuron** (a public-domain design, credited in the README's Acknowledgements), upright above the date and rotated 180° below the description. The SVG is one `fill-rule="evenodd"` path in `currentColor` (no strokes, transforms or embedded images), `viewBox="0 0 99.55 100"` — nearly square, so it's sized by height (`GARAMOND_FLEURON_ASPECT`/`fleuronWidth`). Usage notes for reusing it (CONTRIBUTING.md's "Setlist PDF fleuron" section carries the same list): it's decorative — inline, give it `aria-hidden="true"` and `focusable="false"`; as an `<img>`, `alt=""`. As a border (its original use) it repeats cleanly edge to edge at a pitch equal to its rendered width; a small negative gap tightens it the way the metal type set. Inline with text it looks best at about 1–1.2× the text's cap height, with `vertical-align: middle` or a slight negative offset. The frontend (`lib/garamondFleuron.ts`, `?raw`) and the PDF (`internal/setlistpdf/fleuron.go`, `go:embed`) each read their own byte-identical copy of the SVG — neither build can reach the other's tree — and `TestFleuronMatchesFrontendCopy` fails if they drift: change the frontend file, then copy it over `internal/setlistpdf/assets/garamond-fleuron.svg`. `fleuron.go` parses only the absolute `M`/`C`/`Z` commands that file uses (anything else is an error, not a silent misdraw) and fills even-odd. Libre Baskerville 700 is self-hosted (`index.css`) for the mockup's cover title, matching the PDF's embedded `LibreBaskerville-Bold.ttf`. Setlist Details' Download Set PDF split button goes through `components/DownloadLink` (home-screen hand-off included) and is `download`-permission gated like Piece Details'.
- **The Generated Program Page** (a custom entry's stand-in page — `drawProgramPage`, `internal/setlistpdf/pages.go`, its `program*` constants; the mockup's Generated Program Page) is an unframed interleaf in the cover's print colors and type, optically centered like the cover (lifted 4% of the page height) between 72pt margins in a 288pt column: a small diamond (a 6pt square turned 45°, fainter ink), the role in small caps (Cabin 11pt ×1.08, 0.10em), the name in Libre Baskerville italic 24pt (italic, as custom entries are in the TOC), then — only with notes — the 24pt rule and the notes (Markdown + shortcodes, Cabin 12pt ×1.08, 1.4 leading), and last the duration in the role's small caps. Each part drops out with its gap when absent. A custom entry is still exactly one page (`ComputeLayout`): notes too long to fit start at the top margin and run past the bottom one — nothing continues them onto another page yet. **The mockup's small-caps lines set `lineHeight: 'normal'` explicitly**: Tailwind's base styles give the page `line-height: 1.5`, while the PDF (and the design canvas, which has no Tailwind) use the font's own line height (Cabin 1.215×) — inherited, the mockup's labels sat ~2pt off the PDF's. Same fix on the cover's date line.
- **The colophon** (`drawColophon`, its `colophon*` constants; the mockup's Colophon) sits at the foot of the last page, where a book's colophon traditionally goes, not optically centered like the other generated pages: "Set in Libre Baskerville and Cabin." / "Generated {date}." in Libre Baskerville italic 10pt (1.5 leading, faint ink), the 24pt rule, then the 24pt-tall S mark (`sonneck-s-mark.png`, already in the faint ink) resting on the 72pt bottom margin, 14pt between each.
- **"Download Set PDF" is real** (`GET /api/setlists/{id}/pdf`, `internal/setlistpdf`) — merges a generated cover page, a paginating table of contents, each program entry (a piece's own real PDF pages spliced in at their own original page size, or a generated stand-in page for a custom entry), and a colophon into one downloadable PDF. Visual design lives in the permanent reference mockup `routes/SetlistProgramPageMockup.tsx` (`/mockup/setlist-program-page`), not in this section. Two-permission gate (`Read` then `Download`), matching `handleDownloadPieceFile`. **Dates are written in the reader's locale**: the handler reads the download request's `Accept-Language` (sent by the browser on both a plain download and the home-screen blob fetch) and formats the gig date (cover, TOC) and the colophon's "Generated" date as a long date via `github.com/goodsign/monday` (`longDateFormatter`, `internal/handlers/localedate.go`, matched with `golang.org/x/text/language` over monday's 45 locales, US English first as the fallback) — the same written-out form the app's own `toLocaleDateString` gives. A layout that zero-pads the day ("04 de outubro") has the pad stripped, since the browser never pads; a result with any character the PDF's fonts can't draw (`setlistpdf.CanDraw` — Japanese, Russian…) falls back to US English. The gig date is parsed and formatted as a plain calendar day, no timezone. Font assets are real Google Fonts TTFs checked into `internal/setlistpdf/assets/fonts/` (the web app's own woff2s can't be embedded in a PDF) — Libre Baskerville/Cabin, the same families already self-hosted for the UI. **Merging is done via poppler's `pdfunite`** (`internal/pdf.Merge`, added alongside `PageCount`/`ExtractPages`/`RenderThumbnail`), not a pure-Go PDF-import library — an earlier version used `codeberg.org/go-pdf/fpdf/contrib/gofpdi` to import a piece's pages directly, and that panicked on a perfectly ordinary real-world file (a plain macOS-Quartz-produced PDF, no exotic structure) — gofpdi's own object parser has a real robustness gap its own minimal test fixtures never exercised. `pdfunite` is part of poppler-utils, which this app already depends on and bundles across every distribution channel (Docker image, native macOS/Windows builds), so fixing this added no new dependency at all — the four generated page types are drawn via `fpdf` (kept, MIT, still needed for drawing) into small temp-file PDF chunks, and a piece entry's real file is referenced by its path directly; the ordered chunk-and-piece-file list is concatenated by `pdfunite` into the final output. Region-inferred page shape (`Letter` for `en-US`/`ca`, `A4` for `eu-generic`/`en-GB`, via `s.Cfg.CopyrightRegion()`) applies only to the four generated pages — an imported piece's own page keeps its own original size untouched.
- **A setlist's/custom entry's own `description`/`customNotes` field renders real Markdown + `:shortcode:` symbols in the PDF, not literal source text** (`internal/setlistpdf/richtext.go`) — a hand-rolled two-pass inline parser (no full CommonMark, no Go markdown dependency added), scoped to exactly what these two fields realistically use: paragraphs, a single `\n` as a forced line break, `**bold**`, `*italic*`/`_italic_`, and `musicEmoji.ts`'s own `:shortcode:` set (ported by hand into `musicShortcodes`, kept in sync manually — no shared source of truth between the Go and TS sides). A real second Bravura Text TTF subset (`assets/fonts/BravuraText-subset.ttf`) was re-subsetted fresh from Steinberg's own authoritative `BravuraText.otf` release (not converted from the already-woff2-packaged web asset) at the identical 26 codepoints the web `@font-face` already documents, then converted CFF→TrueType via `fonttools`'s `cu2qu`/`otf2ttf` pipeline — Bravura ships no `.ttf` anywhere upstream (confirmed against its 3 most recent GitHub releases), and `fpdf`'s TTF parser requires real `glyf`/`loca` outlines, not CFF. **Emphasis is resolved before shortcodes, not in one combined pass** — a `:shortcode:` commonly sits *inside* an emphasis span in real descriptions (found live: a real setlist's own `*subito :pp:*` swallowed the nested shortcode as literal text under a naive single-pass scan) — `richEmphasis` matches first, then each resulting plain/emphasis segment is independently re-scanned for shortcodes via `richShortcode`. **`ambientItalic` reproduces index.css's own `.italic em { font-style: normal }` rule exactly** (CLAUDE.md > Frontend's standing gotcha log) — the cover description's base style is itself italic, so a `*marked*` span inverts to roman instead of double-italicizing, while `**bold**` keeps the ambient's own italic state and adds weight on top (needing a real `Cabin-BoldItalic.ttf`, sourced the same way as every other font weight this package uses); a custom entry's own description has no italic ambient, so the same code path renders emphasis italic as normal. A `:shortcode:` symbol never inherits ambient italic/bold at all, matching the web's own `not-italic` wrapper span. Tokens split across a style or shortcode boundary with no whitespace between them in the source (`*subito :pp:*.`, `*emphasis*,`, `B:flat:`) are marked `glued`: drawn with no space before them and wrapped as one unit with the word they touch — otherwise every boundary would render as a stray space (`pp .`).

## Operational basics
- `/healthz` endpoint, used by the Docker healthcheck.
- Backup: daily `VACUUM INTO` snapshot of the SQLite DB. Restore: stop container → replace the DB file → restart. Documented in the README, not just implied.
- **Logs** (`internal/applog`): every log line written to stdout is also written to `DATA_DIR/logs/sonneck-YYYY-MM-DD.log` (one file per day, via a hand-rolled `io.Writer` in the `slog.NewJSONHandler`'s `io.MultiWriter` — no rotation library, matching this project's minimal-dependency posture). `logs/` is a fixed sibling of `db/`/`backups/`/`cache/`/`library/` under `DATA_DIR`, with no env-var override (unlike `BackupDir`/`BACKUP_DIR`) and no new Admin Settings field — retention deliberately reuses `BackupRetentionDays` rather than getting its own setting. Pruning is a straight port of `backup.Prune`'s own logic (flat directory scan, `ModTime()` vs. a `retentionDays`-ago cutoff, `os.Remove` — not filename date parsing) and runs inside `backup.Scheduler`'s existing daily job, right after backup pruning, so log retention rides the same cron firing with zero new scheduling code.

## Search
SQLite FTS5, not a separate search engine like Bleve (design doc §2's own reasoning — StashApp's approach was the starting inspiration; FTS5 achieves the same goal with less operational overhead at this project's scale).

- `pieces_fts` is denormalized, one row per `Piece` — **book-inheritable fields are indexed by their effective value**, not the raw `Piece` column, or search would miss pieces that only inherit a value from their book.
- **Sync is application-level** — an explicit `repo.ResyncSearchIndex(pieceId)` call after any `Piece` or tag-assignment mutation, in the same transaction as the mutation itself. Not SQL triggers: logic spread across `Piece` and several tag join tables is harder to discover and test than one function called from application code. Editing a `Book` field must resync every affected `Piece`, not just call this once.
- The index is derived data, safely droppable/rebuildable from `Piece`/tag tables at any time — via the `rebuild-search-index` CLI, or automatically: `cmd/sonneck/main.go`'s startup path runs a cheap row-count mismatch check and self-heals if the index is out of sync (the same "detect and auto-fix on boot, keep the manual CLI as a fallback" pattern `migrate-people`'s own backfill uses, both best-effort/non-fatal so a failure doesn't block startup).
- **Query matching is three tiers, each engaged only when the previous finds nothing**: prefix (`pieces_fts` phrase-prefix syntax) → trigram substring (`pieces_fts_trigram`, `tokenize='trigram'`) → real typo-tolerant fuzzy (`internal/fuzzy`'s Damerau-Levenshtein/Optimal-String-Alignment distance, exposed as a genuine SQLite scalar function via `modernc.org/sqlite`'s `RegisterDeterministicScalarFunction` — no CGO, no separate driver, and confirmed to work fine with `WHERE`/`ORDER BY`/`LIMIT`/`OFFSET` against a real registered function, so it needed no pagination-architecture change). Never merged — the common case (prefix already matches) never pays for the fallback tiers' cost. **Facet counts** (`GET /api/pieces/facets`/`GET /api/books/facets`) deliberately only replicate the prefix tier of this — recomputing all three tiers for up to 8 sidebar dimensions per request wasn't worth it, so a query that only trigram/fuzzy resolves can show facet counts that don't quite match the actual result list in that one case.
- **"&" and "and" are interchangeable in search, both directions** — `repo.NormalizeAmpersand` (FTS5 paths, space-padded) and `repo.NormalizeAmpersandForLike` (Books/People's plain `LIKE '%term%'`, bare replace — the two backends need different spacing rules), applied at both index and query time.
- **Admin/maintenance actions that predate real per-request auth are CLI subcommands on the same binary, gated by shell/`docker exec` access instead — not HTTP endpoints an unauthenticated request could hit.** Existing instances: `rebuild-search-index`, `regenerate-thumbnails`, `export-csv`, `cleanup-thumbnails`, `migrate-people`, `reset-password` (multi-user support — clears the singlepass admin's password hash, a lockout recovery path; see Multi-user support). Real per-endpoint `admin`-permission gating now exists (Multi-user support, Phase 10) for anything reachable over HTTP, so a *new* maintenance action doesn't strictly need to be CLI-only anymore the way these six did when they were built — but `link-oidc-account` (Phase 14, 7th instance) continues the CLI pattern regardless, for cases (like this one) that are fundamentally about recovering/pre-provisioning access when the normal in-app path can't be used. A command that writes to the SQLite file while the server may still be running relies on WAL mode for safety, the one deliberate exception to "single writer" (Concurrency).
- Multi-select filters (`keyId`/`sheetTypeId`/`instrumentId`/`userTagId`/`practiceStatus` on pieces, `sheetTypeId`/`instrumentId` on books) take comma-separated IDs, OR-matched. Each has an `exclude*` sibling param (`excludeKeyId`, `excludeSheetTypeId`, …) — the Filter Drawer's segmented exclude/neutral/include control, one param per direction rather than a signed value. An include clause and its exclude sibling share one `namedClause.name` so a facet's own live count skips both together (never self-narrowing, in either direction). `favorite`/`bookless`/`hasImslpNumber` are plain tri-state booleans (`true`/`false`/absent = include/exclude/neutral) — no separate exclude param needed for those. A negated clause goes through `negateClause` (`NOT COALESCE((...), 0)`), not a bare `NOT (...)` — an inheritance-aware "own value, else the book's" fragment can evaluate to SQL `NULL` rather than `FALSE` when the column is genuinely unset with no book fallback either, and a bare `NOT NULL` is still `NULL` (silently excluded from a `WHERE`), wrongly dropping a row that plainly doesn't carry the excluded value from an *exclude* result. Facet counts are live/faceted, not static — each value's count reflects every *other* currently active filter, never narrowing against its own selection. Title sort ignores a leading "A"/"An"/"The" (library-catalog convention), computed in SQL rather than a stored sort-name column. `practiceStatusSlot` is a separate, single-value, non-comma-separated param used only by the sidebar's three fixed views — see Multi-user support's own "Practice Status is rename-proof" bullet for why this exists alongside the name-based `practiceStatus`/`excludePracticeStatus` pair.
- **`sort=yearWritten`/`sort=yearPublished` ignore a texty prefix** ("ca. 1708-1711" sorts as 1708, not last) — `leading_year(...)` (`internal/yearparse`), a second registered SQLite scalar function alongside `fuzzydist` (same `RegisterDeterministicScalarFunction` mechanism, `internal/db/db.go`), finds the first run of digits anywhere in the string rather than requiring the field to already start with one. Two independent implementations of the identical rule, kept deliberately in sync rather than shared: this SQL-level one (`pieceSortColumns`/`bookSortColumns`, `internal/handlers/search.go`/`book.go`) and Person Details' own client-side `workYearSortKey` (`PersonDetailsPage.tsx`, a plain `/\d+/` match — that page fetches its whole unpaginated works list and sorts it itself rather than going through a `sort=` param, so there's no SQL involved there at all).

Full build detail (the fuzzy-tier algorithm survey, the trigram/book_title/ampersand migrations and their own backfill requirements, the facet-narrowing math) is in memory `project_fuzzy_search_research.md`, `project_search_book_title.md`, and `project_search_ampersand_and.md`. The exclude/neutral/include tri-state filter build (API contract, the `negateClause` NULL-safety bug and fix, verification method) is in memory `project_tristate_filter_build.md`.

| Concern | Choice |
|---|---|
| Language | TypeScript — types mirror the backend's `{data}`/`{error}` contract |
| Data fetching | TanStack Query for all API calls, not ad-hoc `useEffect`/`useState` |
| Forms | react-hook-form, **light** client-side validation only (required fields, plausible ranges) — the backend stays sole authority; don't maintain a mirrored validation schema |
| Styling | Tailwind CSS, palette/type/spacing as theme tokens |
| Routing | React Router — wizard steps are real routes |
| Icons | Tabler Icons (`@tabler/icons-react`, the scoped package) — import by name, never `import *` |
| Typography | `--font-display`/`--font-sans`/`--font-music` all self-hosted (SIL OFL 1.1, files in `frontend/src/assets/fonts/`), never loaded from Google's CDN at runtime |

- **Shell scope:** build the sidebar nav/route shell to accommodate all planned features early — scaffold-and-hide a not-yet-built feature (route/component exists, reachable, visually present even if stubbed) rather than omitting it as if undecided.
- **Mockup-first, both directions, is a standing rule** (memory `feedback_mockup_first_standing_rule.md`): a genuinely new visual/UX design goes to its `/mockup/*` counterpart first for approval before touching the real page; once any change lands in a real page that has a mockup counterpart — new interaction, added affordance, copy/behavior fix, not just a redesign — the same change gets ported into the mockup in the same pass by default. Mockups deliberately don't import real components (they're a frozen, hand-maintained visual reference) — the one exception is pure presentational data/logic with no markup of its own (e.g. `lib/formatPieceMeta.ts`, `lib/copyrightBadge.ts`), which *is* shared.
- **Light/dark theme**: every color is an `@theme` token in `index.css`, and the dark theme (Walnut, lifted: palette A3, picked from a side-by-side after A6 and A5, both darker, were tried in the app and found too dark) is the same tokens redefined in one `:root[data-theme='dark']` block right after `@theme` — Tailwind's utilities read the tokens as CSS variables, so components never use `dark:` variants. A new color token needs both a light value (with its description comment) and a dark one. `<html data-theme>` is set from the user's saved choice (`user_settings.theme_preference`: light/dark/system) by `lib/theme.ts`'s `useThemeSync` in `AppShell`, which also follows the device while the choice is "system" and recolors the browser bar (`<meta name="theme-color">`). The choice is cached in `localStorage` (`sonneck-theme`) so an inline script in `index.html` sets the theme before the first paint — no light flash, and the login/first-launch screens (outside `AppShell`) get it too; that script mirrors `resolveTheme` and the two bar colors, keep them in step (`cmd/sonneck-desktop/theme.go` carries the same two colors, see Native app). Overlays that must stay dark in both themes (window backdrops, controls over page thumbnails, count badges) use `bg-scrim/NN`, never `bg-ink/NN` — ink turns light in the dark theme. Tooltips, toasts and floating action bars stay dark too: `bg-scrim` with `text-white` (`InfoTooltip`'s bubble, Piece Details' "Copied" toast, the split step's selection bar); a dark label on a light fixed fill uses `text-scrim`, not `text-ink`. A status chip like Setlist Details' "Archived" stays `bg-ink text-paper` on purpose and inverts with the theme, matching the title beside it. Status greens use `--color-grass` (the public-domain/copyleft shields, Admin's up-to-date check), lightened slightly in the dark theme. The upload wizard's ten book-split colors are tokens too (`--color-split-1`…`10`, `lib/pieceSplitLogic.ts`'s `PALETTE` holds `var()` references to them), brightened in the dark theme to an even 5.5:1 against the dark page; a faint version is `color-mix(in srgb, <color> N%, transparent)`, never a hex alpha suffix (`${color}1a`), which a CSS variable can't take. The split step's lane and piece-chip tints take their strength from `--split-tint` (`index.css`: 10%, 20% in the dark theme, where 10% barely shows), and a skipped page's tile its opacity from `--skip-fade` (0.6, 0.15 in the dark theme): a white page faded by opacity sinks into a light background but turns a prominent mid-grey on a dark one, so any "fade this out" opacity over a white page needs a darker-theme value of its own. **Shadows are theme-aware too**: `@theme`'s `--shadow`/`--shadow-sm`…`-2xl` keep Tailwind's shapes but take their color from `--shadow-tint-*` (a plain `:root` block, black 10%/25% as Tailwind ships them; the dark block's near-black scrim at 45–70%, picked from a side-by-side over a lit top edge and a dark outline). Tailwind copies a shadow's value into its utility at build time, so overriding `--shadow-lg` itself in the dark block does nothing; change a tint, and use the plain `shadow-*` utilities, never a `shadow-black/NN` or arbitrary shadow. Person avatars and Person Details' book-credit circles use the same `PALETTE`, so they brighten too; their initials and icons stay white in both themes. Sheet-music thumbnails and the Setlist PDF preview stay white: they show real pages — unless the user turns on **Dark Mode Scores** (User Settings › Appearance, `user_settings.dark_mode_scores`, per account, off by default): `lib/theme.ts`'s `useDarkScoresSync` sets `<html data-dark-scores>` (cached in `localStorage` like the theme, set by the same inline `index.html` script), and `index.css` gives every image with the `score-page` class `filter: invert(0.9) hue-rotate(180deg)`, only while the theme is dark. Every sheet-music page image carries `score-page` (library cards, Book/Person Details, Piece Details and its enlarged view, Edit Piece, the upload steps) — tag any new one; book covers, portraits and the Setlist PDF preview never do. `/mockup/style-sampler` has a Light/Dark preview switch and lists every token's dark value.
- **Solid fills use the `-fill` tokens, never `bg-accent`/`bg-danger`**: a filled green control (primary buttons, an on switch, progress bars) is `bg-accent-fill` (hover `bg-accent-fill/90`), a filled red one `bg-danger-fill` (hover `bg-danger-fill-strong`). In the light theme they're the same colors as `accent`/`danger`; in the dark theme `accent` and `danger` turn light for text, outlines and tints, while the fills stay deep and keep their white labels. Faint tints (`bg-accent/15`, `/20`) stay on `accent`. **Step indicators** (the book upload wizard's and first launch's step bars) are the exception: they carry no label, so the current step is `bg-accent` and completed steps `bg-accent-muted` — in light that's the deep green over a lighter one, and in dark it flips to bright over deep, so the current step is always the one farthest from the page. **Hover and selected fills on a raised surface** (menu and search-result rows, sort and filter buttons, the filter drawer's selected "/", segmented-control hovers) use `bg-paper-hover`, never `bg-paper-sunken`: the same grey in light, but in the dark theme sunken is a deep well (ΔL* −9.4 against `paper-raised`), so `paper-hover` lifts lighter instead (#3b342e, +4.7), picked from a side-by-side of four. **The sidebar's hovers use `bg-sidebar-hover` on the dark rail (nav items, Upcoming Sets rows, the mobile top bar's buttons) and `bg-sidebar-menu-hover` inside its menus (account menu, Upcoming Sets' ⋯), never a `white/5`-style tint**, which mixes in plain white and reads as cool grey beside the warm selected-item brown; both picked from a side-by-side. The small icon circle on a card (First Launch's security choices, Auth Change's admin cards, Admin's user rows, the Upload page's and Drop to Upload's choice tiles) uses `paper-hover` too, picked from a side-by-side, so it doesn't turn into a near-black disc in dark. `paper-sunken` stays for resting wells: thumbnail boxes, tracks, zebra rows, the credit chips. **Disabled solid-green buttons fade to `disabled:opacity-50`, one value app-wide** (was 40/50/60; 40% nearly vanished in dark). **Green pills** (practice status, Your Tags, Piece Details' pills, active filter chips, Admin's status pills) are `border border-accent/30 bg-accent-soft text-accent` — the thin border keeps the edge when a pill sits on a white page scan (the grid card's practice-status badge, which has no fade behind it); a red "Not …" filter chip matches with `border-danger/30`.
- **Checkboxes and radios go through `components/Checkbox.tsx` / `components/Radio.tsx`, never a bare `<input type="checkbox">` or `<input type="radio">`**: `Checkbox` is a real, invisible checkbox over a drawn 16px box (`ink-faint` outline; checked is solid `accent-fill` with a white check), so it looks the same in every browser and both themes; `CheckboxMark` is the box alone, for a row that is itself the control (the Add to Setlist picker's rows are buttons). Picked from a side-by-side of the native checkbox and two drawn sizes. A native one tinted `accent-accent` turns pale sage in the dark theme and its empty box can't be styled. Radios likewise go through `components/Radio.tsx` (same build; selected is a solid `accent-fill` circle with a white center, the radio version of a checked box, picked from a side-by-side). **Sliders go through `components/Slider.tsx`**, never a bare `<input type="range">`: a real range input drawn by `index.css`'s `.slider` (a range's track and knob are per-engine pseudo-elements, so plain CSS rather than utilities) — a 6px track, `accent-fill` up to the knob and `border` beyond (the switch's on and off colors, the fill share passed in as `--slider-fill`), and an 18px white knob ringed 3px in `accent-fill`, since a plain white knob vanished on a white window; picked from two side-by-sides. Upload Portrait's Zoom is the only one today. Mockups use the same components.
- **Confirmations and error messages use the app's own dialog, never `window.confirm()`/`alert()`/`prompt()`** (`lib/dialogs.ts`, shown by `components/DialogHost.tsx`, mounted once in `main.tsx`): the browser's own ignore the theme, and the Mac desktop app's web view can't show them at all — `confirm()` silently answers no, so every Delete did nothing there. `await confirmAction({ title, message, confirmLabel })` resolves true only on the action button (Cancel, Escape and the backdrop resolve false); the title is the question (`Delete "X"?`), the message the consequence, and the button names the action ("Delete book", never "OK"); red by default (`destructive: false` for a green one). `showAlert(message, title?)` is fire-and-forget with one OK. Cancel/OK takes focus, so Enter never confirms a delete. Picked from a side-by-side (the plain window, same shape as the Archive/Duplicate confirmations); a reversible action with its own form keeps its own `Modal`.
- **Every "done" screen uses the same icon**: a plain `IconCheck` (no circle) at 48px in `text-ink-soft` — Auth Change's "All set", First Launch's "You're all set", and the piece and book upload success screens, real and mockup alike. Neutral, not accent: it reports that something finished rather than competing with the buttons below it.
- **Destructive and excluding UI uses the `danger` tokens, never Tailwind's `red-*` palette**: `--color-danger` (red text, solid delete buttons, error lines, the "Not …" filter state), `--color-danger-soft` (the pale fill behind them: exclude chips, delete-button hovers, the Auth Change Flow's accounts-to-delete list), `--color-danger-border` (a danger-soft box's outline) and `--color-danger-strong` (the hover: solid red buttons and red text links darken to it). Chosen from a side-by-side comparison (warm red family over Tailwind's cooler `red-50`); one family, so a dark theme can override it in one place. An available update ("version X available", Admin Settings' Version row) is news, not a warning, and uses `accent-soft`/`accent`.
- **Every new `/mockup/*` page gets a row in `routes/MockupIndexPage.tsx`** (name + one-line note) in the same pass as its route in `App.tsx` — the index is how mockups are found. **`/mockup/states`** (`routes/StatesMockup.tsx`) gathers every empty, error and loading state on one page behind an Empty / Error / Loading switch and a Light / Dark switch; when one of those states changes in a real page, update its copy there too.
- **Failed loads don't retry a 4xx** (`main.tsx`'s `QueryClient` `retry`): a not-found, invalid or not-allowed answer won't change on a retry, so it shows at once; network failures and 5xx still get TanStack's three retries. (Without this, a link to a deleted piece sat on "Loading…" ~7s before "not found".)
- **When the server doesn't answer at start-up** (`AuthGate`, `App.tsx`: the sign-in check fails with anything but a 401), `components/ServerUnreachable.tsx` shows "Can't reach Sonneck" and retries by itself after 5, 10, 20, 30 and 30 seconds with a countdown ("Try now", or pull down, skips the wait), then stops on a "check that it's running" message with a green Try again (design D falling back to B, picked from a side-by-side). Each try first calls `getConfig()` directly and only on success refetches the `config` and `auth/me` queries — refetching a query that has never succeeded puts it back to loading, which swapped the screen for the blank start-up one and reset its countdown on every try. Copies of both states are on `/mockup/states`.
- **Switches are `components/Toggle.tsx`**, never a hand-built `role="switch"` button; where the visible label sits elsewhere in the row, pass a screen-reader-only label (`<span className="sr-only">…</span>`).
- **`/mockup/style-sampler` is the one mockup that is never hand-maintained** (`routes/StyleSamplerMockup.tsx`, `lib/styleSampler.ts`): a reference of the current visual style, for prototyping dark mode. It reads `index.css` (`?raw`) for the color tokens, font stacks and self-hosted cuts, and loads the app's own source on demand (`import.meta.glob` with `?raw`, mockups excluded — its own chunks, fetched only on that page) to count where each color is used, list hard-coded colors, and collect every type style and button/field class set; the shared field components it shows are the real ones. Only its example window is hand-built, from the tokens. **The comment directly above a `--color-*` token in `@theme` is that token's description there** — keep one, current-state, when adding or changing a color. Its usage counts only see a token whose full name appears in the source (`bg-split-1`, `var(--color-split-1)`), so write token names out rather than building them at runtime (`` `var(--color-split-${i})` `` reads as unused).
- **Wizard draft persistence**: `localStorage`, keyed by `bookId`, storing split points + in-progress field values — restore on return to an in-progress import, clear on confirm or explicit cancel.
- **Mobile scope**: the import wizard needs deliberate touch-friendly interaction design for the split-marking step specifically, not just responsive CSS carried over from a desktop layout.
- **Computed fields — deviation from design doc §3**: `Piece.duration` is a plain, directly user-entered field (not auto-recomputed from `bpm`/`measureCount`/`beatsPerMeasure` on every write, contrary to §3's original intent) — a manual "Calculate" convenience button fills it in once from the same formula, but nothing re-applies it server-side after that; the three tempo fields are now purely informational/calculator inputs.
- **`tsc --noEmit -p .` is a silent no-op** — `frontend/tsconfig.json` is a solution-style config (`{ files: [], references: [...] }`) with nothing for the type-checker to actually check. Always run `tsc --noEmit -p tsconfig.app.json`.
- Piece/Book descriptions and a piece's own notes support Markdown (`react-markdown` + `remark-breaks`, through a shared `MarkdownText.tsx` — every field that renders one of these three goes through it) plus a small set of `:shortcode:` music symbols rendered via a self-hosted Bravura Text subset — see `CONTRIBUTING.md`'s own "Music symbol shortcodes" section for the shortcode-map source of truth and how to regenerate the font subset/preview images if either changes. **Both Bravura subsets (web woff2, PDF TTF) are deliberately not upstream-identical**: upstream Bravura has zero side bearings and left-overhanging dynamics, which crowd inline text ("E♭"), so `frontend/scripts/pad-bravura-subset.py` pads every glyph to 0.08em per side (value picked from a side-by-side comparison) — a re-subset must be re-padded. **Bravura Text is second in every font stack** (`--font-display`/`--font-sans`, not just `--font-music`): neither Cabin nor Libre Baskerville has ♭/♯/♮ or any other music glyph, so without it a key name in a pill or a title like "Sonata in B♭" would take its flat from a random system font; the `@font-face`'s `unicode-range` keeps Bravura to just those codepoints. The Setlist PDF does the same per character (`fontFor`, `internal/setlistpdf/kerning.go`).
- **No AI-generated visual assets** — logo/brand/icon work stays hand-authored SVG, never sourced from an image generator. Most such tools' Terms of Service don't permit releasing the output under an open-source license, which conflicts with Sonneck being open-source.
- **Design philosophy: clarity and low visual clutter is the real driver, not formal accessibility compliance for its own sake** — WCAG auditing, comprehensive ARIA coverage, and screen-reader testing are explicitly tertiary for this project. Default to the calmer/simpler option when a design decision has one; when an accessible pattern is also just the better component regardless (a real combobox over a bare `<input>`+dropdown), use it, since that's not extra compliance work. Don't take on accessibility-only work with no general-UX upside beyond what's already a standing rule elsewhere (dropdown keyboard nav below). One cheap habit to keep regardless: never rely on color alone to distinguish tags/keys/states — pair it with text or shape. Applies equally to `/mockup/*` screens and to any Artifact built to support this project, not just shipped app code.
- **The sidebar and the phone drawer scroll as one unit, between two pinned ends**: the top row (collapse button / close ✕, plus the Mac title-bar band) and the account card at the bottom stay put; everything between — nav and Upcoming Sets — sits in one `overflow-y-auto` column, with no inner scroll area of its own. Mockups (`SidebarSetlistsMockup.tsx`, `MobileNavDrawerMockup.tsx`) match. `UserMenuButton`'s menu is portaled to `<body>` and `fixed`-positioned from the card's rect (re-measured on scroll/resize, `z-[60]` over the drawer): the collapsed rail is far narrower than the 240px menu, and the drawer's slide-in `transform` would capture a plain `fixed` child.
- **Sidebar type** (`Sidebar.tsx`, `MobileNav.tsx`, `SidebarSetlists.tsx` and their mockups): nav items are serif `text-base font-medium`, with nav icons at 24px, matching `text-base`'s 24px line height (an icon tracks its label's line height, not its font size); the account name in the card at the bottom is the sans at `text-base`, sized independently of the nav. The Upcoming Sets rows step down to serif `text-sm font-medium` — same typeface, one size smaller — so the list of your setlists reads as secondary to the fixed destinations above it while setlist names stay serif like they are everywhere else (the collapsed rail's setlist letter circles stay `text-base`, matching the rail's nav). Picked from a comparison of six ways to set the list apart (sans list, sans nav, italic, two-line rows, date leaf). Chosen from a side-by-side of the old 15.2px, `text-base` and `text-sm`.
- **Headings, the sidebar's own nav text and every serif button carry `font-medium` (500) minimum weight app-wide, never the unstyled default 400 regular** (a serif button is any `font-display` control with button styling: modal footers, toolbar buttons, wizard buttons, links styled as buttons) — a serif heading at regular weight reads thin next to the sans-serif UI chrome around it. Applies to real pages and their `/mockup/*` counterparts alike; an *italic* font-display span isn't bumped by this rule — it stays the regular 400 italic unless a design deliberately calls for the real 500 italic cut (Piece Details' Source Book card title), and never goes heavier, since there's no bold italic file and the browser would synthesize one. The serif ships 400, 500 and 700 (plus 400 and 500 italic) — **never `font-semibold` on `font-display`**: there's no 600 file, so the browser silently renders the 700 one; write `font-bold` when bold is meant.

**Standing CSS/React gotchas** (full detail and more instances in memory `frontend_design_system.md` — check there for current truth on any CSS/React gotcha before re-deriving one):
- A plain `<button>` needs `cursor-pointer` added explicitly — Tailwind's preflight resets it to `cursor: default`, unlike `<a>`, which gets `pointer` natively.
- **A disabled button always shows the not-allowed cursor and never its hover look, with no per-button classes**: an unlayered `button:disabled` rule at the end of `index.css` (unlayered CSS beats Tailwind's layered utilities, so it wins over `cursor-pointer`), and `index.css`'s `@custom-variant hover` redefines Tailwind's `hover:` as `:hover:not(:disabled)` (`group-hover:` follows). So write no `disabled:cursor-*` class, and never `disabled:pointer-events-none` — it hides the cursor and the button's `title`, and lets a click fall through to a surrounding card link.
- Icon colors are always solid, never a translucent opacity utility — many Tabler icons render as several overlapping `<path>`s sharing one stroke color, and a translucent color re-blends unevenly at every overlap. For faded grey, use the three solid faded-ink tokens rather than mixing a new hex: `ink-muted` (75% of `ink-soft`; muted grey text — the Tempo details toggle, and every empty-state message — library "nothing here"/no-match lines, Book and Person Details' "No pieces yet", the setlists and program empties, Edit Setlist's "No matches" — except the Add to Setlist picker's and the sidebar's, which keep their own fainter italic), `ink-faint` (60%; quiet clickable icons — field chevrons, info hints, external links, copy, add rows, tag remove) and `ink-fainter` (50%; the footer mark, and things that can't be clicked — the no-file cover, the unavailable Open PDF button, list-card chevrons, a disabled autofill). Picked from a side-by-side comparison of one, two and three tiers. Those percentages are the light theme's; the dark theme's ladder is 85/70/60%, a step stronger, because the same contrast reads washed out on a dark ground (tried live in the Style Sampler).
- Every dropdown-style field (`TagComboBox`, `SingleSelect`, `SourceBookField`, and any future one) must support ArrowUp/ArrowDown (wrapping at both ends) and Enter.
- **Every dropdown list and menu looks the same** (picked from a side-by-side): the row under the pointer or arrow keys is `bg-paper-hover`, and a chosen row keeps ink text with a 14px accent `IconCheck` on the right — green means "chosen", never "pointed at" (`SingleSelect`, `SortControl`, `SourceBookField`, `TagComboBox`, `ContextMenu`, Piece Details' menus, the split step's menu, and their mockup copies). **Never a bare `<select>`**: Safari draws its popup in the Mac's colors, not the theme's. Use `SingleSelect` — its `label` is optional (`ariaLabel` names it instead), `size="sm"` gives the compact trigger Admin/User Settings use, `className` sizes it, and long lists scroll (`max-h-64`) with the arrow-key row kept in view.
- Card-style navigation renders a real `<Link>`/`<a>` (`components/ClickableCard.tsx`), never a click-handled `<div>` — a synthetic click handler has no `href`, so cmd/ctrl/middle-click and "open in new tab" silently don't work without a real anchor. A nested interactive child (a button inside the card) must call both `event.preventDefault()` and `event.stopPropagation()` to suppress the card's own navigation — `stopPropagation()` alone isn't enough, since it only stops React's synthetic handler, not the underlying anchor's native default action.
- `overflow: hidden` on an ancestor clips a `position: fixed` **or** `position: absolute` descendant regardless of that descendant's own computed geometry (bounding box, opacity, z-index can all report "correct" while nothing actually paints) — a popup/dropdown that must escape a `Modal`'s own rounded-corner clipping needs a real portal to `document.body`, not just a higher `z-index`. A `transform` on an ancestor is a second, independent reason a portal is needed: it makes that ancestor the containing block for any `position: fixed` descendant, so the descendant positions itself relative to the transformed ancestor instead of the viewport — `Modal.tsx`'s own dialog carries `transition-[transform,opacity]`/`scale-*` for its open/close animation, so anything rendered `fixed` inside it (a drag ghost that must track the raw pointer position, say) needs the same `document.body` portal even with no `overflow: hidden` in the way at all.
- A mutation's "in progress" UI needs an artificial minimum display duration (`lib/minDuration.ts`, `afterMinDuration`) — this app's mutations hit a local SQLite backend and routinely resolve in under one browser paint frame, so a stripe animation or "Saving…" state can be genuinely invisible without one.
- A CSS animation that must keep running under real main-thread load animates `transform`/`opacity` (compositor-only), never `background-position` (forces a full repaint on every single frame — a well-known main-thread-repaint hazard).
- Dot separator is a bullet (`•`), never an interpunct (`·`); page-range abbreviation is the academic `p.`/`pp.` convention, never `pg.` — both keep drifting into freshly-built `/mockup/*` screens with their own local formatting; grep for the literal stale pattern when finishing a new one rather than trusting memory of every call site.
- Click-to-copy always goes through the shared `lib/clipboard.ts` (`copyToClipboard`), never a bare `navigator.clipboard.writeText(...)` — the Clipboard API only exists in a secure context (HTTPS or localhost), which this app being reached over plain HTTP on a LAN (the common self-hosted case, no default reverse proxy/TLS) isn't; Firefox and Safari (desktop and iOS) enforce that strictly, so `navigator.clipboard` is `undefined` there and a bare optional-chained call silently does nothing. `copyToClipboard` falls back to `document.execCommand('copy')` and returns whether the copy actually succeeded — gate any "Copied!" feedback on that return value, not on the call having been made.
- **Cut-off text shows its full text on hover, in the system's own tooltip** (`lib/truncationTitles.ts`, installed in `main.tsx`): one document-level `mouseover` listener gives any `truncate`/`line-clamp-*` element that's actually cut off a plain `title` with its full text, and takes it away once it fits; a `title` a component set itself is never touched. Deliberately the OS tooltip, not `InfoTooltip`. Nothing to add per element — just truncate with those CSS classes, never by slicing the string.
- **The narrow-screen top bar sits above `#app-scroll-container`, never `sticky` inside it** (`AppShell.tsx`, `MobileNavTopBar`): iOS's rubber-band bounce at the top of a scroll container drags a sticky element down with the content, so a fast fling to the top pulled the bar off the screen's edge. Outside the scroller only the page bounces, under a bar that stays put. The library pages' toolbar (`LibraryToolbar`, and the three library mockups' copies) goes the same way: it renders through `components/PageToolbarSlot.tsx`'s `PageToolbarPortal` into a slot `AppShell` keeps between the top bar and the scroller (`lib/pageToolbarSlot.ts`'s context; in place outside `AppShell`), so it never bounces either and the scrollbar starts below it. Don't put a new always-visible bar inside the scroller as `sticky` — portal it into the slot.
- **A closed slide-in panel is `invisible`, not just moved off-screen or faded out** (the nav drawer, both filter drawers, their scrims, and the mockup copies): iOS Safari tints its toolbar from fixed elements at the screen's edge and kept the drawer's sidebar color after it slid away. Closed adds `invisible`, and the transition lists `visibility` (`transition-[translate,visibility]` — `translate`, not `transform`: Tailwind v4's `translate-x-*` sets the `translate` property, so naming `transform` leaves the slide unanimated, `transition-[opacity,visibility]`) so it hides only after the slide or fade finishes. Do the same for any new one.
- **iOS never zooms in on a focused field**: Safari zooms whenever a text field under 16px takes focus, so `index.html` adds `maximum-scale=1` to the viewport meta, from an inline script and only on iPhone/iPad (iPadOS reports itself as a Mac with touch points). iOS still allows pinch-zoom with it; Android would block pinch-zoom with it and never zooms on focus, so it stays plain there. Fields keep their sizes.
- `AppShell.tsx`'s outer container is `h-dvh`, never `h-screen` (`100vh`) — `100vh` stays pinned to a fixed worst-case viewport height and doesn't track mobile Safari's own dynamic address-bar/toolbar animation, which keeps changing the *actually* visible height while the user scrolls; a shell with a *nested* `overflow-y-auto` scroll container (not the document itself scrolling) is exactly the kind of element iOS Safari can reset `scrollTop` to 0 on when that mismatch gets reconciled mid-swipe. Any future shell-like component needs the same fix.
- A flex item's default `min-width` is `auto` (its own content's intrinsic minimum), not `0` — a long value with no natural break point (e.g. an underscore-joined filename) forces the item wider than its own flex-wrap container instead of wrapping. Add `min-w-0` to any flex item that might carry a long/unpredictable text value, `break-words` if it should wrap, or Tailwind's `truncate` (real single-line CSS ellipsis) if it should never wrap at all — prefer `truncate` over hand-rolled character-count slicing, since CSS truncates at whatever width the element actually renders at with no length to precompute.
- Page content has no width ceiling by default (`AppShell.tsx`'s `<main>` is intentionally unconstrained, since different pages want different caps) — reuse `lib/layout.ts`'s `CONTENT_MAX_W` (max-w-6xl, the app-wide default/fallback) or `WIDE_CONTENT_MAX_W` (max-w-[1800px], for Library/Books/People-style grid+list browsing views) on a page's own root wrapper rather than inventing a new arbitrary value or leaving a new page uncapped.
- This project's React Compiler setup disallows **reading**, not just writing, a ref's `.current` during render (`react-hooks/refs`) — the common "read a ref for a cheap memoization/derived value" pattern still needs the value to be real `useState`, populated from an event handler or effect, never a ref accessed inline in the render body. It also flags a plain `setState` call directly inside a `useEffect` body (`react-hooks/set-state-in-effect`) — prefer deriving/updating state from the specific event handler that causes the change (e.g. a rename's own `onBlur`) over watching a query result drift in an effect and reacting to it.
- An `<svg viewBox="...">` with no `width`/`height` attributes has no absolute intrinsic size for CSS to size a replaced element from — only an aspect ratio. `max-w-*`/`max-h-*` (even paired with `w-auto`/`h-auto`) can collapse it to ~0 instead of scaling it down, unlike a raster `<img>`, which always has real natural pixel dimensions once loaded. Give the `<svg>` explicit `width`/`height` attributes matching its `viewBox` 1:1 before relying on CSS max-constraints to shrink it.
- **react-hook-form's `getValues()` can hand back a reference that's still aliased with whatever object was originally passed into `defaultValues`** — a real, live-confirmed bug, not a hypothetical: a form built as `useForm({ defaultValues: { items: liftedParentState } })` that periodically flushes edits back up via `onChange(getValues().items)` can end up with `getValues().items === liftedParentState` once that first flush's reference gets adopted into the parent's own state — every *later* flush then hands back that exact same (RHF-internally-mutated) reference, and React's `useState` setter bails out (`Object.is` sees "no change") without re-rendering, even though the array's contents have moved on. Silent, no error, no warning — the live UI and RHF's own internal state stay fully correct throughout, so it presents as "autosave stops working randomly," not a crash. Never pass `getValues()`'s return value straight into a parent-lifted state setter — clone it first (a `.map(item => ({...item}))` shallow clone of the array and each top-level item is enough) at every flush call site. Found via `BookUploadTitlesStep.tsx`'s own draft-persistence flow, memory `frontend_book_upload_wizard_phase3.md`.
- **A hand-written comment inside a standalone `.svg` file can't contain a literal `--` sequence anywhere in its body** — real `.svg` files parse as XML, which (unlike HTML) forbids `--` inside a comment, not just at the closing `-->`. Has broken a shipped SVG twice by naming a CSS custom property in a comment (e.g. `--color-sidebar-bg`); reword around the literal double-hyphen rather than trying to escape it (XML comments have no escape mechanism), and validate with `python3 -c "import xml.dom.minidom; xml.dom.minidom.parse('file.svg')"` before considering the file done. Doesn't apply to inline `<svg>` in JSX/HTML.
- Cross-element pointer tracking during a custom gesture (long-press-cancels-on-drag, a tap-vs-drag distinction, etc.) should use `element.setPointerCapture(event.pointerId)` in `onPointerDown`, not `document.elementFromPoint()` hit-testing — a mouse has no implicit capture to its down-target the way touch does, so `elementFromPoint` was only ever a workaround for that asymmetry. Once captured, every subsequent `pointermove`/`pointerup` for that pointer keeps targeting the original element regardless of where the pointer physically travels, for mouse and touch alike — reach for this first whenever an interaction only needs "did this same pointer move" rather than genuinely tracking which element is under the cursor.
- A drag-to-reorder gesture built on `setPointerCapture` must capture the pointer on a stable ancestor, never on the element actually being dragged — a reorder, by definition, moves that element to a new position among its siblings (React's key-based reconciliation via `insertBefore`), and Chromium drops pointer capture the instant its held element is relocated in the DOM this way, even without removal/recreation. Since no `pointerup` then fires, whatever state the gesture tracks stays stuck with nothing left to clear it — reported live as "the drag needs an extra click to drop" and reproduced with zero scrolling involved, so don't assume a report naming scrolling is really about scrolling. Capture on a `useRef`-held container that never itself reorders instead (`onPointerMove`/`onPointerUp`/`onPointerCancel`/`onLostPointerCapture` all move there too); keep `onPointerDown` per-row only to record which row started the drag. Separately: a "don't start a drag from this button" exclusion check must use `target instanceof Element`, not `instanceof HTMLElement` — a click on a button's own inner `<svg>` icon lands on an `SVGElement`, which fails the narrower check and silently lets drag-capture steal the click.
- A JS-driven drag's own "grabbing" cursor can't just be a `:active`/`active:` Tailwind variant on the dragged element — that reverts to the plain default arrow the instant the pointer physically leaves that element's own bounding box, which happens constantly mid-drag (over gaps between rows, a floating `pointer-events: none` ghost, or any other element that doesn't itself declare a cursor). Set `document.body.style.cursor = 'grabbing'` for the drag's duration instead — `cursor` is inherited, so it applies everywhere nothing more specific overrides it, not just while hovering the one element that started the gesture. Do this from a `useEffect` keyed on the dragging state, not a direct mutation inside the pointerdown/pointerup handlers — this project's React Compiler setup flags mutating `document` (or anything else defined outside the component) from a plain function with `react-hooks/immutability`, even when that function is really just an event handler; the effect's own cleanup clearing the cursor is exactly the pattern its error message points to.
- A literal non-breaking-space character sitting directly in JSX/template-literal source trips this project's `no-irregular-whitespace` ESLint rule, even though it renders correctly — use a numeric character-code escape inside the string instead of a raw byte.
- A "coming soon"/not-yet-wired control needs `InfoTooltip` (`components/InfoTooltip.tsx`) as its trigger, not a native `disabled` button with a `title` — a `disabled` element receives no pointer events at all, so there's nothing to tap to reveal *why* it's inert on a touch device with no hover concept. Pair `InfoTooltip` with `showPointerCursor={false}` (cursor reads `default`, not `pointer`) and a faint container `opacity` on `triggerClassName` to still look inert while staying genuinely tappable. Inside a dropdown, drop the dropdown's own `overflow-hidden` (its `py-1` already keeps row hover tints inside the rounded corners): `InfoTooltip`'s bubble isn't portaled and fits itself inside the nearest clipping ancestor, which for a one-row menu leaves it nowhere to go — the "+ Annotations" items on Piece Details and Setlist Details (real and mockup) are the reference.
- A small `?`-style hint next to a field label uses `components/InfoIconTooltip.tsx`, not a hand-copied `<InfoTooltip><IconInfoCircle/></InfoTooltip>` block — this used to be copy-pasted at 10 real call sites (`EditBookModal.tsx`, `EditPieceModal.tsx`, `SourceBookField.tsx`, `BookUploadAboutStep.tsx`, the Admin Users permission grid, People Library's own "Show all composers" hint), with real drift already found between copies (one site used a translucent icon color, violating the icon-color-preblend rule below; another used a smaller icon size for no real reason). `InfoTooltip.tsx`'s own bubble also pins `font-sans` explicitly on itself now, not left to ambient inheritance — found live via a caller that nested one inside a `font-display` ancestor and got a serif tooltip message, since the bubble is a sibling of its trigger, not a descendant, so nothing else in the tree defended against that.
- Swapping a `@font-face`'s underlying typeface for one with different proportions needs two independent CSS Fonts 4 fixes, not one, and they interact non-obviously. `size-adjust` matches apparent glyph size (x-height/cap-height, read off each file's `OS/2` table) between the old and new face at the same declared `font-size` — but it also scales the font's own line-box metrics right along with its glyphs, which can make `line-height: normal` (this app's default) reserve visibly more space below every line if the new face has a bigger native descender allowance (real, reported live as "extra space below every line," found to be a genuine 27%+ taller line box, not a false impression). `ascent-override`/`descent-override`/`line-gap-override` fix that second problem independently — except a naive first attempt at "just use the old face's own raw ascent/descent percentages" undershoots, because `size-adjust` scales those override percentages too, the same way it scales the font's native metrics; hitting an exact target means pre-dividing the target percentages by the `size-adjust` factor (e.g. a 97% target under a 115.7% size-adjust needs `ascent-override: 83.8%`, not `97%`). Verify both fixes with real `getBoundingClientRect()` measurements before and after, not by trusting either descriptor's spec wording. (Found during a serif-font evaluation that was itself later rolled back for unrelated aesthetic reasons — the CSS technique stands regardless of which typeface it was found on; see memory `frontend_design_system.md`.)
- Markdown `*emphasis*` (`MarkdownText.tsx`'s own `em` output) nested inside an already-italic block (anything wrapped in the `italic` utility — a quote, a custom setlist entry's note) inverts to roman instead of doubling the slant, via a global `@layer base` rule (`.italic em { font-style: normal }`, `index.css`) — the standard typographic convention for emphasis-within-italic, since `<em>`'s own UA-stylesheet italic wins regardless of its ancestor, so left alone the emphasis is visually indistinguishable from the italic text around it and the emphasis is lost. App-wide by cascade, not per-call-site — a future italic block that renders Markdown gets this for free, no extra wiring needed.
- `mx-auto` on a direct child of a `flex flex-col` container doesn't just center it — an auto margin on a flex item's cross axis (width, in a column flex) overrides `align-items: stretch` entirely per the flexbox spec, so the item sizes to its own *content* width first and only then gets centered in whatever space is left over. A child meant to be "capped at some `max-w-*` and centered" (e.g. a page section narrower than its own page) silently never reaches that cap if its content is narrower than it — confirmed live via `getBoundingClientRect()`, not assumed from the classNames (a text-driven list rendered ~473px wide instead of the intended ~896px `max-w-4xl`). Fix: add `w-full` alongside `mx-auto max-w-*` — forces the item to actually fill the container's cross-axis width up to the cap before the auto margins center it.
- **A date-only value (`"YYYY-MM-DD"`, e.g. a setlist's `gigDate`) goes through `lib/dateOnly.ts`, never a bare `new Date(iso)`** — JavaScript has no date-only type, and a date-only string parses as *midnight UTC*, so `toLocaleDateString`'s default (the viewer's own timezone) shows the previous day anywhere west of UTC: every gig date in the Americas used to display one day early, while the Edit dialog's raw `<input type="date">` showed the right one. `formatDateOnly` formats in UTC (the locale — month names, order — still follows the viewer), `todayDateOnly`/`daysUntil` compare calendar days, matching the server's own `gigDate < today` string comparison (`repo.Setlist.EffectiveArchived`). A real timestamp (`createdAt`/`updatedAt`) is an instant and stays a plain `new Date(...)`.
- React Router reuses the same component instance across a `navigate()` that only changes a route *param* (e.g. `/setlists/:id` → a different `:id`), not a route pattern change — it does not remount. Any local boolean/modal-open state that isn't explicitly reset before such a navigate survives into the newly-navigated page, silently reopening whatever it was controlling there. Real bug: `SetlistPage.tsx`'s own Duplicate action created the copy, then `navigate()`d straight to it without first setting `duplicateModalOpen` back to `false` — the confirm modal stayed open, now showing on top of the *new* setlist's page. Fix: reset any such state in the same `onSuccess` handler, immediately before (or alongside) the `navigate()` call, not left for an unmount that never happens.

## Docker / build
Single Docker image — the Go binary embeds the built frontend via `//go:embed` (`internal/webui`, `all:dist`, with a committed placeholder `index.html` so `go build`/`go run` compile without a real frontend build present; local dev serves the frontend via Vite on `:5173` instead). `internal/handlers/server.go`'s catch-all (`spaHandler`) returns the `{error}` envelope for an `/api/*` miss, otherwise serves a static file from the embedded FS or falls back to `index.html` so a client-side route survives a hard refresh.

- **`Dockerfile`**: 3 stages, no cross-compilation in the file itself — `node` builds the frontend, `golang` copies that output over the placeholder and runs `CGO_ENABLED=0 go build` (no CGO anywhere in this module, so this produces a fully static binary), `debian-slim` is the runtime (`poppler-utils` for PDF thumbnailing, `wget` for the `HEALTHCHECK`). Runs as a fixed non-root uid/gid 1000 — `/data` is `chown`'d to that user at build time so a fresh Docker named volume inherits correct ownership automatically; a host bind-mount (what `docker-compose.yml` actually uses) keeps whatever ownership the host directory already has, which needs a manual `chown` on a host where the operator's own uid isn't 1000 (documented inline in `docker-compose.yml`).
- **`docker-compose.yml`**: one service, host bind-mount at `/data`, commented `environment:` block, healthcheck using `/healthz`.
- **CI** (`.github/workflows/docker-publish.yml`): a push to `main` runs a validation build only (`push: false` — what the README's Build-status badge reflects day to day). Three floating tags:
  - **`:dev`** rebuilds nightly (`schedule`, an arbitrary off-the-hour UTC cron), from the latest commit on `main` whose own push-triggered validation build actually succeeded — not just whatever `main`'s HEAD happens to be, which could be unvalidated or broken. Resolved via `gh run list` against this same workflow file (`push`/`main`/`success`, newest first) in a "Resolve latest validated commit on main" step, then checked out by that specific SHA; the job fails loudly rather than building an unvalidated commit if no successful run is found. Needs `actions: read` on top of the usual `contents: read`/`packages: write` to query its own past runs. Never moves on a release event, of either kind.
  - **`:latest`** moves on a `released` event only, and only after confirming via the GitHub API that this release is genuinely what GitHub currently considers latest (not just "most recently published") — a release for an older branch, or with "Set as the latest release" unchecked, can't clobber it.
  - **`:beta`** is a strict superset of `:latest` — moves in the exact same step, under the exact same latest-check gate, whenever `:latest` does (a `released` event), *and* unconditionally on every `prereleased` event too (no latest-style check there — every pre-release is by definition newer than the last one). So `:beta` always names the newer of "the current stable release" and "the current pre-release," while `:latest` only ever names the former.

  Both a `released` and a `prereleased` event build a real multi-arch image either way (native ARM64 runners, not QEMU — `linux/amd64`/`linux/arm64` as separate matrix jobs pushed by digest, merged into one manifest via `docker buildx imagetools create`) tagged with the release's own version tag (e.g. `v2.0.0-beta.1`) — every published release, stable or not, stays pinnable/referenceable regardless of which floating tag it also moves. The nightly `:dev` build has no equivalent version tag — there's no release to pin it to, `:dev` itself is the only pointer, and tomorrow's nightly run just moves it again. `workflow_dispatch` re-runs just the `:latest` check/re-point with no rebuild, for correcting which release is marked latest after the fact. Every `${{ github.event.release.tag_name }}` reference goes through an `env:` var, never interpolated directly into a `run:` script body (git ref names allow shell metacharacters).
- **GHCR package visibility is independent of the source repo's visibility** — after the first release-triggered publish, the package defaults to private regardless, and needs a manual Package settings → visibility → Public (this **cannot be undone** through the normal UI once switched).

## Native app (Wails)
A second, parallel distribution channel alongside Docker (design doc's original scope never included this — added later for a lower-friction install on a musician's own Mac/Windows machine, per the README's own "Installation" section). `cmd/sonneck-desktop` is a real, separate `main` package — not a build tag on `cmd/sonneck` — since a Wails app needs `wails.Run(...)` wired to its own window/event loop, structurally different from `cmd/sonneck`'s plain `http.ListenAndServe`. It reuses the exact same bootstrap (`config.Load`, migrations, `handlers.New(...)`) and passes the resulting `http.Handler` straight into Wails' `AssetServer.Handler` — zero adapter code, zero separate API surface; `internal/handlers` itself has no Wails dependency at all. Linux is out of scope for this channel (Docker already serves that audience).

- **`buildTarget`** — `"docker"` (default) or `"native"`, ldflags-injected exactly like `buildSHA`/`buildDate`, threaded through `handlers.New(...)` onto `Server.BuildTarget` and surfaced on `GET /api/config`. The one signal every native-only frontend branch and backend behavior gates on.
- **A native install has no `docker-compose.yml` environment block** — anything Docker configures via env vars, native has to persist itself. `internal/nativeconfig` (`Settings{LibraryPath, ShareOnNetwork, PendingLibraryPath, PendingMoveExisting}`) is a small JSON file at `os.UserConfigDir()/Sonneck/config.json`, read once at process start (before `config.Load()`) and written by two real, admin-gated (or pre-first-launch) endpoints — `GET`/`PATCH /api/native/settings`. `internal/netinfo.ListenAddress`/`ListenWithFallback` resolve the actual bind address: native defaults to `127.0.0.1`-only (never reachable from another device) unless `ShareOnNetwork` is on, and retries up to 9 ports above the configured default if it's taken — Docker's own one-attempt, every-interface behavior is unchanged either way, gated on `buildTarget`. `DataDir`'s own GOOS-aware default (`config.DefaultDataDir`) is the user's own Music folder on macOS/Windows, not `/data`.
- **Everything library-path/network-related is "persist immediately, apply on next restart," not live** — `DATA_DIR` and the bind address are both resolved once at process start, so neither can change without a real relaunch. `PATCH /api/native/settings` always writes through to disk on every call (so an abandoned toggle can never resurface later); a genuine restart is a separate, explicit action (`POST /api/native/restart` — spawns a fresh copy of the process via `os.Executable()`/`exec.Command`, then asks the *current* process to shut down gracefully via a real Wails `runtime.Quit`, not a raw `os.Exit`, so deferred cleanup — especially `db.Close()` — actually runs). A changed library location is a real two-phase commit: `PATCH` only ever writes `PendingLibraryPath`/`PendingMoveExisting`, and `nativeconfig.ApplyPendingLibraryMove` (`cmd/sonneck-desktop/main.go`, called before `config.Load()`/`db.Open()` on the next boot) does the actual move — `os.Rename` first, falling back to a manual recursive copy+delete for a genuine cross-device move (a different drive), refusing outright rather than merging if the destination already has content, and leaving everything untouched on failure (the app just boots against the old directory, pending move preserved to retry later).
- **The native OS folder-picker dialog needs no Wails `Bind`/generated JS bridge at all** — `runtime.OpenDirectoryDialog`/`runtime.Quit` both just need the `context.Context` Wails hands its `OnStartup` callback, and can be called from any goroutine. `cmd/sonneck-desktop/main.go` stores that context in a package-level, mutex-guarded var and exposes it via two plain closures (`chooseFolder`/`requestRestart`) wired into `handlers.NativeOptions` — so "choose a folder"/"restart" are just two more ordinary `POST` endpoints the existing fetch-based frontend already knows how to call.
- **`/api/native/*` (settings/choose-folder/restart) has a real, non-default access rule**: reachable with no session at all while first-launch hasn't completed yet (the native Folder step needs to persist a path and restart before any session can exist — same posture as `POST /api/setup/complete`), `admin`-gated once it has. This needed a new `preFirstLaunchOnlyPaths` table in `authMiddleware` (`internal/handlers/middleware.go`), distinct from the permanently-open `publicAPIPaths` — these routes must not stay reachable by an unauthenticated LAN request once Share on Network is actually on.
- **Native-only Admin Settings additions**, both real, both gated on `buildTarget === 'native'`: **Share on Network** (off by default; once on, shows the primary LAN address with a copy button and a genuinely client-side-generated QR code — the `qrcode` npm package's browser build, canvas output, never a remote QR-generation API, since that would leak a LAN address to a third party for a feature that only needs to work on the LAN; the code is drawn `#1a1a1a` on `#ffffff` in a `bg-white` tile (`AdminPage.tsx`'s `QRCodeCanvas`), **fixed in every theme on purpose** — not a style and not a missed token: a QR code needs dark-on-light contrast to scan, so a dark mode must leave it alone) and **Library location** (folder picker + the move-vs-point-only choice described above). Both surface a "Restart Now" banner when a change is pending, never silently apply.
- **`.github/workflows/native-build.yml` ("Native Release")** builds and packages for both OSes, then attaches the result directly to a GitHub Release — triggers only on a real `release`/`prereleased` event or manual `workflow_dispatch`, no push trigger (a full run — poppler bundling, codesigning, NSIS packaging, a real smoke-test launch — is expensive enough not to run on every push once past active development). `wails.json`'s `info.productVersion` is rewritten from the release's own tag before `wails build` runs — but the two OS jobs now do this asymmetrically, since only one of them has a real numeric-format constraint to satisfy. macOS keeps its original behavior: the tag padded to `X.X.X` (a stray `-alpha`/`-beta`/`-rc` suffix included as-is), since `Info.plist` tolerates any string. Windows keeps `wails.json`'s `productVersion` as the **real tag verbatim** (so the installer's own file-properties "Product version"/"File version" strings stay human-meaningful, e.g. `0.7-beta.4`) and instead patches a *separate*, NSIS-safe numeric value directly into `project.nsi`'s `VIProductVersion`/`VIFileVersion` lines only — those are binary version-resource fields NSIS requires to be exactly 4 plain integers, which a real tag with a prerelease suffix isn't. Any `-alpha`/`-beta`/`-rc[.N]` qualifier folds into the numeric patch slot via non-overlapping bands (`alpha`=0, `beta`=100, `rc`=200, offset by the qualifier's own iteration number; a real patch number present alongside a qualifier is multiplied by 1000 first so it can't collide with a band) — e.g. `0.7-beta.4` → `0.7.104`. Found via a real beta release (tag `0.7-beta`) that built fine on macOS but hard-failed Windows with NSIS's own `invalid VIFileVersion format` error, since the un-normalized tag flowed straight into a field that can't hold non-numeric text. macOS bundles `poppler-utils` via Homebrew + `dylibbundler` into the `.app` and re-signs ad-hoc (unsigned distribution is the accepted v1 posture, not an oversight — see below); the bundled binaries' own baked-in rpath is `@executable_path/../libs/` **literally**, so the destination folder dylibbundler writes to must be named `libs`, not `lib`, regardless of what seems more natural. Windows stages a prebuilt [oschwartz10612/poppler-windows](https://github.com/oschwartz10612/poppler-windows) release into the installer's own source tree before `wails build -nsis` runs, so `build/windows/installer/project.nsi` (hand-customized, not the Wails-generated default) can bundle it inside the installer itself; NSIS isn't preinstalled on `windows-latest` and needs Chocolatey, and a machine-PATH change from an installer inside one CI step doesn't propagate to the next step in the same job — only `$GITHUB_PATH` is guaranteed to. Both platforms' smoke-test also asserts the served root page is the real frontend, not `internal/webui/dist`'s own committed placeholder (a real regression this project shipped with silently until a user actually opened a built app).
- **The native window opens on the theme's page color, not white** (`cmd/sonneck-desktop/theme.go`): Wails' own default window background is white, which flashed before a dark page painted. Before `wails.Run`, `readLaunchTheme` reads account 1's saved `theme_preference`, and `launchWindowColor` (the only account outside OIDC); `launchWindowColor` passes `--color-paper`'s light or dark value as `BackgroundColour`; "system" asks the OS (`osPrefersDark`: macOS's `AppleInterfaceStyle` default, Windows' `AppsUseLightTheme` registry value; build-tagged files, light elsewhere). On macOS that color only reaches the window, and the WebKit view paints its own white over it until the page loads, so `mac.Options.WebviewIsTransparent` is on; Windows gives WebView2 the same color by itself. After launch, `lib/theme.ts`'s `applyTheme` keeps the window color in step through `window.runtime.WindowSetBackgroundColour` (Wails injects `window.runtime` into the page it serves; absent in a browser).
- **The title bar never clashes with the theme** (picked from a side-by-side over fully frameless windows, which lose the native window buttons): **macOS hides it** (`mac.TitleBarHiddenInset()` — Wails can't change a Mac window's light/dark look while running; its theme calls are no-ops there). The page runs to the top and the traffic lights float in a 52px band (centered 26px down, ending 78px from the left; measured in a real build). `index.html`'s no-flash script marks `<html data-native-titlebar>` when `window.runtime` exists on a Mac user agent; `index.css` turns that into `--titlebar-inset` (52px) and `--titlebar-lights` (88px), both 0 everywhere else. Pages keep starting at the top — no empty band above them; only what would sit under the lights moves: the expanded sidebar's top row already leaves that corner empty, the collapsed rail widens to `max(4rem, --titlebar-lights)` so all three lights sit on the dark rail (its icons and button stay centered; picked from real renders over pushing the page down while collapsed) and gets an inset-tall band above its button, the narrow-window top bar pads its left by `--titlebar-lights`, and the phone-width drawer and the photo viewer's close button drop by the inset. Dragging the window: `lib/nativeTitleBar.ts`'s `dragRegion` (`--wails-draggable: drag`, which inherits, so a control inside opts out with `noDragRegion`) and `zoomOnDoubleClick` (Wails' drag skips double-clicks) on the sidebar's top row, the collapsed rail's spacer and the narrow top bar; screens without the app shell (sign-in, first launch, auth change) get `components/NativeTitleBar.tsx`'s full-width `TitleBarDragStrip` (rendered in `main.tsx`, hidden by an `index.css` `:has(#app-scroll-container)` rule while the shell is up). **Windows keeps its native frame** (Snap Layouts and all) with the bar following Sonneck's theme: `launchWindowsTheme` at launch, then `applyTheme`'s `WindowSetDarkTheme`/`WindowSetLightTheme`; on Windows 11 it's tinted with the page colors (`windowsTitleBarColors`: paper, ink, ink-faint, border).
- **Links the bare web view can't handle are rerouted** (`lib/nativeLinks.ts`, installed in `main.tsx` only when `window.runtime.BrowserOpenURL` exists — never in a browser): the macOS web view (WKWebView) has no browser around it, so a link off Sonneck would do nothing or replace the app, and Wails implements neither downloads nor a PDF window. One document-level click/middle-click listener: an `http(s):`/`mailto:` link to another origin goes to Wails' `BrowserOpenURL` (the system browser — the footer, Admin's "version X available" pill, IMSLP/Wikipedia, Markdown links); a same-origin `/api/` link with `download` (Download PDF, Download Set PDF) goes to `POST /api/native/save-file`, a native Save dialog with the file's usual download name; a same-origin `/api/` link with `target="_blank"` (Book Details' Open Book PDF) goes to `POST /api/native/open-file`, which opens it in the system's default app (Preview). Both endpoints (`internal/handlers/nativefiles.go`) re-request the URL through the app's own complete handler (`Server.root`) with the caller's cookie, so a desktop download gets exactly the sign-in and permission checks a browser download does; they take only this app's own `/api/` paths, stream the file to disk (never whole in memory), need only a signed-in user (not admin like the rest of `/api/native/*`), and 404 outside the native build. `NativeOptions.SaveFile` (Wails `SaveFileDialog`) and `OpenPath` (`pkg/browser.OpenFile`) do the OS side. A new link of any of these kinds needs nothing extra — a plain `<a href>` (with `download` or `target="_blank"` for a file) is enough.
- **Testing a desktop build locally (dev tooling): run it as an `.app`, never as a bare binary.** Build without the Wails CLI by copying a `vite build` into `internal/webui/dist` and running `CGO_LDFLAGS="-framework UniformTypeIdentifiers" go build -tags desktop,production ./cmd/sonneck-desktop` (the CLI adds that framework itself; restore the committed placeholder `index.html` afterwards). A bare executable gets every macOS Open/Save panel cancelled the instant it opens — the system's out-of-process panel service needs a bundle — so the folder picker and Download's Save dialog look broken when they aren't. Wrap it in a minimal bundle (`Contents/MacOS/<exe>` plus an `Info.plist` with `CFBundleIdentifier`/`CFBundleExecutable`, ad-hoc `codesign -s - --force`) and launch it with `open -n --env DATA_DIR=<throwaway> --env PORT=<port> <bundle>.app`, so `./data` is never touched; stop it by the port's PID. A panel can be checked without a screen: `curl -m 8 -X POST 127.0.0.1:<port>/api/native/choose-folder` only times out if the panel stayed open.
- **Deliberately accepted/deferred, not bugs**: distribution is unsigned (real Gatekeeper/SmartScreen warnings on first launch, documented in the README's own Installation section, not blocking); OIDC/SSO is Docker-only (needs secrets + a registered redirect URI a native app has no safe place to hold); native Spaces-based fullscreen (the title bar's hover-to-fullscreen affordance, Cmd+Ctrl+F) doesn't work — a real Wails v2 gap ([wailsapp/wails#2582](https://github.com/wailsapp/wails/issues/2582)) that would need custom cgo/Objective-C code reaching into the actual `NSWindow`, which Wails doesn't otherwise expose a path for.
